### 073-1.자료 구조의 정의 (Definition of Data Structure)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 효율적인 프로그램을 작성하기 위해 자료를 기억장치(메모리) 공간 내에 **저장하는 방법**과, 저장된 자료 간의 **관계 및 처리 방법**을 연구하고 분석하는 것
- **[2] 핵심 키워드:** 저장 공간의 효율성, 실행시간의 신속성, 자료의 표현/연산, 구조화
- **[3] 구조 / 관점 / 분류:** 컴퓨터 과학 - 데이터 관리 기초
- **[4] 시험 포인트:**
    - **고려사항 (빈출):** 효율적인 프로그램을 작성할 때 가장 우선적으로 고려해야 할 두 가지는 **'저장 공간의 효율성(Space)'**과 **'실행시간의 신속성(Time)'**임
    - **특징:**
        - 자료 구조에 따라 프로그램의 **실행 시간**이 달라짐
        - 어떠한 자료 구조에서도 필요한 모든 연산들을 처리할 수 있음
- **[5] 한 문장 설명:** 자료 구조는 프로그램의 저장 공간 효율성과 실행 속도 신속성을 높이기 위해 데이터의 저장 방식과 관계를 구조화하는 기술이다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **왜 배우는가?:**
    - 도서관에서 책을 아무렇게나 쌓아두면 찾기 힘들지만(비효율), 번호순으로 꽂아두면(자료구조 적용) 빨리 찾을 수 있음.
    - 컴퓨터 메모리도 마찬가지로, 데이터를 어떻게 조직화하느냐에 따라 성능(속도와 메모리 사용량)이 천지차이임.
- **주요 목표:**
    - **공간 복잡도 (Space Complexity):** 메모리를 얼마나 적게 쓰는가?
    - **시간 복잡도 (Time Complexity):** 얼마나 빨리 실행되는가?

## 073. 자료 구조의 분류 (Data Structure)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 데이터를 효율적으로 저장하고 관리하기 위해 분류하는 체계
- * 핵심 키워드**: 선형 구조, 비선형 구조, 선형 리스트, 트리, 그래프
- * 구조 / 관점 / 분류**: 데이터 간의 연결 관계에 따라 선형 구조와 비선형 구조로 분류
- * 시험 포인트**: 선형 구조(스택, 큐, 데크)와 비선형 구조(트리, 그래프)를 구분하는 문제
- * 한 문장 설명**: 자료 구조는 선형 리스트, 연결 리스트와 같은 선형 구조와 트리, 그래프 같은 비선형 구조로 나뉜다.
- * 연관 설명**: 074, 075, 076, 078

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- 선형 구조(Linear Structure): 데이터가 일렬로 나열되는 구조 (배열, 리스트, 스택, 큐)
- 비선형 구조(Non-Linear Structure): 데이터가 계층적이거나 망 형태로 연결된 구조 (트리, 그래프)
- 연속 리스트: 배열과 같이 연속되는 기억장소에 저장되어 밀도가 가장 좋음
- 연결 리스트: 임의의 공간에 데이터를 두고 포인터로 연결하여 삽입·삭제가 용이함
- 자료 구조의 선택은 프로그램의 실행 속도와 메모리 사용 효율에 직접적인 영향을 줌

### 073-2.열 (Array)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** **동일한 자료형(Same Data Type)**의 데이터들이 **같은 크기**로 나열되어 **순서**를 갖고 있는 집합
- **[2] 핵심 키워드:** 동일 자료형, 정적(Static), **첨자(Index/Subscript)**, 반복 처리, n차원
- **[3] 구조 / 관점 / 분류:** 자료 구조 - 정적 자료 구조 (선형 구조)
- **[4] 시험 포인트:**
    - **정적 특성 (단점):** 기억장소의 **추가가 어렵고**, 데이터 삭제 시 해당 공간이 **빈 공간**으로 남아있어 **메모리 낭비**가 발생함
    - **접근 방법:** **첨자(Index)**를 이용하여 데이터에 빠르게 접근함
    - **활용:** 반복적인 데이터 처리 작업에 적합하며, 동일한 변수 이름을 사용하여 처리가 간편함
    - **구조 표현:**
        - **1차원 배열:** `a[0], a[1], ... a[n-1]` (한 줄로 나열)
        - **2차원 배열:** `a[0][0], a[0][1]...` (행과 열로 구성된 행렬 형태)
- **[5] 한 문장 설명:** 배열은 동일한 자료형을 가진 정적인 자료 구조로, 첨자(Index)를 통해 빠르게 접근하나 데이터 삭제 시 메모리 낭비가 발생할 수 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **메모리 낭비의 의미:**
    - 배열은 처음 만들 때 크기를 고정함 (예: 10칸).
    - 중간에 데이터를 지워도 그 '칸' 자체는 사라지지 않고 비어있는 상태로 유지되므로, 다른 용도로 쓰기 어려움 (유연성이 떨어짐)
- **첨자(Index):**
    - 책의 페이지 번호와 같아서, 순차적으로 뒤질 필요 없이 "5번 데이터를 가져와"라고 하면 바로 접근 가능함.
    - 보통 0부터 시작함 (`a[0]`이 첫 번째 데이터)

## 074. 선형 리스트(Linear List)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 데이터들을 일정한 **순서(Order)**에 의해 나열한 자료 구조
- **[2] 핵심 키워드:** 연속 리스트(배열), 연결 리스트(포인터), 밀도 1, 삽입/삭제 용이성, 접근 속도
- **[3] 구조 / 관점 / 분류:** 자료 구조 - 선형 구조의 구현 방식 (배열 vs 포인터)
- **[4] 시험 포인트:** **'연속 리스트(배열)'**와 **'연결 리스트'**의 장단점 비교가 핵심임.
    - **연속 리스트 (Contiguous List) = 배열:**
        - **저장 방식:** 기억장소에 **연속적으로** 저장됨
        - **장점:** 기억장소 이용 효율(밀도)이 **1**로서 가장 좋음 (빈 공간 없이 꽉 채움)
        - **단점:** 중간에 데이터를 삽입/삭제하려면 기존 자료들을 **이동(Move)**시켜야 하므로 번거로움
    - **연결 리스트 (Linked List):**
        - **저장 방식:** 자료들이 **임의의 기억공간**에 흩어져 있으며, **포인터(Pointer)**를 이용해 서로 연결됨
        - **장점:** 노드의 **삽입·삭제 작업이 용이**함 (데이터 이동 없이 포인터만 바꾸면 됨)
        - **단점:**
            - 포인터를 저장할 공간이 추가로 필요하여 **기억 공간 이용 효율이 좋지 않음**
            - 포인터를 찾아가는 시간이 필요하므로 **접근 속도(Access Time)가 느림**
            - 중간 링크가 끊어지면 다음 노드를 찾을 수 없음
- **[5] 한 문장 설명:** 선형 리스트는 연속된 공간을 쓰는 연속 리스트(검색 빠름, 삽입/삭제 느림)와 포인터로 연결된 연결 리스트(삽입/삭제 빠름, 검색 느림)로 나뉜다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **이미지로 보는 동작 원리:**
    - **연속 리스트(배열) 삽입/삭제:**
        - 중간에 '금'을 넣으려니 뒤에 있는 '토, 일'을 한 칸씩 뒤로 밀어야 함 (비효율).
        - '수'를 제거하려니 뒤에 있는 '목, 금, 토, 일'을 한 칸씩 앞으로 당겨야 함 (비효율).
    - **연결 리스트 구조:**
        - `Data` 필드와 `Pointer(Link)` 필드로 구성됨.
        - 물리적으로는 메모리 여기저기(번지수 106, 7, 2...)에 흩어져 있지만, 화살표(포인터)를 따라가면 논리적으로 순서가 이어짐.
- **비유:**
    - **연속 리스트:** 영화관 지정석 (사람들이 다닥다닥 붙어있음. 중간에 한 명 끼워 넣으려면 다 일어나서 한 칸씩 옆으로 가야 함).
    - **연결 리스트:** 보물찾기 (첫 번째 쪽지가 두 번째 쪽지 위치를 알려줌. 중간에 코스를 바꾸려면 쪽지 내용만 고치면 됨).

## 075. 스택(Stack)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 리스트의 **한쪽 끝(Top)**으로만 자료의 삽입(Insert)과 삭제(Delete) 작업이 이루어지는 자료 구조
- **[2] 핵심 키워드:** **후입선출(LIFO)**, Top/Bottom, Push/Pop, **오버플로(Overflow)**, **언더플로(Underflow)**, 재귀(Recursion)
- **[3] 구조 / 관점 / 분류:** 자료 구조 - 선형 구조 (제한된 접근)
- **[4] 시험 포인트:**
    - **작동 원리 (LIFO):** **'나중에 들어온 것이 먼저 나간다(Last In First Out)'**는 원칙이 가장 중요함
    - **주요 용도 (암기 필수):** **재귀 호출(Recursion)**, **후위(Postfix) 표기법** 연산, 서브루틴 호출, 인터럽트 처리, 깊이 우선 탐색(DFS) 등 "왔던 길을 되돌아가는" 경우에 사용됨
    - **포인터 역할:**
        - **Top:** 가장 마지막에 삽입된 자료가 있는 위치를 가리킴 (삽입/삭제의 기준점)
        - **Bottom:** 스택의 가장 밑바닥
    - **에러 상황:**
        - **Overflow:** 꽉 찬 스택에 더 넣으려고 할 때 (`Top > M`)
        - **Underflow:** 텅 빈 스택에서 꺼내려고 할 때 (`Top = 0`)
- **[5] 한 문장 설명:** 스택은 나중에 들어온 데이터가 먼저 나가는 LIFO 구조로, 재귀 호출이나 후위 표기법 계산 등에 쓰이며 한쪽 끝(Top)에서만 연산이 일어난다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **연산 알고리즘 상세:**
    - **삽입 (Push):** 먼저 `Top`을 1 증가시킨 후(`Top = Top + 1`), 그 자리에 데이터를 넣음. (넣기 전에 꽉 찼는지 확인 필수)
    - **삭제 (Pop):** 먼저 데이터를 꺼낸 후, `Top`을 1 감소시킴(`Top = Top - 1`). (꺼내기 전에 비어있는지 확인 필수)
- **실전 예제 분석:**
    - **입력 순서:** A, B, C, D
    - **출력 요구:** B, C, D, A 순서로 출력하려면?
    - **과정:**
        1. PUSH A (스택: A)
        2. PUSH B (스택: A, B)
        3. POP B (출력: **B** / 스택: A)
        4. PUSH C (스택: A, C)
        5. POP C (출력: **C** / 스택: A)
        6. PUSH D (스택: A, D)
        7. POP D (출력: **D** / 스택: A)
        8. POP A (출력: **A** / 스택: 비어있음)
    - 결과적으로 **BCDA**가 출력됨

## 076. 큐(Queue)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 리스트의 **한쪽(Rear)**에서는 삽입 작업이, **다른 한쪽(Front)**에서는 삭제 작업이 이루어지도록 구성한 자료 구조
- **[2] 핵심 키워드:** **선입선출(FIFO)**, Front(삭제), Rear(삽입), **운영체제 작업 스케줄링**
- **[3] 구조 / 관점 / 분류:** 자료 구조 - 선형 구조 (순서대로 처리)
- **[4] 시험 포인트:**
    - **작동 원리 (FIFO):** **'가장 먼저 들어온 것이 가장 먼저 나간다(First In First Out)'**는 원칙이 핵심 (스택의 LIFO와 반대)
    - **두 개의 포인터 (구분 필수):**
        - **프런트(F, Front):** 가장 **먼저** 삽입된 자료의 위치를 가리키며, **삭제(Delete)** 작업 시 사용됨
        - **리어(R, Rear):** 가장 **마지막**에 삽입된 자료의 위치를 가리키며, **삽입(Insert)** 작업 시 사용됨
    - **주요 용도 (빈출):** **운영체제(OS)의 작업 스케줄링(Scheduling)**, 인쇄 대기열(Spool) 등 순서가 중요한 작업에 사용됨
- **[5] 한 문장 설명:** 큐는 먼저 들어온 데이터가 먼저 나가는 FIFO 구조로, 삽입은 Rear에서, 삭제는 Front에서 이루어지며 주로 운영체제의 작업 스케줄링에 활용된다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **비유 (Real World):**
    - **스택:** 프링글스 통 (맨 위에 있는 과자부터 먹어야 함).
    - **큐:** 맛집 줄 서기 (먼저 온 사람이 먼저 들어감).
- **동작 상세:**
    - 데이터가 들어오면(Enqueue) `Rear`가 뒤로 한 칸 이동.
    - 데이터가 나가면(Dequeue) `Front`가 뒤로 한 칸 이동하여 따라감.
    - `Front`와 `Rear`가 같은 위치에 있으면 큐가 비어있는(Empty) 상태임.

### 076-1. 데크 (Deque)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 삽입과 삭제가 리스트의 **양쪽 끝(Both Ends)**에서 모두 발생할 수 있는 자료 구조
- **[2] 핵심 키워드:** **Double Ended Queue**, 양쪽 끝 삽입/삭제, **Scroll(입력제한)**, **Shelf(출력제한)**
- **[3] 구조 / 관점 / 분류:** 자료 구조 - 선형 구조 (Stack + Queue의 장점 결합)
- **[4] 시험 포인트:**
    - **정의:** **Stack과 Queue의 장점**만 따서 구성한 것으로, 양쪽 어디서든 넣고 뺄 수 있음
    - **제한된 데크 (빈출 암기):** 양쪽 모두 입출력이 가능하지만, 한쪽을 제한하는 변형 구조 2가지.
        - **Scroll (스크롤):** **입력**이 한쪽에서만 발생하고, 출력은 양쪽에서 가능한 구조 (**입력 제한**)
        - **Shelf (셸프):** **출력**이 한 곳에서만 이루어지고, 입력은 양쪽에서 가능한 구조 (**출력 제한**)
- **[5] 한 문장 설명:** Deque는 Stack과 Queue를 합친 형태로 양쪽 끝에서 삽입/삭제가 가능하며, 입력만 제한한 Scroll과 출력만 제한한 Shelf가 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **명칭의 유래:** **D**ouble **E**nded **Que**ue의 앞글자를 따서 **Deque(데크)**라고 부름.
- **유연성:** 스택처럼 쓸 수도 있고(한쪽 막고 쓰면), 큐처럼 쓸 수도 있고(한쪽 넣고 반대쪽 빼면), 둘 다 섞어 쓸 수도 있는 가장 유연한 선형 자료 구조임.
- **암기 팁:**
    - **Scroll (입력 제한):** 두루마리(Scroll)를 말 때는 한 방향으로만 만다(Input). (펼치는 건 양쪽으로 가능)
    - **Shelf (출력 제한):** 선반(Shelf)에 물건을 양쪽에서 밀어 넣을 순 있지만, 꺼낼 땐 한쪽으로 쏟아진다. (※ 개인적인 암기 연상법 예시)

### 076-2.그래프 (Graph)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 정점(Vertex)과 간선(Edge)의 두 집합으로 이루어진 자료 구조
- **[2] 핵심 키워드:** **정점(V)**, **간선(E)**, 방향/무방향 그래프, **사이클(Cycle)**, 통신망/교통망
- **[3] 구조 / 관점 / 분류:** 자료 구조 - 비선형 구조 (가장 복잡하고 일반적인 형태)
- **[4] 시험 포인트:**
    - **구성 요소:** 그래프 G는 **V(Vertex, 정점)**와 **E(Edge, 간선)**의 집합으로 정의됨
    - **구분:** 간선의 **방향성 유무**에 따라 **방향 그래프(Directed Graph)**와 **무방향 그래프(Undirected Graph)**로 구분됨
    - **응용 분야 (빈출):** **통신망(Network), 교통망, 이항관계**, 연립방정식, 유기화학 구조식 등 복잡한 연결 관계를 표현할 때 사용됨
    - **트리와의 관계:** **'트리(Tree)'**는 그래프의 특수한 형태로, **'사이클(Cycle)이 없는 그래프'**를 말함
- **[5] 한 문장 설명:** 그래프는 정점(V)과 간선(E)으로 구성된 비선형 자료 구조로, 통신망이나 교통망 등에 쓰이며 사이클이 없는 그래프를 트리라고 한다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **이미지 예시 설명:**
    - **G1:** 무방향 그래프 (화살표 없음, 단순히 연결됨).
    - **G2:** 트리 구조 (사이클이 없음, 계층적).
    - **G3:** 방향 그래프 (화살표 있음, 1→2와 2→1은 다름).
- **트리 vs 그래프:** 모든 트리는 그래프이지만, 모든 그래프가 트리는 아님. (트리 ⊂ 그래프). 그래프에서 '순환(Cycle)'을 끊어내고 계층을 만들면 트리가 됨.

## 077. 방향/무방향 그래프의 최대 간선 수

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 정점(Node) 수 n에 따라 그래프가 가질 수 있는 링크(Edge)의 최대 개수.
- * 핵심 키워드**: n(n-1)/2, n(n-1), 정점(n), 간선.
- * 구조 / 관점 / 분류**: 비선형 구조(Non-Linear Structure)인 그래프 이론 기반.
- * 시험 포인트**: 무방향 그래프($n(n-1)/2$)와 방향 그래프($n(n-1)$)의 공식 계산 문제.
- * 한 문장 설명**: 정점이 n개일 때, 무방향 그래프의 최대 간선 수는 n(n-1)/2이고 방향 그래프는 n(n-1)이다.
- * 연관 설명**: 073

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- 정점이 4개인 경우: 무방향 그래프의 최대 간선 수는 $4(4-1)/2 = 6$개임.
- 정점이 4개인 경우: 방향 그래프의 최대 간선 수는 $4(4-1) = 12$개임.
- 무방향 그래프: 간선에 방향이 없어 양방향 통행이 가능한 연결 구조.
- 방향 그래프: 간선에 화살표로 방향이 표시되어 특정 방향으로만 이동 가능한 구조.
- 모든 노드가 서로 연결된 그래프를 완전 그래프(Complete Graph)라고 함.

**077-1. 인접 행렬을 이용한 그래프의 표현 (Graph Representation using Adjacency Matrix)**
**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** 그래프의 정점(Vertex) 간 연결 관계를 $N \times N$ **행렬(Matrix)**로 표현하는 방법
• **[2] 핵심 키워드:** $P_{ij}=1$ (연결), $P_{ij}=0$ (미연결), **방향(Directed)** vs **무방향(Undirected)**, 대칭성
• **[3] 구조 / 관점 / 분류:** 자료 구조 - 그래프 구현 방법
• **[4] 시험 포인트:** **방향 그래프**와 **무방향 그래프**의 행렬 표현 차이를 묻는 문제가 출제됨.
    ◦ **방향 그래프 (Directed Graph):**
        ▪ 행렬의 원소 $P_{ij}$는 정점 $V_i$에서 $V_j$로 가는 **화살표(간선)가 있으면 1**, 없으면 0
        ▪ **특징:** 행(Row)은 **나가는(Out)** 간선, 열(Column)은 **들어오는(In)** 간선을 의미함. (예: 1번 행의 합 = 정점 1의 진출 차수)
    ◦ **무방향 그래프 (Undirected Graph):**
        ▪ $V_i$와 $V_j$가 선으로 **연결(인접)되어 있으면 1**, 없으면 0
        ▪ **특징:** $i$와 $j$가 연결되면 $j$와 $i$도 연결된 것이므로, 대각선을 기준으로 **대칭(Symmetric)** 형태를 띰 ($P_{ij} = P_{ji}$)
• **[5] 한 문장 설명:** 인접 행렬은 정점 간의 연결 여부를 0과 1로 표현하며, 방향 그래프는 화살표 방향대로, 무방향 그래프는 대칭적으로 1을 표시한다.
**TẦNG B – NOTE 보충 (HIỂU SÂU)**
• **이미지 예제 분석 (방향 그래프):**
    ◦ 경로: $1 \rightarrow 2 \rightarrow 3 \rightarrow 4 \rightarrow 5 \rightarrow 3$ (루프)
    ◦ 행렬 값:
        ▪ 1행 2열 = 1 ($1 \rightarrow 2$)
        ▪ 5행 3열 = 1 ($5 \rightarrow 3$)
        ▪ 나머지는 해당 방향이 없으므로 0.
• **이미지 예제 분석 (무방향 그래프):**
    ◦ 정점 4는 1, 2, 3과 모두 연결되어 있음.
    ◦ 따라서 행렬의 4행(Row 4)을 보면 1, 2, 3열이 모두 **1**로 채워져 있음 (`1 1 1 0`)
• **장단점:**
    ◦ **장점:** 두 정점이 연결되어 있는지 확인하기 매우 빠름 (인덱스로 바로 접근).
    ◦ **단점:** 정점(V)의 개수가 많고 간선(E)이 적은 희소 그래프(Sparse Graph)의 경우, 0으로 채워지는 공간이 많아 **메모리 낭비**가 심함.

## 078. 트리의 개요(Tree)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 정점(Node)과 선분(Branch)을 이용하여 **사이클(Cycle)을 이루지 않도록** 구성한 그래프(Graph)의 특수한 형태
- **[2] 핵심 키워드:** **사이클 없음**, 계층 구조(족보/조직도), **근 노드(Root)**, **디그리(Degree)**, 단말 노드(Leaf), 깊이(Depth)
- **[3] 구조 / 관점 / 분류:** 자료 구조 - 비선형 구조 (계층적 관계 표현)
- **[4] 시험 포인트:** 주어진 트리 그림을 보고 각 용어의 **값(숫자)**을 묻는 문제가 출제됨. (아래 예시 기준)
    - **근 노드 (Root Node):** 트리의 가장 위에 있는 노드 (예: **A**)
    - **디그리 (Degree, 차수):** 각 노드가 가지고 있는 **자식 노드(가지)의 수**
        - 예: 노드 A의 디그리 = 3, 노드 B의 디그리 = 2
    - **트리의 디그리 (Degree of Tree):** 트리 내의 노드들 중 **가장 높은(Max)** 디그리 값
        - 예: A와 D가 3개를 가지므로 이 트리의 디그리는 **3**
    - **단말 노드 (Terminal Node / Leaf Node):** 자식이 하나도 없는(디그리가 0인) 노드
        - 예: **K, L, F, G, H, I, J, M**
    - **깊이 (Depth / Height):** 트리의 최대 레벨(Level)
        - 예: Level 1 ~ 4까지 있으므로 깊이는 **4**
- **[5] 한 문장 설명:** 트리는 사이클이 없는 계층적 그래프로, 시험에서는 특정 노드의 차수(Degree), 단말 노드(Leaf) 판별, 트리의 전체 깊이(Depth)를 묻는 문제가 나온다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **용어 상세 정리 (이미지 필기 참조):**
    - **부모 노드 (Parent Node):** 자신과 연결된 상위 노드 (예: B의 부모는 A)
    - **자식 노드 (Child Node):** 자신과 연결된 하위 노드 (예: A의 자식은 B, C, D)
    - **형제 노드 (Sibling):** 같은 부모를 둔 노드들 (예: B, C, D는 형제)
- **실생활 예시:**
    - **가족의 계보(족보):** 할아버지 → 아버지/작은아버지 → 나/사촌 (계층 구조)
    - **조직도:** 사장 → 부장 → 과장 → 대리 (상하 관계)

## 079. 트리의 운행법 (Tree Traversal)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** 트리를 구성하는 각 노드들을 찾아가는 방법으로, 산술식의 표기법(Prefix, Infix, Postfix)과 밀접한 관련이 있음
• **[2] 핵심 키워드:** Preorder(전위), Inorder(중위), Postorder(후위), **Root의 위치**
• **[3] 구조 / 관점 / 분류:** 자료 구조 - 트리 순회 알고리즘
• **[4] 시험 포인트:**
    ◦ **암기 비법:** **'Root(뿌리)'가 언제 방문되는가**가 이름(Pre/In/Post)을 결정함.
    ◦ **1. Preorder (전위 순회):** **Root** $\rightarrow$ Left $\rightarrow$ Right
        ▪ Root(A)가 가장 먼저 나옴.
    ◦ **2. Inorder (중위 순회):** Left $\rightarrow$ **Root** $\rightarrow$ Right
        ▪ Root(A)가 중간에 나옴.
    ◦ **3. Postorder (후위 순회):** Left $\rightarrow$ Right $\rightarrow$ **Root**
        ▪ Root(A)가 가장 나중에 나옴.
• **[5] 한 문장 설명:** 트리의 순회는 Root를 언제 방문하느냐에 따라 Root가 먼저면 Preorder, 중간이면 Inorder, 마지막이면 Postorder로 나뉜다

.
**TẦNG B – NOTE 보충 (HIỂU SÂU & GIẢI ĐỀ)**
• **실전 문제 풀이 (이미지 예제 분석):**
    ◦ **트리 구조:** Root는 A, 왼쪽 서브트리(B,D,E,H,I), 오른쪽 서브트리(C,F,G).
    ◦ **Preorder (A $\rightarrow$ L $\rightarrow$ R):**
        ▪ A 찍고 $\rightarrow$ 왼쪽 덩어리(B가 루트) 처리 $\rightarrow$ 오른쪽 덩어리(C가 루트) 처리
        ▪ 결과: **A B D H I E C F G**
    ◦ **Inorder (L $\rightarrow$ A $\rightarrow$ R):**
        ▪ 왼쪽 맨 끝(H)부터 훑고 올라오면서 처리
        ▪ 결과: **H D I B E A F C G**
    ◦ **Postorder (L $\rightarrow$ R $\rightarrow$ A):**
        ▪ 자식들 다 처리하고 부모 처리 (H, I 처리 후 D, D와 E 처리 후 B...)
        ▪ 결과: **H I D E B F G C A** (Root인 A가 맨 마지막에 옴)
• **팁:** 헷갈릴 때는 이미지처럼 **서브트리 단위로 동그라미**를 쳐놓고, 그 덩어리 안에서 순서를 매긴 뒤 합치는 것이 정확함.

## 080. 수식의 표기법 (Expression Notation)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** 산술식을 계산하기 위해 이진 트리(Binary Tree)를 사용하여 표현하는 방법
• **[2] 핵심 키워드:** **전위(Prefix)**, **중위(Infix)**, **후위(Postfix)**, 연산자(Operator) 위치, **스택(Stack)** 활용
• **[3] 구조 / 관점 / 분류:** 자료 구조 - 수식 표현 및 변환
• **[4] 시험 포인트:** **연산자(Root)가 어디에 오느냐**에 따라 3가지로 구분됨 (트리 순회와 1:1 매칭).
    ◦ **전위 표기법 (Prefix):** **연산자** $\rightarrow$ Left $\rightarrow$ Right (Preorder와 동일)
        ▪ 예: $+AB$
    ◦ **중위 표기법 (Infix):** Left $\rightarrow$ **연산자** $\rightarrow$ Right (Inorder와 동일, 우리가 흔히 쓰는 수식)
        ▪ 예: $A+B$
    ◦ **후위 표기법 (Postfix):** Left $\rightarrow$ Right $\rightarrow$ **연산자** (Postorder와 동일, 컴퓨터/컴파일러가 선호)
        ▪ 예: $AB+$
• **[5] 한 문장 설명:** 수식 표기법은 연산자가 피연산자(Operand)의 앞에 오면 Prefix, 중간이면 Infix, 뒤에 오면 Postfix이며, 컴퓨터는 주로 스택을 이용해 Postfix나 Prefix로 변환하여 처리한다.
**TẦNG B – NOTE 보충 (계산 문제 풀이법)**
시험에서는 **"다음 Infix 수식을 Postfix로 변환하시오"** 같은 문제가 나옵니다. 이미지의 예제를 따라 풀어보겠습니다.
**1. Infix $\rightarrow$ Prefix / Postfix 변환 (괄호법)**
• **예제:** $X = A / B * (C + D) + E$
• **방법:** 연산 우선순위에 따라 괄호로 묶은 뒤, 연산자를 괄호의 **앞(Prefix)**이나 **뒤(Postfix)**로 뺍니다.
• **Postfix 변환 과정 (연산자를 뒤로):**
    1. $(A/B)$ $\rightarrow$ $AB/$
    2. $(C+D)$ $\rightarrow$ $CD+$
    3. $(AB/ * CD+)$ $\rightarrow$ $AB/CD+*$
    4. $(... + E)$ $\rightarrow$ $AB/CD+*E+$
    5. $(X = ...)$ $\rightarrow$ **$XAB/CD+*E+=$**
• **Prefix 변환 과정 (연산자를 앞으로):**
    1. $(A/B)$ $\rightarrow$ $/AB$
    2. $(C+D)$ $\rightarrow$ $+CD$
    3. $(/AB * +CD)$ $\rightarrow$ $*/AB+CD$
    4. $(... + E)$ $\rightarrow$ $+*/AB+CDE$
    5. $(X = ...)$ $\rightarrow$ **$=X+*/AB+CDE$**
**2. Postfix / Prefix $\rightarrow$ Infix 변환 (복원)**
• **Postfix $\rightarrow$ Infix (예: $ABC-/DEF+*+$):**
    ◦ 앞에서부터 읽다가 **'연산자'**가 나오면 바로 앞의 두 피연산자 사이에 끼워 넣음.
    ◦ $BC-$ $\rightarrow$ $(B-C)$
    ◦ $EF+$ $\rightarrow$ $(E+F)$
    ◦ $D(E+F)*$ $\rightarrow$ $D*(E+F)$
    ◦ $A(B-C)/$ $\rightarrow$ $A/(B-C)$
    ◦ 최종: *$A/(B-C) + D(E+F)$**
• **Prefix $\rightarrow$ Infix (예: $+/A-BC*D+EF$):**
    ◦ 뒤에서부터 읽거나, 연산자 뒤에 **'두 개의 피연산자'**가 뭉쳐있는 곳을 찾아 끼워 넣음.
    ◦ $-BC$ $\rightarrow$ $(B-C)$
    ◦ $+EF$ $\rightarrow$ $(E+F)$
    ◦ $*D(E+F)$ $\rightarrow$ $D*(E+F)$
    ◦ $/A(B-C)$ $\rightarrow$ $A/(B-C)$
    ◦ 최종: *$A/(B-C) + D(E+F)$**

## 081. 삽입 정렬 (Insertion Sort)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** 가장 간단한 정렬 방식 중 하나로, **이미 순서화된 파일(앞부분)**에 새로운 하나의 레코드를 **순서에 맞게 삽입(Insert)**시켜 정렬하는 방식
• **[2] 핵심 키워드:** **이미 순서화된 파일**, **알맞은 위치에 삽입**, 2번째부터 시작, **O($n^2$)**
• **[3] 구조 / 관점 / 분류:** 알고리즘 - 내부 정렬 (단순하지만 효율적일 수 있음)
• **[4] 시험 포인트:**
    ◦ **동작 설명 (빈출 정의):** "두 번째 키와 첫 번째 키를 비교... n번째 키를 앞의 **n-1개의 키와 비교**하여 알맞은 순서에 삽입한다"는 문구가 나오면 무조건 삽입 정렬임
    ◦ **시간 복잡도:** 평균과 최악 모두 **O($n^2$)**임
    ◦ **회전수 계산:** 데이터가 $N$개일 때, 총 **$N-1$ 회전(Pass)**을 수행함
        ▪ 예: 5개 데이터 $\rightarrow$ 4회전 수행.

**TẦNG B – NOTE 보충 (HIỂU SÂU & GIẢI ĐỀ)**
• **실전 풀이 (이미지 예제: 8, 5, 6, 2, 4)**
    ◦ **초기 상태:** `8 | 5 6 2 4` (맨 앞 8은 정렬된 상태로 가정하고 시작)
    ◦ **1회전 (2번째 데이터 '5' 처리):**
        ▪ 5를 앞의 8과 비교 $\rightarrow$ 5가 작으니 앞으로 이동.
        ▪ 결과: **5 8** `6 2 4`
    ◦ **2회전 (3번째 데이터 '6' 처리):**
        ▪ 6을 앞의 (5, 8)과 비교 $\rightarrow$ 5보다 크고 8보다 작으니 그 사이로 쏙(Insert).
        ▪ 결과: **5 6 8** `2 4`
    ◦ **3회전 (4번째 데이터 '2' 처리):**
        ▪ 2를 앞의 (5, 6, 8)과 비교 $\rightarrow$ 제일 작으니 맨 앞으로 삽입.
        ▪ 결과: **2 5 6 8** `4`
    ◦ **4회전 (5번째 데이터 '4' 처리):**
        ▪ 4를 앞의 (2, 5, 6, 8)과 비교 $\rightarrow$ 2보다는 크고 5보다는 작으니 그 사이로 삽입.
        ▪ 최종 결과: **2 4 5 6 8**
• **비유:** 카드 게임을 할 때, 새로운 카드를 한 장씩 가져와서 이미 손에 들고 있는 정렬된 카드들 사이 적절한 위치에 꽂아 넣는 것과 같음.

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

• **[2] 핵심 키워드:** **매개변수(h)**, **서브파일(Subfile)**, **Insertion 정렬 확장**, $O(n^{1.5})$

    ◦ **동작 원리:**

    ◦ **특징:** 입력 파일이 **'부분적으로 정렬'**되어 있는 경우에 매우 유리한 방식임
    ◦ **시간 복잡도:**
        ▪ 평균: **$O(n^{1.5})$**
        ▪ 최악: **$O(n^2)$**
• **[5] 한 문장 설명:** 셸 정렬은 삽입 정렬을 확장한 것으로, 간격(h)을 두어 서브파일을 만든 뒤 각각 삽입 정렬을 수행하여 멀리 있는 요소들을 빠르게 이동시키는 방식이다.
**TẦNG B – NOTE 보충 (HIỂU SÂU)**
• **왜 만들었나? (삽입 정렬의 단점 극복):**
    ◦ 일반적인 삽입 정렬은 바로 옆자리와만 비교하므로, 만약 제일 작은 숫자가 맨 뒤에 있다면 맨 앞까지 오기 위해 수많은 이동(Shift)이 필요함.
    ◦ **Shell Sort**는 처음에 듬성듬성(간격 h) 비교해서 작은 숫자를 앞으로 '성큼성큼' 보냄.
    ◦ 마지막에 간격이 1이 되면 일반 삽입 정렬과 똑같아지지만, 이미 데이터가 거의 다 정렬된 상태(Best Case에 근접)이므로 매우 빠르게 끝남.
• **이미지 예시 분석:**
    ◦ `8, 5, 6, 2, 4, 1` 배열에서 간격을 두고 묶음.
    ◦ 예: 8과 2, 5와 4, 6과 1 등을 비교해서 큰 흐름을 먼저 잡음

## 082. 선택 정렬 (Selection Sort)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** $n$개의 레코드 중에서 **최소값(Minimum)**을 찾아 **첫 번째** 레코드 위치에 놓고, 나머지 $(n-1)$개 중에서 다시 최소값을 찾아 **두 번째** 위치에 놓는 방식을 반복하여 정렬하는 알고리즘
• **[2] 핵심 키워드:** **최소값(Min Value)**, 위치 교환(Swap), **O($n^2$)**
• **[3] 구조 / 관점 / 분류:** 알고리즘 - 내부 정렬 (가장 이해하기 쉬운 방식)
• **[4] 시험 포인트:**
    ◦ **동작 원리 (키워드):** 문제 지문에서 **"최소값을 찾아..."** 라는 말이 나오면 무조건 선택 정렬임
    ◦ **시간 복잡도:** 평균과 최악 모두 **O($n^2$)**임
• **[5] 한 문장 설명:** 선택 정렬은 전체 데이터 중 가장 작은 값을 '선택'하여 맨 앞의 데이터와 자리를 바꾸는 과정을 반복하는 방식이다.
**TẦNG B – NOTE 보충 (HIỂU SÂU & GIẢI ĐỀ)**
• **실전 풀이 (이미지 예제: 8, 5, 6, 2, 4)**
    ◦ **1회전 (가장 작은 수 '2' 찾기):**
        ▪ 전체(`8 5 6 2 4`) 중 최소값은 **2**.
        ▪ 맨 앞의 **8**과 **2**의 자리를 바꿈 (Swap).
        ▪ 결과: **2** `5 6 8 4` (2는 자리 확정)
    ◦ **2회전 (남은 것 중 가장 작은 수 '4' 찾기):**
        ▪ 남은(`5 6 8 4`) 중 최소값은 **4**.
        ▪ 맨 앞(두 번째 자리)의 **5**와 **4**의 자리를 바꿈.
        ▪ 결과: **2 4** `6 8 5` (2, 4 확정)
    ◦ **3회전 (남은 것 중 가장 작은 수 '5' 찾기):**
        ▪ 남은(`6 8 5`) 중 최소값은 **5**.
        ▪ 맨 앞(세 번째 자리)의 **6**과 **5**의 자리를 바꿈.
        ▪ 결과: **2 4 5** `8 6` (2, 4, 5 확정)
    ◦ **4회전 (남은 것 중 가장 작은 수 '6' 찾기):**
        ▪ 남은(`8 6`) 중 최소값은 **6**.
        ▪ 맨 앞(네 번째 자리)의 **8**과 **6**의 자리를 바꿈.
        ▪ 최종 결과: **2 4 5 6 8**

## 083. 버블 정렬 (Bubble Sort)

### 

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** 주어진 파일에서 **인접한 두 개의 레코드** 키 값을 비교하여, 그 크기에 따라 레코드의 **위치를 서로 교환(Swap)**하는 정렬 방식
• **[2] 핵심 키워드:** **인접한 두 개 비교**, 거품(Bubble), **플래그 비트(Flag Bit)**, **O($n^2$)**
• **[3] 구조 / 관점 / 분류:** 알고리즘 - 내부 정렬 (교환 방식)
• **[4] 시험 포인트:**
    ◦ **동작 원리:** 인접한 두 수를 비교해서 큰 값을 뒤로(오름차순 기준) 계속 보냄. 마치 물속의 거품이 수면 위로 올라가는 것과 비슷함.
    ◦ **종료 조건:** 더 이상 교환이 일어나지 않으면 정렬이 끝난 것으로 간주하며, 이를 판단하기 위해 **'플래그 비트(Flag Bit)'**를 사용할 수 있음
    ◦ **시간 복잡도:** 평균과 최악 모두 **O($n^2$)**임
• **[5] 한 문장 설명:** 버블 정렬은 인접한 두 데이터를 비교하여 정렬하는 방식으로, 매 회전마다 가장 큰 값이 맨 뒤로 이동하며 평균 수행 시간은 $O(n^2)$이다.

**TẦNG B – NOTE 보충 (HIỂU SÂU & GIẢI ĐỀ)**
• **실전 풀이 (이미지 예제: 8, 5, 6, 2, 4)**
    ◦ **1회전 (가장 큰 수 '8'을 맨 뒤로 보내기):**
        ▪ (8, 5) 비교 $\rightarrow$ 교환 (`5 8 6 2 4`)
        ▪ (8, 6) 비교 $\rightarrow$ 교환 (`5 6 8 2 4`)
        ▪ (8, 2) 비교 $\rightarrow$ 교환 (`5 6 2 8 4`)
        ▪ (8, 4) 비교 $\rightarrow$ 교환 (`5 6 2 4` **`8`**) $\rightarrow$ **8 고정**
    ◦ **2회전 (남은 것 중 가장 큰 수 '6'을 뒤로):**
        ▪ (5, 6) 비교 $\rightarrow$ 그대로
        ▪ (6, 2) 비교 $\rightarrow$ 교환 (`5 2 6 4 8`)
        ▪ (6, 4) 비교 $\rightarrow$ 교환 (`5 2 4` **`6 8`**) $\rightarrow$ **6 고정**
    ◦ **3회전 (남은 것 중 가장 큰 수 '5'를 뒤로):**
        ▪ (5, 2) 비교 $\rightarrow$ 교환 (`2 5 4 6 8`)
        ▪ (5, 4) 비교 $\rightarrow$ 교환 (`2 4` **`5 6 8`**) $\rightarrow$ **5 고정**
    ◦ **4회전:** (2, 4) 비교 $\rightarrow$ 그대로 (`2 4 5 6 8`) $\rightarrow$ **정렬 완료**

## 084. 퀵 정렬 (Quick Sort)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** 레코드의 많은 자료 이동을 없애고, 하나의 파일을 **부분적으로 나누어(Divide)** 가면서 정렬하는 방법
• **[2] 핵심 키워드:** **피벗(Pivot)**, **분할과 정복(Divide and Conquer)**, **스택(Stack)**, **가장 빠른 방식**, **$O(n\log_2n)$**
• **[3] 구조 / 관점 / 분류:** 알고리즘 - 내부 정렬 (고급 정렬)
• **[4] 시험 포인트:**
    ◦ **동작 원리 (핵심):** **'피벗(Pivot)'**이라 불리는 기준값을 중심으로 **작은 값은 왼쪽** 서브파일로, **큰 값은 오른쪽** 서브파일로 분해시킴
    ◦ **필요 자료구조:** 프로그램에서 **'되부름(Recursion, 재귀)'**을 이용하기 때문에 **'스택(Stack)'**이 필요함
    ◦ **특징:** 정렬 방식 중에서 **'가장 빠른 방식'**으로 알려져 있음
    ◦ **시간 복잡도 (빈출):**
        ▪ **평균:** **$O(n\log_2n)$**
        ▪ **최악:** **$O(n^2)$** (이미 정렬되어 있거나 역순일 때 피벗을 잘못 잡으면 느려짐)
• **[5] 한 문장 설명:** 퀵 정렬은 피벗(Pivot)을 기준으로 작은 값과 큰 값을 분할(Divide)하고 정복(Conquer)하는 방식이며, 재귀 호출을 위해 스택을 사용하고 평균적으로 가장 빠른 속도를 자랑한다.
**TẦNG B – NOTE 보충 (HIỂU SÂU)**
• **분할과 정복 (Divide and Conquer):**
    ◦ **Divide:** 피벗을 기준으로 "너는 작으니까 왼쪽 방, 너는 크니까 오른쪽 방"으로 나눔.
    ◦ **Conquer:** 나눠진 방 안에서 또 다시 대장을 뽑아(피벗) 쪼개기를 반복함.
    ◦ 더 이상 쪼갤 수 없을 때까지 반복하면 전체가 정렬됨.
• **왜 빠른가?:** 먼 거리에 있는 데이터를 교환할 때 한 번에 휙휙 넘길 수 있어서(Skip), 바로 옆이랑만 비교하는 버블 정렬보다 훨씬 효율적임.
• **스택의 필요성:** "왼쪽 방 정리해!"라고 시키고 나서(함수 호출), 그게 끝나면 다시 돌아와서 "오른쪽 방 정리해!"라고 해야 하므로, 돌아올 위치를 기억하기 위해 스택(Stack) 영역을 사용함.

## 086. 2-Way 합병 정렬 (Merge Sort)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

### **086-1 . 기수 정렬 (Radix Sort) = Bucket Sort**

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** 데이터를 비교하는 대신, **큐(Queue)**를 이용하여 데이터의 **자릿수(Digit)**별로 나누어 담았다가 꺼내며 정렬하는 방식
• **[2] 핵심 키워드:** **Queue(큐)**, **자릿수(Digit)**, 버킷(Bucket), **$O(dn)$**
• **[3] 구조 / 관점 / 분류:** 알고리즘 - 내부 정렬 (비교하지 않는 정렬 방식)
• **[4] 시험 포인트:**
    ◦ **사용 자료구조:** 정렬을 위해 **'Queue'**를 사용한다는 점이 가장 큰 특징임
    ◦ **동작 원리:** 레코드의 키 값을 분석하여 같은 수(혹은 문자)끼리 **'버킷'**에 분배하였다가 순서대로 꺼냄
    ◦ **시간 복잡도 (매우 빠름):** 평균과 최악 모두 **$O(dn)$**임 (단, $d$는 자릿수, $n$은 데이터 개수)
        ▪ 비교 정렬의 한계인 $O(n\log n)$보다 빠를 수 있음.
• **[5] 한 문장 설명:** 기수 정렬은 큐(Queue)를 이용하여 각 자릿수(Digit) 별로 버킷에 담아 정렬하며, 시간 복잡도는 $O(dn)$이다.
**TẦNG B – NOTE 보충 (HIỂU SÂU)**
• **왜 Bucket인가?:** 0번부터 9번까지 번호가 매겨진 10개의 양동이(Bucket/Queue)를 준비해두고, 숫자의 '일의 자리'를 보고 해당 번호 양동이에 툭툭 던져 넣기 때문.
• **동작 과정 (이미지 예시: 11, 25, 39, 19, 36, 21, 15):**
    1. **일의 자리 기준:**
        ▪ 1통: 1**1**, 2**1**
        ▪ 5통: 2**5**, 1**5**
        ▪ 6통: 3**6**
        ▪ 9통: 3**9**, 1**9**
    2. 순서대로 꺼내면: 11, 21, 25, 15, 36, 39, 19 (일의 자리는 정렬됨)
    3. **십의 자리 기준:** 위 결과를 다시 십의 자리에 맞춰 버킷에 넣음.
    4. 순서대로 꺼내면: **11, 15, 19, 21, 25, 36, 39** (최종 정렬 완료)

## 087. 이분 검색 (Binary Search)

**이분 검색 (Binary Search) = 이진 검색**
**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** 전체 파일을 두 개의 서브파일로 **분리(Divide)**해 가면서 키(Key) 레코드를 검색하는 방식
• **[2] 핵심 키워드:** **반드시 순서화(Sorted)**, **중간 레코드(Middle)**, 검색 효율 높음, **$(F+L)/2$**
• **[3] 구조 / 관점 / 분류:** 알고리즘 - 검색 (효율적인 검색)
• **[4] 시험 포인트:**
    ◦ **필수 전제조건 (가장 중요):** 이분 검색을 하려면 파일이 **'반드시 순서화(정렬, Ordered)'** 되어 있어야 함. 정렬되지 않은 파일에는 사용할 수 없음
    ◦ **동작 원리:** 찾고자 하는 Key 값을 파일의 **'중간 레코드(Middle Record)'** Key 값과 비교하면서 진행함
    ◦ **효율성:** 비교 횟수를 거듭할 때마다 검색 대상 데이터 수가 **절반(1/2)**으로 줄어들기 때문에 탐색 효율이 좋고 시간이 적게 소요됨 ($O(\log_2n)$)
    ◦ **중간값 계산 공식:** $M = \frac{F + L}{2}$ (단, $F$: 첫 번째 인덱스, $L$: 마지막 인덱스, 소수점은 버림)
• **[5] 한 문장 설명:** 이분 검색은 반드시 정렬된 파일에서 중간값(M)과 비교하여 검색 범위를 절반씩 줄여나가는 고효율 검색 방식이다.
**TẦNG B – NOTE 보충 (HIỂU SÂU)**
• **비유 (Up & Down 게임):**
    ◦ 술자리 게임에서 "소주 뚜껑 숫자 맞추기(1~50)"를 할 때, 다짜고짜 "1? 2? 3?"(순차 검색) 하지 않음.
    ◦ 보통 "25!"(중간)라고 외치고, "Up"이라고 하면 26~50 사이의 중간인 "38!"을 외침. 이게 바로 이분 검색임.
• **성능 비교:**
    ◦ 데이터가 1,000개일 때:
        ▪ **순차 검색(Linear Search):** 재수 없으면 1,000번 다 뒤져야 함.
        ▪ **이분 검색(Binary Search):** 약 10번($2^{10}=1024$)만 비교하면 무조건 찾음.

## 088. 해싱 함수 (Hashing Function)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- **[1] 개념:** **해시 함수(Hash Function)**를 이용하여 레코드 키에 대한 **해시 테이블(Hash Table)** 내의 **홈 주소(Home Address)**를 계산하여 데이터를 직접 저장하거나 검색하는 방식**[2] 핵심 키워드:** **Hash Table**, **Bucket/Slot**, **Collision(충돌)**, **Overflow**, **제산법(Division)[3] 구조 / 관점 / 분류:** 알고리즘 - 검색 (직접 접근 파일 구조)**[4] 시험 포인트:**
• **구조 용어 (구분 필수):**
    ◦ **버킷 (Bucket):** 하나의 주소를 갖는 구역.
    ◦ **슬롯 (Slot):** 한 개의 레코드를 저장할 수 있는 공간. **n개의 슬롯이 모여 하나의 버킷**을 형성함.
• **현상 용어 (빈출):**
    ◦ **충돌 (Collision):** 서로 다른 두 개 이상의 레코드가 **같은 주소**를 갖는 현상.
    ◦ **Synonym:** 충돌을 일으킨(같은 주소를 갖는) 레코드들의 집합.
    ◦ **오버플로 (Overflow):** 버킷 내에 빈 슬롯이 없어서 더 이상 저장할 수 없는 상태.
• **해시 함수 종류:**
    ◦ **제산법 (Division):** 키 값을 **소수(Prime Number, Q)**로 나눈 **나머지(Mod)**를 주소로 사용함 ($h(K) = K \pmod Q$).
    ◦ **제곱법, 폴딩법, 기수 변환법** 등이 있음.**[5] 한 문장 설명:** 해싱은 해시 함수를 통해 키를 주소로 변환하여 해시 테이블(버킷/슬롯)에 저장하는 방식으로, 충돌(Collision)과 오버플로(Overflow) 처리가 중요하며 주로 제산법(나머지 연산)을 사용한다.

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- 해싱(Hashing)은 **해시 테이블(Hash Table)**이라는 기억공간을 할당하고,

**해시 함수(Hash Function)**를 이용하여 **레코드 키**에 대한

해시 테이블 내의 **홈 주소(Home Address)**를 계산한 후

주어진 레코드를 해당 기억장소에 **저장하거나 검색 작업**을 수행하는 방식.

- 대수적 코딩법 (Algebraic Coding): 키 값을 이루고 있는 각 자리의 **비트 수를 한 다항식의 계수로 간주**하고,이 다항식을 해시표의 크기에 의해 정의된 다항식으로 나누어 얻은 **나머지 다항식의 계수**를 홈 주소로 삼는 방식.

---

- 숫자 분석법 (Digit Analysis, 계수 분석법) 키 값을 이루는 **숫자의 분포를 분석**하여 비교적 고른 자리를 **필요한 만큼 택해서 홈 주소**로 삼는 방식.

### 무작위법 (Random) : *난수(Random Number)**를 발생시켜 나온 값을 홈 주소로 삼는 방식.

## 해싱 – 해시 테이블(Hash Table)

레코드를 **한 개 이상 보관할 수 있는 버킷들로 구성된 기억공간**으로 **보조기억장치**에 구성할 수도 있고 **주기억장치**에 구성할 수도 있음.

---

### 용어 정리

**버킷(Bucket) ,** 하나의 주소를 갖는 파일의 한 구역을 의미함, 버킷의 크기는 같은 주소에 포함될 수 있는 레코드 수를 의미함.

**슬롯(Slot):** 한 개의 레코드를 저장할 수 있는 공간으로 n개의 슬롯이 모여 하나의 버킷을 형성함.

**Collision (충돌 현상):** 서로 다른 두 개 이상의 레코드가 같은 주소를 갖는 현상.

**Synonym:** 충돌로 인해 같은 Home Address를 갖는 레코드들의 집합.

**Overflow:** 계산된 Home Address의 Bucket 내에 저장할 기억공간이 없는 상태로, Bucket을 구성하는 Slot이 여러 개일, Collision은 발생해도 Overflow는 발생하지 않을 수 있음.

### 091-1.절차형 SQL (Procedural SQL)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** C나 JAVA 등의 프로그래밍 언어와 같이 **연속적인 실행**이나 **분기, 반복** 등의 제어가 가능한 SQL
- **[2] 핵심 키워드:** **BEGIN ~ END 블록**, **프로시저(Procedure)**, **트리거(Trigger)**, **사용자 정의 함수(Function)**
- **[3] 구조 / 관점 / 분류:** 데이터베이스 - SQL 활용
- **[4] 시험 포인트:** 절차형 SQL의 **3가지 종류**와 각각의 정의를 묻는 문제가 출제됨.
    - **프로시저 (Procedure):** 일종의 **트랜잭션 언어**로, 미리 저장해 놓은 SQL 작업을 **호출(Call)**을 통해 실행함
    - **트리거 (Trigger):** 데이터의 입력(Insert), 갱신(Update), 삭제(Delete) 등의 **이벤트(Event)**가 발생할 때마다 관련 작업이 **자동으로(Automatically)** 수행됨
    - **사용자 정의 함수 (User-Defined Function):** 프로시저와 유사하지만, 종료 시 **예약어 Return**을 사용하여 처리 결과를 **단일값으로 반환**한다는 차이점이 있음
- **[5] 한 문장 설명:** 절차형 SQL은 BEGIN~END 블록 구조를 가지며 C언어처럼 분기/반복이 가능한 SQL로, 종류에는 호출해서 쓰는 프로시저, 자동 실행되는 트리거, 값을 반환하는 사용자 정의 함수가 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **왜 쓰는가?:** 일반적인 SQL(SELECT, INSERT...) 한 줄로는 복잡한 비즈니스 로직(예: "재고가 10개 미만이면 주문을 넣고, 아니면 보류해라")을 처리하기 어렵기 때문.
- **효율성:** DBMS 엔진 내부에서 직접 실행되므로, 애플리케이션과 DB 사이의 데이터 전송량(패킷)을 줄일 수 있음.
- **비유:**
    - **Procedure:** "청소해!" 라고 시키면 청소만 하고 끝나는 함수 (Void).
    - **Function:** "지금 몇 시야?" 라고 물으면 시간을 알려주는 함수 (Return Value).
    - **Trigger:** "도둑이 들면(Event) -> 경보를 울려라(Action)" (자동 감지 시스템).
- ví dụ
    
    # 1️⃣ 프로시저 (Procedure) – *phải gọi thì mới chạy*
    
    ### 📌 Mục đích
    
    - Xử lý **một chuỗi nghiệp vụ**
    - Có thể có nhiều bước
    - **KHÔNG return giá trị trực tiếp**
    
    ---
    
    ### 🔧 Ví dụ: Chuyển tiền giữa 2 tài khoản
    
    ```sql
    CREATEPROCEDURE transfer_money (
        p_from_idIN NUMBER,
        p_to_idIN NUMBER,
        p_amountIN NUMBER
    )
    BEGIN
    -- Trừ tiền người gửi
    UPDATE account
    SET balance= balance- p_amount
    WHERE account_id= p_from_id;
    
    -- Cộng tiền người nhận
    UPDATE account
    SET balance= balance+ p_amount
    WHERE account_id= p_to_id;
    
    COMMIT;
    END;
    
    ```
    
    ### ▶️ Cách chạy
    
    ```sql
    CALL transfer_money(1001,1002,500);
    
    ```
    
    📌 **Điểm mấu chốt để nhớ**
    
    - Gọi bằng `CALL`
    - Không dùng trong `SELECT`
    - Dùng cho **xử lý nghiệp vụ**
    
    ---
    
    # 2️⃣ 트리거 (Trigger) – *tự động chạy khi có sự kiện*
    
    ### 📌 Mục đích
    
    - Tự động phản ứng khi:
        - INSERT
        - UPDATE
        - DELETE
    - **KHÔNG gọi bằng tay**
    
    ---
    
    ### 🔧 Ví dụ: Khi thêm đơn hàng → tự động ghi log
    
    ```sql
    CREATETRIGGER trg_order_log
    AFTERINSERTON orders
    FOREACHROW
    BEGIN
    INSERT INTO order_log(order_id, log_date)
    VALUES (:NEW.order_id, SYSDATE);
    END;
    
    ```
    
    ### ▶️ Khi nào trigger chạy?
    
    ```sql
    INSERT INTO ordersVALUES (101,'A001',300);
    
    ```
    
    ➡️ Trigger **tự chạy**, bạn không cần gọi
    
    📌 **Điểm mấu chốt để nhớ**
    
    - Gắn với **event**
    - Tự động
    - Hay dùng cho **log, audit, kiểm soát dữ liệu**
    
    ---
    
    # 3️⃣ 사용자 정의 함수 (User Defined Function) – *bắt buộc RETURN 1 giá trị*
    
    ### 📌 Mục đích
    
    - Tính toán
    - Chuyển đổi
    - Dùng **bên trong SQL**
    
    ---
    
    ### 🔧 Ví dụ: Tính thuế VAT 10%
    
    ```sql
    CREATEFUNCTION calc_tax (
        p_priceIN NUMBER
    )
    RETURN NUMBER
    IS
    BEGIN
    RETURN p_price*0.1;
    END;
    
    ```
    
    ### ▶️ Cách dùng
    
    ```sql
    SELECT product_name,
           price,
           calc_tax(price)AS tax
    FROM product;
    
    ```

### 092-1.쿼리 성능 최적화 (Query Performance Optimization)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 데이터 입·출력 애플리케이션의 성능 향상을 위해 **SQL 코드를 최적화**하는 작업
- **[2] 핵심 키워드:** **APM(성능 측정 도구)**, **옵티마이저(Optimizer)**, **실행 계획(Execution Plan)**, **인덱스(Index)**
- **[3] 구조 / 관점 / 분류:** 데이터베이스 - 성능 관리 및 튜닝
- **[4] 시험 포인트:** 최적화 수행 **절차(순서)**가 문제로 출제됩니다.
    1. **대상 선정:** 성능 측정 도구인 **APM** 등을 사용하여 최적화 할(느린) 쿼리를 선정함
    2. **계획 검토:** **옵티마이저(Optimizer)**가 수립한 **실행 계획(Execution Plan)**을 분석함
    3. **재구성 (튜닝):** 분석 결과를 바탕으로 **SQL 코드**를 수정하거나 **인덱스(Index)**를 재구성함
- **[5] 한 문장 설명:** 쿼리 성능 최적화는 APM으로 대상 쿼리를 찾고, 옵티마이저의 실행 계획을 검토한 뒤 SQL과 인덱스를 수정하여 성능을 높이는 과정이다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **왜 하는가?:** SQL 문장 하나 잘못 짜면 데이터베이스 전체가 느려질 수 있음(병목 현상).

    - **실행 계획 (Execution Plan):** 옵티마이저가 짠 경로 지도. 개발자는 이 지도를 보고 "아, 여기서 비효율적으로 도네?" 하고 파악해서 고침.

### 093-1.단위 기능 명세서 작성 (Writing Unit Function Specifications)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 설계 과정에서 작성하는 **기능 및 코드 명세서**나 **설계 지침**과 같이 단위 기능을 명세화한 문서들을 의미함
- **[2] 핵심 키워드:** **추상화(Abstraction)**, **구조화(Structuring)**, **정보 은닉(Information Hiding)**
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 구현 및 설계
- **[4] 시험 포인트:** 단위 기능 명세서 작성 시 고려해야 할 **3가지 핵심 원칙**이 출제됨.
    - **추상화 (Abstraction):** 복잡한 시스템을 **단순하게 구현**하기 위한 작업
    - **구조화 (Structuring):** 대형 시스템을 분해하여 단위 기능별로 구분하고, 각 기능들을 **계층적으로 구성**하는 과정
    - **정보 은닉 (Information Hiding):** 모듈을 **독립적으로 운용**할 수 있게 하고, 한 모듈 내의 정보가 **다른 모듈에 영향을 주지 않도록** 하는 원리
- **[5] 한 문장 설명:** 단위 기능 명세서는 복잡한 시스템을 단순화(추상화)하고 계층적으로 분해(구조화)하며, 모듈 간 간섭을 최소화(정보 은닉)하여 작성해야 한다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **왜 필요한가?:** 개발자가 코딩하기 전에 "이 함수는 정확히 무슨 일을 하고, 어떤 입력과 출력을 가지는지"를 명확히 정의해두어야 나중에 혼란이 없음.
- **원칙 상세:**
    - **추상화:** "자동차를 운전한다" (O) vs "엔진에 연료를 주입하고 피스톤을 움직여 바퀴를 굴린다" (X). 복잡한 내부 로직은 숨기고 핵심 기능만 정의함.
    - **정보 은닉:** 내 월급 명세서를 옆 동료가 볼 수 없게 숨겨야(Private), 서로 싸움이 안 나는 것과 같음. 모듈 내부 변수가 밖으로 새어나가면 버그의 원인이 됨.
    - 단위 기능 명세서 작성 → 입-출력기증 구현 → 알고리즘 구현

## 094. IPC (Inter-Process Communication)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 모듈 간 통신 또는 복수의 프로세스 간 통신을 구현하기 위한 인터페이스
- 
- 집합.
- * 핵심 키워드**: Shared Memory, Socket, Semaphores, Pipes, Message Queueing.
- * 구조 / 관점 / 분류**: 프로세스 간 데이터 공유 및 메시지 교환 방식.
- * 시험 포인트**: IPC의 대표적인 5가지 통신 메소드 종류 암기.
- * 한 문장 설명**: IPC는 실행 중인 여러 프로세스가 상호작용하고 데이터를 공유하게 한다.
- * 연관 설명**: 072, 297

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- Shared Memory: 다수 프로세스가 동일한 메모리 영역을 공유하여 가장 빠른 통신 가능.
- Socket: 네트워크를 통해 서로 다른 시스템 간의 프로세스 통신을 지원.
- Semaphores: 공유 자원에 대한 접근 제어(Locking 메커니즘)를 통해 동기화 수행.
- Pipes: FIFO(선입선출) 방식의 메모리를 공유하며, 한 번에 한 프로세스만 접근 가능.
- Message Queueing: 메시지 단위로 데이터를 전달하는 비동기 통신 방식.

**094-1. 알고리즘 구현** 
**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** 입·출력 구현 이후, 실제로 모듈별 기능을 수행하는 로직(알고리즘)을 구현하는 단계
• **[2] 핵심 키워드:** **디바이스 드라이버**, **네트워크**, **파일**, **메모리**, **프로세스 모듈**
• **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 구현 (모듈 유형별)
• **[4] 시험 포인트:** 각 모듈(Module)의 **정의와 역할**을 묻는 문제가 출제됨.
    ◦ **디바이스 드라이버 모듈:** 하드웨어 **주변 장치**의 동작을 구현
    ◦ **네트워크 모듈:** 네트워크 장비 및 **데이터 통신** 기능을 구현
    ◦ **파일 모듈:** 컴퓨터 내부의 **데이터 구조 영역**에 접근하는 방법을 구현
    ◦ **메모리 모듈:** 파일을 프로세스의 **가상 메모리에 매핑/해제**하거나 프로세스 간 **통신(IPC)** 기능을 구현
    ◦ **프로세스 모듈:** 하나의 프로세스 안에서 **다른 프로세스를 생성**하는 방법을 구현
• **[5] 한 문장 설명:** 알고리즘 구현 단계에서는 하드웨어 제어(드라이버), 통신(네트워크), 데이터 접근(파일), 메모리 관리(메모리), 프로세스 생성(프로세스) 등 기능별로 모듈을 구현한다.
**TẦNG B – NOTE 보충 (HIỂU SÂU)**
• **구현 순서:** 단위 기능 명세서 작성 $\rightarrow$ 입·출력 기능 구현 $\rightarrow$ 알고리즘 구현
• **모듈별 비유:**
    ◦ **Device Driver:** "프린터야 인쇄해!"라고 명령 내리는 통역사.
    ◦ **Memory Module:** 책상(RAM)을 정리하고, 옆 사람과 쪽지(IPC)를 주고받게 해주는 관리자.
    ◦ **Process Module:** "새 창 띄워!"라고 명령했을 때(Chrome 탭 추가) 새 작업 공간을 만들어주는 역할.

- ví dụ
    
    ### 단위 기능: “파일에서 데이터 읽기”
    
    - Spec:
        - Input: file path
        - Output: data
    - I/O:
        - Nhận path
        - Trả data
    - **Algorithm 구현**:
    
    ```
    open file
    read data
    close file
    return data
    
    ```
    
    👉 Phần pseudo-code này chính là **알고리즘 구현**

**097-2. 테스트 프로세스 (Test Process)**
**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** 테스트를 위해 수행하는 모든 작업들이 테스트의 목적과 조건을 달성할 수 있도록 도와주는 일련의 과정
• **[2] 핵심 키워드:** **5단계**, **테스트 시나리오/케이스(분석/설계)**, **테스트 프로시저(구현/실현)**
• **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 테스트 관리
• **[4] 시험 포인트:** 테스트 프로세스 **5단계의 순서**와 각 단계별 **주요 산출물**을 묻는 문제가 출제됨.
    1. **계획 및 제어 (Planning & Control):** 테스트 목표 달성을 위한 계획을 수립하고, 진행 상황을 제어함
    2. **분석 및 설계 (Analysis & Design):** 테스트 목표를 구체화하여 **테스트 시나리오**와 **테스트 케이스**를 작성함
    3. **구현 및 실현 (Implementation & Execution):** 효율적인 수행을 위해 테스트 케이스들을 조합하여 **테스트 프로시저(절차)**를 명세화하고, 실제 테스트를 수행함
    4. **평가 (Evaluation):** 계획과 목표에 맞게 수행되었는지 평가하고 기록함
    5. **완료 (Completion):** 추후 참고 자료 및 증거 자료로 활용하기 위해 산출물을 기록 및 저장함
• **[5] 한 문장 설명:** 테스트 프로세스는 '계획/제어 $\rightarrow$ 분석/설계(케이스 작성) $\rightarrow$ 구현/실현(프로시저 작성 및 수행) $\rightarrow$ 평가 $\rightarrow$ 완료'의 5단계로 진행된다.
**TẦNG B – NOTE 보충 (HIỂU SÂU)**
• **단계별 비유 (여행 계획):**
    ◦ **계획:** "이번 주말에 부산 가자!" (일정, 예산 수립).
    ◦ **분석/설계:** "해운대랑 광안리 가야지" (**목적지 리스트** = Test Case).
    ◦ **구현/실현:** "해운대 먼저 갔다가 버스 타고 광안리 가자" (**이동 동선** = Test Procedure) $\rightarrow$ 실제로 감 (Execution).
    ◦ **평가:** "재밌었나? 예산은 안 초과했나?" (Review).
    ◦ **완료:** 사진 정리해서 인스타그램에 올림 (Archiving).
• **용어 구분 (빈출):**
    ◦ **Test Case:** *무엇*을 검사할 것인가? (입력값, 기대결과)
    ◦ **Test Procedure:** *어떻게(어떤 순서로)* 검사할 것인가? (실행 절차)

- **[2] 핵심 키워드:** **창작물**, **배타적 독점적 권리**, **불법 복제 방지**, **저작권 보호 기술**

- **[5] 한 문장 설명:** 저작권은 프로그램 등 창작물에 대한 창작자의 배타적 권리이며, 디지털 저작물은 복제가 쉬워 별도의 저작권 보호 기술이 필요하다.

### 100-3. 디지털 저작권 관리 (DRM; Digital Right Management)의 개요

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 저작권자가 배포한 디지털 콘텐츠가 저작권자가 **의도한 용도로만 사용**되도록, 콘텐츠의 **생성, 유통, 이용**까지의 전 과정에 걸쳐 사용되는 관리 및 보호 기술
- **[2] 핵심 키워드:** **패키저(Packager)**, **클리어링 하우스(Clearing House)**, **실시간/미리 패키징**, **종량제(Metering)**
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 보안 및 저작권 관리
- **[4] 시험 포인트:** DRM의 **동작 흐름**과 **핵심 구성요소**의 역할이 출제됩니다.
    - **패키징 (Packaging):** 콘텐츠를 보호하기 위해 암호화하는 과정.
        - **크기가 작은 경우 (음원, 문서):** 사용자가 요청하는 시점에 **실시간**으로 패키징
        - **크기가 큰 경우 (영화 등):** 배포 전에 **미리** 패키징을 수행함
    - **클리어링 하우스 (Clearing House):** 저작권자가 설정한 **라이선스 정보가 등록**되는 곳으로, 사용자가 콘텐츠를 이용할 때 **인증 및 권한 소유 여부**를 확인해주는 역할을 함
    - **종량제 과금:** 소프트웨어의 실제 사용량을 측정하여 이용한 만큼 요금을 부과하는 방식도 DRM을 통해 구현됨
- **[5] 한 문장 설명:** DRM은 디지털 콘텐츠가 정해진 규칙대로만 사용되도록 제어하는 기술로, 패키저가 콘텐츠를 잠그고 클리어링 하우스가 열쇠(권한)를 관리한다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **비유 (호텔 카드키 시스템):**
    - **콘텐츠:** 호텔 객실 (들어가고 싶은 곳).
    - **패키저:** 방문 도어락 (잠그는 역할).
    - **클리어링 하우스:** 프론트 데스크 (투숙객인지 확인하고 카드키를 발급해주는 곳).
    - **사용자:** 카드키를 대고 문을 여는 투숙객.
- **왜 필요한가?:** 단순히 "복제 금지"만 하는 게 아니라, "3일간만 보기", "인쇄는 안 되고 화면 보기만 가능", "한 번 볼 때마다 500원" 같이 **세밀한 제어**를 하기 위해서임.

### 100-. 디지털 저작권 관리의 기술 요소 (DRM Technical Elements)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** DRM을 실현하기 위해 필요한 구체적인 정보보호 및 관리 기술들의 집합
- **[2] 핵심 구성요소 (암기 필수):**
    - **암호화 (Encryption):** 콘텐츠를 허가된 사용자만 볼 수 있도록 잠그는 기술 (가장 기본)
    - **키 관리 (Key Management):** 콘텐츠를 암호화/복호화하는 데 필요한 **암호화 키(Key)**를 안전하게 저장하고 배포하는 기술
    - **식별 기술 (Identification):** 콘텐츠마다 고유한 번호를 부여하여 구별하는 기술 (예: **DOI**, **URI**)
    - **저작권 표현 (Right Expression):** "3회 재생 가능", "복사 불가" 등 라이선스 내용을 기계가 이해할 수 있는 언어(XML 등)로 표현하는 기술 (예: **XrML**)
    - **크랙 방지 (Tamper Resistance):** 해커가 프로그램의 보호 기능을 무력화하려는 시도(Tampering)를 막는 기술
    - **인증 (Authentication):** 콘텐츠를 요청한 사람이 정당한 사용자인지 확인하는 기술
- **[3] 한 문장 설명:** DRM 시스템은 콘텐츠를 암호화하고(Encryption), 키를 관리하며(Key Management), 사용 권한을 표현(Right Expression)하고, 불법 변조를 막는(Tamper Resistance) 기술들로 구성된다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **기술 간의 관계:**
    - **암호화**가 '자물쇠'라면, **키 관리**는 '열쇠 보관함'임. 자물쇠가 아무리 튼튼해도 열쇠를 아무데나 두면 소용없음.
    - *식별 기술(DOI)**은 '주민등록번호'와 같음. "이 파일이 그 영화 맞니?"라고 확인하는 용도.
    - **크랙 방지**는 '자물쇠를 톱으로 썰지 못하게 하는 특수 합금' 같은 역할임.

## 101. DRM 패키징 및 라이선스 등록

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 디지털 콘텐츠를 암호화하여 패키징하고, 저작권자가 설정한 권한 정보를 클리어링 하우스에 등록하는 과정
- * 핵심 키워드**: 패키징(Packaging), 라이선스(License), 클리어링 하우스, 전자서명
- * 구조 / 관점 / 분류**: 콘텐츠 보호 및 관리 프로세스
- * 시험 포인트**: 콘텐츠 크기에 따라 실시간 패키징(소규모)과 사전 패키징(대규모)으로 구분함
- * 한 문장 설명**: 저작권자가 설정한 라이선스 정보는 클리어링 하우스에 등록되어 관리된다.
- * 연관 설명**: 102, 103

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- 원본 콘텐츠가 아날로그인 경우 디지털로 변환한 후 패키저(Packager)에 의해 DRM 패키징 수행
- 음원이나 문서처럼 크기가 작은 경우 사용자의 요청 시점에서 실시간으로 패키징함
- 크기가 큰 콘텐츠는 미리 패키징을 완료한 후 배포하는 방식을 사용함
- 패키징된 콘텐츠에는 암호화된 저작권자의 전자서명이 포함됨
- 사용자는 클리어링 하우스에 등록된 라이선스 정보를 통해 권한을 확인받아야 함

## 102. 클리어링 하우스 (Clearing House)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 시험 포인트**: 종량제 방식 적용 시 서비스 실제 사용량을 측정하여 요금을 부과하는 역할
- * 한 문장 설명**: 클리어링 하우스는 사용자 인증과 콘텐츠 사용 권한 소유 여부를 확인해 주는 곳이다.

- 암호화(Encryption): 콘텐츠 및 라이선스를 보호하기 위한 핵심 기술

- * 핵심 키워드**: 저장소(Repository), 가져오기(Import), 체크아웃, 체크인, 커밋, 동기화

- * 한 문장 설명**: 버전 관리 용어는 개발자들이 저장소에 파일을 주고받으며 변경 내역을 관리하는 절차를 정의한다.

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **저장소(Repository)**: 최신 버전의 파일들과 변경 내역에 대한 정보가 실제로 저장되는 공간
- **가져오기(Import)**: 버전 관리가 되지 않은 상태의 파일을 저장소에 처음으로 복사하는 작업
- **체크아웃(Check-Out)**: 수정을 위해 저장소에서 파일과 버전 관리 정보를 자신의 작업 공간으로 받아옴
- **체크인(Check-In)**: 수정한 파일을 저장소의 파일에 새로운 버전으로 갱신하여 등록함
- **동기화(Update)**: 저장소에 있는 최신 버전으로 자신의 로컬 작업 공간을 맞추는 작업

- * 한 문장 설명**: 공유 폴더 방식은 단순한 파일 복사를 통해 버전 관리를 수행하는 전통적인 기법이다.

- * 한 문장 설명**: 클라이언트/서버 방식은 중앙 서버를 통해 데이터의 일관성을 유지하고 변경 내용을 통합한다.
- * 연관 설명**: 113, 116

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- 개발자가 자신의 PC(클라이언트)에서 작업을 완료한 후 서버에 반영(Commit)함
- 서버가 주도권을 가지며 데이터의 무결성과 보안을 강화하기에 유리함
- **CVS, SVN**: 가장 널리 쓰이는 대표적인 클라이언트/서버 방식의 도구임
- 네트워크 연결이 끊어지면 중앙 서버에 접근할 수 없어 버전 관리가 어려워지는 단점이 있음

### 115.버전 관리 도구 - 분산 저장소 방식 (Distributed Repository)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 버전 관리 자료가 **하나의 원격 저장소(Remote)**와 분산된 **개발자 PC의 로컬 저장소(Local)**에 함께 저장되어 관리되는 방식
- **[2] 핵심 키워드:** **로컬 저장소(Local Repo)**, **복사(Clone)**, **오프라인 작업**, **Git**
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 형상 관리 도구 유형
- **[4] 시험 포인트:**
    - **동작 원리:** 개발자는 원격 저장소의 자료를 자신의 **로컬 저장소로 복사(Clone)**하여 작업함.
    - **작업 흐름:** 변경된 내용은 **로컬 저장소에 우선 반영(Commit)**한 다음, 이를 나중에 **원격 저장소에 반영(Push)**함.
    - **장점 (가장 중요):** 로컬에서 버전 관리가 가능하므로, **인터넷이 끊기거나 원격 저장소에 문제**가 생겨도 할 일을 계속할 수 있음 (안전성 높음).
    - **대표 도구 (암기):** **Git**, Mercurial, Bitkeeper, Bazaar 등.
- **[5] 한 문장 설명:** 분산 저장소 방식은 원격 저장소를 로컬로 복사해 작업하는 방식으로, 서버가 죽어도 로컬에서 작업이 가능하며 대표적으로 **Git**이 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **비유 (클라우드 vs USB):**
    - **중앙 집중형 (SVN):** 구글 닥스(Google Docs). 인터넷 끊기면 수정 불가.
    - **분산형 (Git):** 워드 파일을 내 컴퓨터(Local)에 다운받아서 수정. 인터넷 없어도 수정/저장 가능하고, 나중에 인터넷 될 때 업로드(Push)함.
- **시험 대비 분류:**
    1. **공유 폴더 방식 (RCS):** 그냥 폴더 하나 공유해서 씀 (매일 덮어쓰기 사고 남).
    2. **클라이언트/서버 방식 (SVN, CVS):** 중앙 서버 1대 (서버 고장나면 전멸).
    3. **분산 저장소 방식 (Git):** 모두가 서버의 복제본을 가짐 (서버 고장나면 내 걸로 복구 가능).

## 116. Subversion (서브버전, SVN)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 아파치 소프트웨어 재단에서 CVS를 개선하여 발표한 중앙 집중형 버전 관리 시스템
- * 핵심 키워드**: Trunk, Branches, Merge, Revision, Commit
- * 구조 / 관점 / 분류**: 클라이언트/서버 구조의 오픈 소스 도구
- * 시험 포인트**: 커밋(Commit)할 때마다 리비전(Revision) 번호가 1씩 증가하는 특징
- * 한 문장 설명**: SVN은 소스가 오픈되어 무료로 사용 가능하며 파일 및 디렉토리의 이름 변경과 이동이 자유롭다.
- * 연관 설명**: 112, 114

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **Trunk**: 모든 개발 작업이 기본적으로 수행되는 메인 디렉토리
- **Branches**: 추가적인 작업이나 실험적 기능을 위해 분리된 별도의 작업 공간
- **Merge**: 분리된 브랜치에서의 작업을 완료한 후 다시 트렁크와 합치는 과정
- 서버는 주로 유닉스(Unix) 환경에서 운영되며 클라이언트는 다양한 OS를 지원함
- CVS의 단점이었던 디렉토리 이동 및 이름 변경 문제를 해결하여 사용성이 높음

## 117. Git (깃)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- **원격 저장소**: 협업을 위해 여러 사람이 공유하는 곳으로 로컬 내역을 반영하거나 가져올 때 사용
- **스냅샷**: 파일의 변경 내용을 통째로 저장하는 방식으로, 이력 추적 및 복구 속도가 매우 빠름
- **브랜치**: 기본 관리 틀에 영향을 주지 않고 독립적인 기능 테스팅과 동시 개발을 가능하게 함
- 2005년 리눅스 커널 개발을 위해 처음 제작되었으며 현재 가장 대중적으로 사용됨

### 120-1. 소프트웨어의 분류 (Software Classification)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 하드웨어를 동작시켜 사용자가 작업을 편리하게 수행하도록 하는 **프로그램과 자료 구조** 등을 총칭함
- **[2] 핵심 분류:** **상용 소프트웨어(Commercial)** vs **서비스 제공 소프트웨어(Service Provision)**
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 소프트웨어 일반
- **[4] 시험 포인트:** 두 가지 대분류와 하위 상세 분류를 매칭하는 문제가 출제됩니다.
    - **1. 상용 소프트웨어 (Commercial Software):** 보통의 사용자들이 **공통적으로 필요로 하는 기능**을 제공하여 판매를 목적으로 함
        - **산업 범용 (General-purpose):**
            - **시스템 SW:** 운영체제(OS), 스토리지, 보안 등 하드웨어 제어
            - **미들웨어:** OS와 응용 프로그램 사이를 연결 (분산 시스템 등)
            - **응용 SW:** 영상 처리, CG/VR, 기업용 SW 등 특정 업무 처리
        - **산업 특화 (Specialized):** 자동차, 항공, 의료, 국방 등 **특정 분야**에서만 쓰는 기능 구현
    - **2. 서비스 제공 소프트웨어 (Service Provision Software):** 판매 목적이 아니라, **특정 사용자**가 필요로 하는 기능을 구현해서 제공함 (SI 프로젝트 등)
        - **신규 개발:** 새로운 서비스 제공 목적
        - **기능 개선:** UI, 속도, 편의성 등 기존 기능 업그레이드
        - **추가 개발:** 법/제도 변경 등으로 새로운 기능 추가
        - **시스템 통합 (System Integration):** 별도로 돌던 서비스들을 **원스톱(One-Stop)**으로 합치는 것
- **[5] 한 문장 설명:** 소프트웨어는 판매를 위한 '상용 소프트웨어'(범용/특화)와 특정 요구사항을 해결하기 위한 '서비스 제공 소프트웨어'(신규/개선/통합)로 나뉜다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **구분 팁 (돈을 버는 방식):**
    - **상용 SW:** **제품(Product)**을 팖. (예: MS Windows, Adobe Photoshop, 배틀그라운드) -> "누구나 사서 쓰세요."
    - **서비스 제공 SW:** **용역(Service)**을 제공함. (예: 삼성전자 사내 인사 시스템, 국세청 홈택스) -> "돈 줄 테니까 우리 회사만을 위해 만들어줘."
- **현업 용어:** 보통 '서비스 제공 소프트웨어' 개발을 **SI (System Integration) 업계**라고 부르고, '상용 소프트웨어' 개발을 **솔루션/패키지 업계**라고 부름.

### 120-2 애플리케이션 테스트의 기본 원리 (Basic Principles of Application Testing)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 소프트웨어의 잠재적인 결함을 줄이고 품질을 높이기 위해 테스트 수행 시 지켜야 할 가이드라인
- **[2] 핵심 키워드 (암기 필수):** **완벽한 테스트 불가능**, **파레토 법칙(Pareto)**, **살충제 패러독스(Pesticide Paradox)**, **정황(Context) 의존**
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 테스트 이론
- **[4] 시험 포인트:** 각 원리의 **정의**와 **명칭**을 연결하는 문제가 출제됩니다.
    1. **완벽한 테스팅은 불가능 (Impossible):** 테스트는 결함이 "있음"을 증명할 수는 있어도, "없음"을 증명할 수는 없음. (결함을 줄일 뿐, 제로(0)로 만들 순 없음)
    2. **파레토 법칙 (Pareto Principle):** 애플리케이션의 **20%에 해당하는 핵심 코드**에서 전체 **결함의 80%**가 발견된다는 법칙 (오류 발생의 집중성)
    3. **살충제 패러독스 (Pesticide Paradox):** 동일한 테스트 케이스로 반복해서 테스트하면 더 이상 새로운 결함을 찾을 수 없음. (벌레가 내성이 생기듯). 따라서 **테스트 케이스를 지속적으로 개선/보완**해야 함
    4. **정황(Context)에 의존:** 소프트웨어의 성격(금융, 게임, 안전 등)에 따라 테스트 방법과 강도를 다르게 적용해야 함
- **[5] 한 문장 설명:** 테스트는 완벽할 수 없으며, 오류는 특정 모듈에 집중되고(파레토), 같은 테스트만 반복하면 효과가 없으므로(살충제), 상황에 맞게(정황) 테스트를 갱신해야 한다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **살충제 패러독스 비유:**
    - 똑같은 덫을 똑같은 위치에 계속 놓으면, 쥐들이 그 길을 피해 다녀서 더 이상 안 잡힘. 새로운 덫(새로운 Test Case)을 놔야 함.
- **파레토 법칙의 교훈:**
    - "모든 코드를 다 꼼꼼히 볼 시간이 없다면?" -> **오류가 많이 나오는 그 20%의 모듈**을 찾아서 집중적으로 패라. (효율성 극대화).
- **완벽한 테스트 불가능의 의미:**
    - 고객이 "이거 버그 절대 없는 거죠?"라고 물으면, 개발자는 "버그를 못 찾았을 뿐이지 없다고는 못 합니다"라고 답하는 게 정직한(논리적인) 답변임.

### 120-3. 애플리케이션 테스트의 필요성 (Necessity of Application Testing)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 프로그램 실행 전에 오류를 찾아내어 예방하고, 제품의 신뢰도를 높이기 위해 반드시 수행해야 하는 활동
- **[2] 핵심 키워드:** **오류 예방(Error Prevention)**, **신뢰도 향상(Reliability)**, **조기 발견(Early Detection)**, **효율성(Efficiency)**
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 테스트 개요
- **[4] 시험 포인트:** 테스트를 수행해야 하는 **4가지 주요 이유**가 출제됩니다.
    - **오류 예방:** 프로그램을 실제로 실행(출시)하기 전에 **미리 오류를 발견하여 예방**할 수 있음
    - **신뢰도 향상:** 사용자의 요구사항이나 기대 수준을 만족시키는지 **반복적으로 확인**함으로써 제품에 대한 믿음(신뢰도)을 높임
    - **오류 유입 방지 (초기 테스트):** 개발 **초기부터 테스트를 계획하고 시작**하면, 단순 오류 발견뿐만 아니라 새로운 오류가 들어오는 것을 막을 수 있음
    - **효율성:** 효과적인 테스트는 **최소한의 시간과 노력**으로 **많은 결함**을 찾아낼 수 있게 해줌
- **[5] 한 문장 설명:** 애플리케이션 테스트는 출시 전 오류를 예방하고, 사용자 요구사항을 만족시켜 신뢰도를 높이며, 초기부터 수행 시 개발 비용과 노력을 절감해준다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **왜 '초기(Early)'부터 해야 하는가?:**
    - **비용의 문제 (1:10:100 법칙):** 요구사항 분석 단계에서 버그를 잡으면 1달러가 들지만, 개발 다 끝나고 잡으면 10달러, 고객에게 배포된 후에 잡으면 100달러(이미지 실추, 보상 비용 등)가 듦.
- **신뢰도 vs 품질:**
    - **품질(Quality):** 버그가 없는 것.
    - **신뢰도(Reliability):** "내가 버튼을 눌렀을 때, 항상 내가 기대한 대로 동작하는가?" (사용자 관점).

- * 한 문장 설명**: 애플리케이션 테스트는 기능을 정확히 수행하는지 검증하고 고객 요구를 만족하는지 확인한다.

- **확인(Validation)**: 사용자 시각에서 실제 요구사항에 부합하고 정상 동작하는지 확인
- 단순히 에러를 찾는 것 이상으로 소프트웨어의 신뢰성과 안정성을 높이는 품질 활동임

## 122. 애플리케이션 테스트 관련 용어

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 소프트웨어의 품질을 확인하고 검증하기 위해 사용되는 핵심적인 용어 정의
- * 핵심 키워드**: 확인(Validation), 검증(Verification)
- * 구조 / 관점 / 분류**: 사용자 입장의 테스트(확인)와 개발자 입장의 테스트(검증)
- * 시험 포인트**: '사용자 요구사항에 맞게 구현되었는가'는 확인(Validation)의 정의임
- * 한 문장 설명**: 애플리케이션 테스트는 사용자의 입장에서 확인하고 개발자의 입장에서 검증하는 과정을 포함한다.
- **: 연관 설명**: 121, 125

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **확인(Validation)**: 사용자가 요청한 대로 기능이 동작하는지, 즉 '사용자 시각'에서 결과를 중시함
- **검증(Verification)**: 개발자가 설계한 명세서나 규격에 맞게 만들어졌는지, 즉 '개발자 시각'에서 과정을 중시함
- 소프트웨어 품질은 명세서 준수(검증)뿐만 아니라 실제 사용자의 만족(확인)이 동시에 이루어져야 확립됨

### 122-1.애플리케이션 테스트의 분류 - 실행 여부 (Classification by Execution)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 프로그램을 실제로 **실행하는지 여부**에 따라 테스트 방식을 크게 두 가지로 나눔
- **[2] 핵심 분류:** **정적 테스트(Static)** vs **동적 테스트(Dynamic)**
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 테스트 기법
- **[4] 시험 포인트:** 두 테스트의 **정의(실행 여부)**와 **종류(예시)**를 구분하는 문제가 출제됨.
    - **정적 테스트 (Static Test):**
        - 프로그램을 **실행하지 않고** 명세서나 소스 코드를 대상으로 분석하는 테스트
        - 개발 초기에 결함을 발견하여 비용을 절감하는 데 효과적임.
        - **종류:** **워크스루(Walkthrough)**, **인스펙션(Inspection)**, **코드 검사**
    - **동적 테스트 (Dynamic Test):**
        - 프로그램을 **실행하여** 오류를 찾는 테스트
        - 소프트웨어 개발의 모든 단계에서 수행됨.
        - **종류:** **블랙박스 테스트**, **화이트박스 테스트**
- **[5] 한 문장 설명:** 테스트는 프로그램을 돌려보지 않고 문서를 검토하는 '정적 테스트'(워크스루, 인스펙션)와, 실제로 돌려보는 '동적 테스트'(화이트박스, 블랙박스)로 나뉜다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **비유 (책 교정):**
    - **정적 테스트:** 책을 인쇄하기 전에 원고를 눈으로 읽으며 오타를 찾는 것 (내용 실행 X).
    - **동적 테스트:** 책이 나온 뒤에 실제로 소리 내어 읽어보거나, 독자에게 읽혀서 반응을 보는 것 (내용 실행 O).
- **관계:** 우리가 흔히 말하는 '테스트'는 대부분 **동적 테스트**이지만, 품질을 높이기 위해서는 코딩 단계에서 **정적 테스트(리뷰)**를 잘하는 것이 매우 중요함.

## 123. 프로그램 실행 여부에 따른 테스트

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 핵심 키워드**: 정적 테스트(Static), 동적 테스트(Dynamic), 워크스루, 인스펙션
- * 구조 / 관점 / 분류**: 실행 여부에 따른 정적 분석과 동적 실행 테스트
- * 시험 포인트**: 화이트박스와 블랙박스 테스트는 모두 '동적 테스트'에 해당함
- * 한 문장 설명**: 정적 테스트는 코드 실행 없이 결함을 발견하고, 동적 테스트는 실행을 통해 오류를 검출한다.

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **정적 테스트**: 개발 초기에 명세서나 소스 코드를 분석하여 결함을 미리 발견함으로써 개발 비용을 절감함
- **워크스루(Walkthrough)**: 개발자가 직접 설명하고 동료들이 검토하는 비정식적인 회의 방식
- **인스펙션(Inspection)**: 공식적인 검토 회의로, 작성자 외의 다른 전문가들이 결함을 찾아내는 과정
- **동적 테스트**: 모든 개발 단계에서 수행 가능하며 소프트웨어의 실제 동작 상태를 확인하는 데 필수적임

## 124. 테스트 기반(Test Bases)에 따른 테스트

- * 핵심 키워드**: 명세 기반(Specification), 구조 기반(Structure), 경험 기반(Experience)
- * 구조 / 관점 / 분류**: 요구사항 명세, 내부 논리, 테스터의 노하우 기준 분류
- * 시험 포인트**: 명세가 불충분하거나 시간이 부족할 때는 경험 기반 테스트가 효과적임
- * 한 문장 설명**: 테스트는 사용자의 요구사항 명세, 시스템의 내부 논리, 또는 전문가의 경험을 기반으로 수행된다.
- **: 연관 설명**: 096, 130, 131

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **명세 기반 테스트**: 사용자의 요구사항을 빠짐없이 테스트 케이스로 만들어 확인하며, 동등 분할이나 경계 값 분석 등이 포함됨
- **구조 기반 테스트**: 프로그램 내부의 로직과 제어 흐름을 직접 확인하며 구문 기반, 결정 기반 등이 있음
- **경험 기반 테스트**: 유사 기술에 대한 테스터의 직관과 노하우를 활용하며 에러 추정, 탐색적 테스팅 등이 대표적임

## 125. 시각에 따른 테스트

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 테스트를 수행하는 주체(개발자 vs 사용자)와 목적에 따른 분류
- * 핵심 키워드**: 검증(Verification), 확인(Validation), 살충제 패러독스, 오류-부재의 궤변
- * 구조 / 관점 / 분류**: 제품 생산 과정(검증)과 제품 사용 결과(확인) 관점
- * 시험 포인트**: 결함을 모두 제거해도 사용자 요구를 만족하지 못하면 품질이 낮은 것임(오류-부재의 궤변)
- * 한 문장 설명**: 검증 테스트는 명세서대로의 완성을, 확인 테스트는 사용자 요구대로의 정상 동작을 점검한다.
- **: 연관 설명**: 122

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **살충제 패러독스(Pesticide Paradox)**: 동일한 테스트 케이스로 반복 테스트를 하면 더 이상 새로운 결함을 찾을 수 없는 현상
- **결함 집중(Defect Clustering)**: 대다수의 결함은 특정 소수 모듈에 집중되어 발생한다는 이론 (파레토 법칙 적용)
- 테스트 전략 수립 시 결함이 집중된 20%의 모듈을 집중적으로 테스트하여 효율성을 높여야 함

## 126. 목적에 따른 테스트

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 무엇을 검증하고자 하는지에 따라 다양한 목적으로 분류되는 테스트 유형
- * 핵심 키워드**: 회복, 안전, 강도(Stress), 성능, 회귀(Regression), 병행
- * 구조 / 관점 / 분류**: 시스템의 기능적/비기능적 속성 검증 목적
- * 시험 포인트**: '코드 수정 후 새로운 결함 유무를 확인'하는 테스트는 회귀(Regression) 테스트임
- * 한 문장 설명**: 애플리케이션은 복구 능력, 보안, 과부하 대응 등 구체적인 목적에 맞춰 다양한 테스트를 거친다.
- **: 연관 설명**: 132, 140

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **강도(Stress) 테스트**: 시스템에 과도한 정보량이나 빈도를 부과하여 과부하 시의 정상 실행 여부를 확인 함
- **회귀(Regression) 테스트**: 수정된 코드가 기존 기능에 영향을 주지 않았는지 보증하기 위해 반복 수행함
- **회복(Recovery) 테스트**: 결함 발생 후 시스템이 올바르게 복구되는지 점검함
- **병행(Parallel) 테스트**: 변경된 소프트웨어와 기존 버전에 동일 데이터를 입력하여 결과를 비교함

---

**애플리케이션 테스트의 비유**:
**정적 테스트(123)**는 건물을 짓기 전 설계도를 꼼꼼히 훑어보는 것이고, **동적 테스트(123)**는 실제로 문을 열고 닫으며 확인하는 것입니다. 만약 설계도대로 잘 지어졌는지(검증)만 확인하고 실제 살 사람이 편한지(확인)를 무시한다면, 그것이 바로 **오류-부재의 궤변(125)**에 빠지는 것입니다.

## 127. 화이트박스 테스트 (White Box Test)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 모듈의 원시 코드를 오픈시킨 상태에서 원시 코드의 논리적인 모든 경로를 테스트하여 테스트 케이스를 설계하는 방법
- * 핵심 키워드**: 원시 코드 오픈, 논리적 경로, 제어 구조, 동적 테스트
- * 구조 / 관점 / 분류**: 개발자 관점의 코드 내부 로직 검증
- * 시험 포인트**: 원시 코드의 모든 문장을 최소 한 번 이상 실행하는 것이 특징임
- * 한 문장 설명**: 화이트박스 테스트는 프로그램 내부 로직과 제어 구조를 직접 관찰하여 모든 문장의 실행 여부를 확인한다.
- * 연관 설명**: 123, 128, 129

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- 프로그램 내부의 작동 과정을 직접 들여다보며 테스트 케이스를 설계함
- 선택(if), 반복(for, while) 등의 분기점 부분을 수행하여 논리적 경로를 제어함
- 모듈 안의 작동을 직접 관찰할 수 있는 가시성을 제공함
- 소스 코드의 복잡도를 평가하고 내부 경로가 올바르게 작동하는지 확인함
- 화이트박스 테스트는 동적 테스트의 한 종류로 분류됨

## 128. 화이트박스 테스트의 종류

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 화이트박스 테스트를 수행하기 위해 사용되는 세부적인 검사 기법들
- * 핵심 키워드**: 기초 경로 검사, 조건 검사, 루프 검사, 데이터 흐름 검사
- * 구조 / 관점 / 분류**: 테스트 대상 로직의 특성에 따른 분류
- * 시험 포인트**: '데이터 흐름 검사'는 변수의 정의와 변수 사용 위치에 초점을 맞춤
- * 한 문장 설명**: 화이트박스 테스트는 기초 경로 검사와 조건, 반복, 데이터 흐름을 점검하는 제어 구조 검사로 나뉜다.
- * 연관 설명**: 127, 129

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **기초 경로 검사(Base Path Testing)**: 절차적 설계의 논리적 복잡성을 측정하여 실행 경로의 지침으로 사용함
- **조건 검사(Condition Testing)**: 모듈 내에 있는 논리적 조건(True/False)을 테스트함
- **루프 검사(Loop Testing)**: 프로그램의 반복 구조가 올바르게 작동하는지 집중적으로 점검함
- **데이터 흐름 검사(Data Flow Testing)**: 프로그램 내에서 값이 할당되고 사용되는 경로를 추적함

## 129. 화이트박스 테스트의 검증 기준 (Coverage)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 테스트 케이스가 소스 코드의 논리적 구조를 얼마나 충실히 수행했는지 측정하는 기준
- * 핵심 키워드**: 문장 검증, 분기 검증, 조건 검증, 분기/조건 기준
- * 구조 / 관점 / 분류**: 테스트 완성도를 평가하는 정량적 지표
- * 시험 포인트**: '분기 검증 기준'은 조건식의 결과가 True와 False인 경우가 각각 한 번 이상 수행되어야 함
- * 한 문장 설명**: 테스트 검증 기준은 구문, 결정(분기), 조건 등 소스 코드의 실행 범위를 결정하는 척도이다.
- * 연관 설명**: 127, 128

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **문장 검증(Statement Coverage)**: 모든 구문이 최소 한 번은 실행되도록 설계함
- **분기 검증(Branch Coverage)**: 결정 검증(Decision Coverage)이라고도 하며, 조건문의 모든 결과(T/F)를 확인 함
- **조건 검증(Condition Coverage)**: 조건문 내에 포함된 개별 조건식의 결과가 T/F인 경우를 모두 수행함
- **분기/조건 기준**: 분기 검증과 조건 검증을 모두 만족하도록 입력 데이터를 설계함

## 130. 블랙박스 테스트 (Black Box Test)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 소프트웨어가 수행할 특정 기능이 완전히 작동되는지 입증하기 위해 명세를 기초로 실시하는 테스트
- * 핵심 키워드**: 기능 테스트, 명세 기반, 인터페이스 오류, 후반부 적용
- * 구조 / 관점 / 분류**: 사용자 요구사항 중심의 결과 중심 테스트
- * 시험 포인트**: 프로그램 내부 구조를 고려하지 않고 인터페이스 상에서 실시됨
- * 한 문장 설명**: 블랙박스 테스트는 내부 구조를 무시한 채 명세서상의 기능이 누락 없이 작동하는지 확인한다.
- * 연관 설명**: 121, 123, 131

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- 소프트웨어 인터페이스(입출력) 단계에서 주로 실시되는 테스트임
- 부정확하거나 누락된 기능, 초기화 및 종료 오류 등을 발견하기 위해 사용함
- 프로그램의 내부 논리보다는 명세(Specification)를 기반으로 테스트 케이스를 결정함
- 테스트 과정의 후반부에 주로 적용되어 최종적인 기능을 점검함

## 131. 블랙박스 테스트의 종류

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 블랙박스 테스트를 수행하기 위해 입력 데이터와 결과값에 초점을 맞춘 기법들
- * 핵심 키워드**: 동치 분할, 경계값 분석, 원인-효과 그래프, 오류 예측, 비교 검사
- * 구조 / 관점 / 분류**: 입력 값의 범위 및 경험에 따른 기법 분류
- * 시험 포인트**: '경계값 분석'은 중간값보다 최소/최대값 부근에서 오류 발생 확률이 높다는 점을 이용함
- * 한 문장 설명**: 블랙박스 테스트는 유효/무효 값을 균등하게 나누는 동치 분할과 경계 부근을 검사하는 경계값 분석 등을 활용한다.
- * 연관 설명**: 130

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **동치 분할(Equivalence Partitioning)**: 입력 조건을 타당한 것과 타당하지 않은 것으로 나누어 테스트 케이스를 생성함
- **원인-효과 그래프**: 입력 데이터 간의 관계와 출력에 미치는 상황을 체계적으로 분석함
- **오류 예측(Error Guessing)**: 테스터의 과거 경험이나 감각을 활용하여 보충적으로 수행함
- **비교 검사(Comparison Testing)**: 여러 버전의 프로그램에 동일 데이터를 넣어 결과가 같은지 비교함

| Thời điểm | Giai đoạn sau | Giai đoạn đầu |

## 132. 개발 단계에 따른 애플리케이션 테스트

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 소프트웨어 개발 생명 주기에 따라 단계별로 분류되는 테스트 레벨
- * 핵심 키워드**: V-모델, 단위 테스트, 통합 테스트, 시스템 테스트, 인수 테스트
- * 구조 / 관점 / 분류**: 개발 단계와 테스트 단계를 연결하는 V-모델 기반 분류
- * 시험 포인트**: 요구사항 단계와 인수 테스트, 설계 단계와 통합 테스트의 연결 관계 확인
- * 한 문장 설명**: 애플리케이션 테스트는 개발 단계와 연계된 V-모델에 따라 단위부터 인수 단계까지 순차적으로 진행된다.

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **V-모델**: 요구사항-인수, 분석-시스템, 설계-통합, 구현-단위 테스트가 서로 대응됨
- 하위 단계에서 상위 단계로 갈수록 테스트의 범위가 넓어짐
- 각 단계의 테스트 결과는 이전 개발 단계의 오류를 검증하는 지표가 됨
- 소프트웨어 생명 주기(SDLC)의 각 활동 결과물에 대한 무결성을 확인함

---

**애플리케이션 테스트 기법의 비유**:
**화이트박스 테스트(127)**는 투명한 시계 속의 톱니바퀴가 하나하나 맞물려 돌아가는지 내부 설계를 확인하는 것이고, **블랙박스 테스트(130)**는 시계의 뒷면은 보지 않고 버튼을 눌렀을 때 시간이 정확히 표시되는지(기능)만 확인하는 것입니다. 만약 시계가 내부적으로는 잘 만들어졌어도 사용자가 보기 불편하다면 **오류-부재의 궤변(125)**에 빠진 시계가 됩니다.

## 133. 단위 테스트 (Unit Test)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 코딩 직후 소프트웨어 설계의 최소 단위인 모듈이나 컴포넌트에 초점을 맞춰 기능을 검증하는 것
- * 핵심 키워드**: 모듈/컴포넌트, 인터페이스, 구조 기반 테스트, 오류처리 경로
- * 구조 / 관점 / 분류**: 개발자 관점의 최하위 단계 테스트
- * 시험 포인트**: 알고리즘 오류, 무한 루프, 계산 수식 오류 등을 발견하는 단계임
- * 한 문장 설명**: 단위 테스트는 모듈 내부의 로직을 상대로 하며 주로 화이트박스 테스트 기법을 사용한다.

### TẦNG B – NOTE 보충 (HIỂU SÂU)

**136-1 . 통합 테스트 (Integration Test)**
**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** 단위 테스트가 끝난 **모듈을 통합하는 과정**에서 발생하는 오류 및 결함을 찾는 테스트 기법

• **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 테스트 단계
• **[4] 시험 포인트:** 통합 방식인 **비점진적** 방식과 **점진적** 방식의 장단점을 비교하는 문제가 출제됩니다.
    ◦ **비점진적 통합 방식 (Non-incremental):**
        ▪ 단계적인 절차 없이 **모든 모듈을 한꺼번에 결합**해서 테스트함.
        ▪ 대표적으로 **빅뱅(Big Bang)** 통합 테스트가 있음
        ▪ **장점:** 규모가 작은 소프트웨어에 유리하며, 단시간 내 테스트 가능.
        ▪ **단점:** 프로그램 전체를 대상으로 하므로 **오류 발견 및 원인 식별(장애 위치 파악)이 매우 어려움**
    ◦ **점진적 통합 방식 (Incremental):**
        ▪ 모듈 단위로 **단계적으로 통합**하면서 테스트함.
        ▪ 종류: **하향식(Top-down)**, **상향식(Bottom-up)**, **혼합식(Sandwich)**
        ▪ **장점:** 오류 수정이 쉽고, 인터페이스와 관련된 오류를 완전히 테스트할 가능성이 높음
• **[5] 한 문장 설명:** 통합 테스트는 모듈 간 상호작용을 검사하는 단계로, 한 번에 합치는 '빅뱅 방식'과 단계적으로 합치는 '점진적 방식'(상향식/하향식)이 있다.
**TẦNG B – NOTE 보충 (HIỂU SÂU)**
• **비유 (자동차 조립):**
    ◦ **Unit Test:** 엔진 따로, 바퀴 따로, 핸들 따로 검사. (각 부품은 정상임).
    ◦ **Integration Test (Big Bang):** 부품을 다 조립해놓고 시동을 걸었음. 안 켜짐. $\rightarrow$ 엔진 문제인지, 배터리 연결 문제인지, 점화 플러그 문제인지 **알 수가 없음(디버깅 난이도 최상)**.

- * 한 문장 설명**: 하향식 테스트는 테스트 초기부터 사용자에게 시스템의 전체 구조를 보여주기에 유리하다.

- 상위 모듈에서는 실제 데이터를 사용한 테스트 케이스 작성이 어려울 수 있음

## 138. 상향식 통합 테스트 (Bottom Up Integration Test)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 핵심 키워드**: 클러스터(Cluster), 테스트 드라이버(Driver), 하위 모듈 우선, 스텁 불필요
- * 구조 / 관점 / 분류**: 하위에서 상위로 올라가는 점진적 통합 방식
- * 시험 포인트**: 상위 제어 모듈이 없을 때 이를 호출하고 데이터를 전달하는 '드라이버'가 필요함
- * 한 문장 설명**: 상향식 테스트는 하위 모듈들을 클러스터로 결합하여 테스트를 효율적으로 수행한다.
- * 연관 설명**: 134, 139

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **클러스터(Cluster)**: 하나의 주요 제어 모듈과 관련된 종속 모듈의 그룹
- 하위 단계부터 테스트하므로 별도의 스텁(Stub)은 필요하지 않음
- 드라이버는 테스트가 완료된 후 본래의 상위 모듈로 교체됨

## 139. 테스트 드라이버와 테스트 스텁 (Test Driver vs Test Stub)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 핵심 키워드**: 상위 모듈 대체(Driver), 하위 모듈 대체(Stub), 가짜 모듈, 매개변수 전달
- * 구조 / 관점 / 분류**: 테스트 하네스(Harness)의 핵심 구성 요소
- * 시험 포인트**: 드라이버는 상향식(Bottom Up), 스텁은 하향식(Top Down)에 사용됨
- * 한 문장 설명**: 드라이버는 하위 모듈을 호출하고, 스텁은 상위 모듈의 호출에 단순 응답을 제공한다.
- * 연관 설명**: 137, 138, 147

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **드라이버(Driver)**: 테스트 대상 모듈에 데이터를 전달하고 결과를 도출하는 상위 역할 수행
- **스텁(Stub)**: 시험용으로 일시적인 조건만 가지고 하위 모듈의 기능을 흉내 냄
- 소프트웨어 개발과 테스트를 병행할 수 있게 해주는 필수 도구임

### 140-1.테스트 케이스 작성 순서 (Test Case Writing Sequence)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 테스트 전략이나 계획서를 기반으로, 실제 테스트를 수행하기 위한 구체적인 항목(Test Case)을 작성하는 절차
- **[2] 핵심 키워드:** **자료 확보**, **우선순위(위험 평가)**, **구조 설계**, **입력값/기대결과**, **유지보수**
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 테스트 설계
- **[4] 시험 포인트:** 작성 순서 6단계를 묻거나, 특정 단계의 **활동 내용**을 묻는 문제가 출제됨.
    1. **테스트 계획 검토 및 자료 확보:** 테스트 범위와 접근 방법을 이해하고, 기능 명세서 등 필요한 자료를 수집함
    2. **위험 평가 및 우선순위 결정:** 결함의 위험도에 따라 **어디에 초점을 맞출지(우선순위)** 결정함 (파레토 법칙 적용)
    3. **테스트 요구사항 정의:** 사용자 요구사항을 재검토하고, 테스트할 기능과 조건을 분석함
    4. **테스트 구조 설계 및 방법 결정:** 테스트 케이스의 형식(Format)과 분류 방법을 정하고, 절차나 도구를 결정함
    5. **테스트 케이스 정의 (핵심):** 실제 케이스를 작성하는 단계. **입력 값(Input)**, **실행 조건**, **예상 결과(Expected Result)** 등을 구체적으로 기술함
    6. **타당성 확인 및 유지보수:** 기능 변경에 맞춰 케이스를 갱신(Update)하고 유용성을 검토함
- **[5] 한 문장 설명:** 테스트 케이스 작성은 계획 검토와 위험 평가(우선순위)를 거쳐, 구조를 잡고 입력값/예상결과를 정의한 뒤 지속적으로 유지보수하는 순서로 진행된다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **왜 '위험 평가(2단계)'가 중요한가?:**
    - 시간은 유한함. 모든 것을 테스트할 수 없음.
    - "결제 기능(돈)"이 "프로필 사진 변경"보다 위험도가 훨씬 높으므로, 결제 기능부터 꼼꼼히 테스트하도록 우선순위를 매기는 과정임.
- **Test Case의 3요소:**
    - **Input (입력):** "아이디에 'admin', 비번에 '1234' 입력."
    - **Condition (조건):** "로그인 페이지에서, 엔터키를 쳤을 때."

### 146-1. 테스트 자동화 도구의 장점 / 단점 (Pros/Cons of Test Automation Tools)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 사람이 반복적으로 수행하던 테스트 작업을 스크립트나 도구를 사용하여 **기계가 대신 수행**하게 하는 것.
- **[2] 핵심 키워드:** **반복 작업 자동화(Repetitive)**, **일관성(Consistency)**, **객관성(Objectivity)**, **비용/교육(Cost/Training)**
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 테스트 자동화
- **[4] 시험 포인트:** 자동화 도구의 **장점**과 **단점**을 명확히 구분하는 문제가 출제됩니다.
    - **장점 (Pros):**
        - **효율성:** 데이터 재입력 같은 **반복적인 작업을 자동화**하여 인력과 시간을 획기적으로 줄임
        - **일관성 & 객관성:** 사람의 컨디션에 좌우되지 않고 **사용자 요구사항을 일관성 있게 검증**하며, 결과에 대한 **객관적인 평가 기준**을 제공함
        - **품질 향상:** 다양한 환경(다중 플랫폼)에서의 호환성을 보장하고, **UI가 없는 서비스**도 정밀하게 테스트 가능함
        - **시각화:** 결과를 그래프 등 다양한 형태로 보여줌
    - **단점 (Cons):**
        - **진입 장벽:** 도구 사용법에 대한 별도의 **교육 및 학습**이 필요함 (배우는 데 시간 걸림)
        - **초기 비용:** 프로세스 단계별로 적용하기 위한 **시간, 비용, 노력**이 많이 듦 (초기 세팅이 힘듦)
        - **가격:** 좋은 비공개 상용 도구(Commercial Tool)는 **가격이 비쌈**
- **[5] 한 문장 설명:** 테스트 자동화는 반복 작업을 줄이고 결과의 일관성/객관성을 보장하지만, 도구 사용법을 배워야 하고 초기 구축 비용이 많이 든다는 단점이 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **비유 (손설거지 vs 식기세척기):**
    - **손설거지 (Manual):** 그릇이 적을 땐 빠름. 하지만 매일 100명분을 해야 한다면? 사람이 지쳐서 그릇을 깸 (Human Error).
    - **식기세척기 (Automation):**
        - **장점:** 100명분이든 1000명분이든 똑같은 품질로 닦아줌. 사람은 딴 거 하면 됨.
        - **단점:** 기계가 비쌈. 그릇 넣는 법(Scripting)을 배워야 함. 그릇이 1개뿐이면 오히려 기계 돌리는 게 낭비임.
- **결론:** "반복되는 테스트(Regression Test)"에는 자동화가 필수적임.

**141-2. 테스트 자동화 수행 시 고려사항 (Considerations for Test Automation)**
**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** 테스트 자동화를 성공적으로 도입하고 운영하기 위해 계획 단계에서 검토해야 할 핵심 원칙들
• **[2] 핵심 키워드:** **재사용성(Reusability)**, **적절한 도구(Appropriate Tool)**, **일정 계획(Scheduling)**, **초기 투입(Early Involvement)**
• **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 테스트 자동화 관리
• **[4] 시험 포인트:** 자동화 수행 시 **지켜야 할 사항**과 **피해야 할 사항**이 출제됩니다.
    ◦ **대상 선정:** 테스트 절차를 고려할 때, **재사용 및 측정이 불가능한** 테스트 프로그램은 자동화 대상에서 **제외**해야 함 (1회성 테스트는 자동화하면 손해임)
    ◦ **도구 선택:** 모든 테스트 과정을 완벽하게 자동화할 수 있는 '만능 도구'는 없으므로, **용도에 맞는 적절한 도구**를 선택해서 사용해야 함
    ◦ **일정 관리:** 자동화 도구를 도입하려면 **환경 설정** 및 사용법을 익히는 **습득 기간**이 필요하므로, 이를 프로젝트 일정에 포함시켜야 함
    ◦ **인력 투입:** 테스트 엔지니어가 늦게 투입되면 프로젝트 이해도가 떨어져 불완전한 테스트가 될 수 있으므로, 반드시 **프로젝트 초기**에 투입 시기를 계획해야 함
• **[5] 한 문장 설명:** 테스트 자동화 시에는 재사용 불가능한 테스트는 제외하고, 용도에 맞는 도구를 선택하며, 도구 습득 시간과 엔지니어의 조기 투입을 일정에 반영해야 한다.
**TẦNG B – NOTE 보충 (HIỂU SÂU)**
• **왜 '재사용성'이 중요한가?:**
    ◦ 자동화 스크립트를 짜는 데 3일이 걸렸는데, 테스트를 딱 한 번만 돌리고 끝난다면? $\rightarrow$ 그냥 사람이 1시간 동안 손으로 하는 게 훨씬 이득임.
    ◦ 자동화는 **"만들어서 여러 번 우려먹어야"** 본전이 뽑히는 투자임.
• **엔지니어 조기 투입의 이유:**
    ◦ 개발 다 끝난 뒤에 "자, 이제 자동화해주세요"라고 하면, 엔지니어는 "이 버튼의 ID가 뭐죠?", "이 기능은 왜 이렇게 동작하죠?"라고 묻느라 시간 다 보냄.
    ◦ 기획/설계 단계부터 같이 참여해야 **"자동화하기 좋은 구조"**로 개발할 수 있음.

## 150. 빅오 표기법 (Big-O Notation)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- **O(n log n)**: 힙 정렬, 2-Way 합병 정렬의 복잡도
- **O(n^2)**: 삽입, 선택, 버블 정렬의 최악/평균 복잡도
