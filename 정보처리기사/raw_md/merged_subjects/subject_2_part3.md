- * 연관 설명**: 132, 135

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **알파 테스트**: 통제된 환경(개발자 장소)에서 사용자와 개발자가 함께 확인하는 기법
- **베타 테스트**: 최종 사용자가 실제 업무 환경(Field Testing)에서 직접 수행하며 발견된 오류를 보고함
- 인수 테스트를 통과하면 프로젝트가 공식적으로 종료됨

**136-1 . 통합 테스트 (Integration Test)**
**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** 단위 테스트가 끝난 **모듈을 통합하는 과정**에서 발생하는 오류 및 결함을 찾는 테스트 기법
• **[2] 핵심 키워드:** **모듈 통합(Module Integration)**, **인터페이스 오류(Interface Error)**, **비점진적(Big Bang)** vs **점진적(Incremental)**
• **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 테스트 단계
• **[4] 시험 포인트:** 통합 방식인 **비점진적** 방식과 **점진적** 방식의 장단점을 비교하는 문제가 출제됩니다.
    ◦ **비점진적 통합 방식 (Non-incremental):**
        ▪ 단계적인 절차 없이 **모든 모듈을 한꺼번에 결합**해서 테스트함.
        ▪ 대표적으로 **빅뱅(Big Bang)** 통합 테스트가 있음
        ▪ **장점:** 규모가 작은 소프트웨어에 유리하며, 단시간 내 테스트 가능.
        ▪ **단점:** 프로그램 전체를 대상으로 하므로 **오류 발견 및 원인 식별(장애 위치 파악)이 매우 어려움**
    ◦ **점진적 통합 방식 (Incremental):**
        ▪ 모듈 단위로 **단계적으로 통합**하면서 테스트함.
        ▪ 종류: **하향식(Top-down)**, **상향식(Bottom-up)**, **혼합식(Sandwich)**
        ▪ **장점:** 오류 수정이 쉽고, 인터페이스와 관련된 오류를 완전히 테스트할 가능성이 높음
• **[5] 한 문장 설명:** 통합 테스트는 모듈 간 상호작용을 검사하는 단계로, 한 번에 합치는 '빅뱅 방식'과 단계적으로 합치는 '점진적 방식'(상향식/하향식)이 있다.
**TẦNG B – NOTE 보충 (HIỂU SÂU)**
• **비유 (자동차 조립):**
    ◦ **Unit Test:** 엔진 따로, 바퀴 따로, 핸들 따로 검사. (각 부품은 정상임).
    ◦ **Integration Test (Big Bang):** 부품을 다 조립해놓고 시동을 걸었음. 안 켜짐. $\rightarrow$ 엔진 문제인지, 배터리 연결 문제인지, 점화 플러그 문제인지 **알 수가 없음(디버깅 난이도 최상)**.
    ◦ **Integration Test (Incremental):** 엔진에 변속기만 붙여서 돌려봄(OK). 거기에 바퀴 붙여서 돌려봄(OK). $\rightarrow$ 에러 나면 방금 붙인 그 놈이 범인임.

## 137. 하향식 통합 테스트 (Top Down Integration Test)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 프로그램의 상위 모듈에서 하위 모듈 방향으로 통합하며 테스트하는 기법
- * 핵심 키워드**: 주요 제어 모듈, 깊이 우선(Depth-first), 넓이 우선(Breadth-first), 스텁(Stub)
- * 구조 / 관점 / 분류**: 상위에서 하위로 내려가는 점진적 통합 방식
- * 시험 포인트**: 미구현된 하위 모듈을 대체하기 위해 '스텁(Stub)'이 사용됨
- * 한 문장 설명**: 하향식 테스트는 테스트 초기부터 사용자에게 시스템의 전체 구조를 보여주기에 유리하다.
- * 연관 설명**: 134, 139

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **깊이 우선 통합**: 제어 경로를 따라 수직 방향의 모듈들을 먼저 통합함
- **넓이 우선 통합**: 구조의 수평 방향에 있는 모듈들을 차례로 통합함
- 상위 모듈에서는 실제 데이터를 사용한 테스트 케이스 작성이 어려울 수 있음

## 138. 상향식 통합 테스트 (Bottom Up Integration Test)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 프로그램의 하위 모듈에서 상위 모듈 방향으로 통합하며 테스트하는 기법
- * 핵심 키워드**: 클러스터(Cluster), 테스트 드라이버(Driver), 하위 모듈 우선, 스텁 불필요
- * 구조 / 관점 / 분류**: 하위에서 상위로 올라가는 점진적 통합 방식
- * 시험 포인트**: 상위 제어 모듈이 없을 때 이를 호출하고 데이터를 전달하는 '드라이버'가 필요함
- * 한 문장 설명**: 상향식 테스트는 하위 모듈들을 클러스터로 결합하여 테스트를 효율적으로 수행한다.
- * 연관 설명**: 134, 139

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **클러스터(Cluster)**: 하나의 주요 제어 모듈과 관련된 종속 모듈의 그룹
- 하위 단계부터 테스트하므로 별도의 스텁(Stub)은 필요하지 않음
- 드라이버는 테스트가 완료된 후 본래의 상위 모듈로 교체됨

## 139. 테스트 드라이버와 테스트 스텁 (Test Driver vs Test Stub)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 결합 테스트 시 미구현된 모듈을 대체하거나 구동하기 위한 가짜(Dummy) 모듈
- * 핵심 키워드**: 상위 모듈 대체(Driver), 하위 모듈 대체(Stub), 가짜 모듈, 매개변수 전달
- * 구조 / 관점 / 분류**: 테스트 하네스(Harness)의 핵심 구성 요소
- * 시험 포인트**: 드라이버는 상향식(Bottom Up), 스텁은 하향식(Top Down)에 사용됨
- * 한 문장 설명**: 드라이버는 하위 모듈을 호출하고, 스텁은 상위 모듈의 호출에 단순 응답을 제공한다.
- * 연관 설명**: 137, 138, 147

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **드라이버(Driver)**: 테스트 대상 모듈에 데이터를 전달하고 결과를 도출하는 상위 역할 수행
- **스텁(Stub)**: 시험용으로 일시적인 조건만 가지고 하위 모듈의 기능을 흉내 냄
- 소프트웨어 개발과 테스트를 병행할 수 있게 해주는 필수 도구임

### 140-1.테스트 케이스 작성 순서 (Test Case Writing Sequence)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 테스트 전략이나 계획서를 기반으로, 실제 테스트를 수행하기 위한 구체적인 항목(Test Case)을 작성하는 절차
- **[2] 핵심 키워드:** **자료 확보**, **우선순위(위험 평가)**, **구조 설계**, **입력값/기대결과**, **유지보수**
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 테스트 설계
- **[4] 시험 포인트:** 작성 순서 6단계를 묻거나, 특정 단계의 **활동 내용**을 묻는 문제가 출제됨.
    1. **테스트 계획 검토 및 자료 확보:** 테스트 범위와 접근 방법을 이해하고, 기능 명세서 등 필요한 자료를 수집함
    2. **위험 평가 및 우선순위 결정:** 결함의 위험도에 따라 **어디에 초점을 맞출지(우선순위)** 결정함 (파레토 법칙 적용)
    3. **테스트 요구사항 정의:** 사용자 요구사항을 재검토하고, 테스트할 기능과 조건을 분석함
    4. **테스트 구조 설계 및 방법 결정:** 테스트 케이스의 형식(Format)과 분류 방법을 정하고, 절차나 도구를 결정함
    5. **테스트 케이스 정의 (핵심):** 실제 케이스를 작성하는 단계. **입력 값(Input)**, **실행 조건**, **예상 결과(Expected Result)** 등을 구체적으로 기술함
    6. **타당성 확인 및 유지보수:** 기능 변경에 맞춰 케이스를 갱신(Update)하고 유용성을 검토함
- **[5] 한 문장 설명:** 테스트 케이스 작성은 계획 검토와 위험 평가(우선순위)를 거쳐, 구조를 잡고 입력값/예상결과를 정의한 뒤 지속적으로 유지보수하는 순서로 진행된다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **왜 '위험 평가(2단계)'가 중요한가?:**
    - 시간은 유한함. 모든 것을 테스트할 수 없음.
    - "결제 기능(돈)"이 "프로필 사진 변경"보다 위험도가 훨씬 높으므로, 결제 기능부터 꼼꼼히 테스트하도록 우선순위를 매기는 과정임.
- **Test Case의 3요소:**
    - **Input (입력):** "아이디에 'admin', 비번에 '1234' 입력."
    - **Condition (조건):** "로그인 페이지에서, 엔터키를 쳤을 때."
    - **Expected Result (기대 결과):** "메인 페이지로 이동하고, 상단에 '환영합니다' 메시지가 떠야 함."

        ▪ **유스케이스(Use Case) 간의 업무 흐름**이 정상적인지 확인
        ▪ 개발된 **모듈/프로그램 간의 연계(Interface)**가 정상적으로 동작하는지 확인
• **[5] 한 문장 설명:** 테스트 시나리오는 요구사항과 설계서를 바탕으로 시스템/모듈별로 분리해 작성하며, 유스케이스 간의 흐름과 모듈 연계가 정상적인지 확인하는 문서다.

• **Test Case vs Test Scenario:**

    ◦ 기능 하나하나는 잘 되더라도, 이어 붙였을 때 데이터가 끊기면 안 되기 때문. (예: 장바구니에는 담겼는데 결제창 가면 목록이 비어있는 경우).

### 146-1. 테스트 자동화 도구의 장점 / 단점 (Pros/Cons of Test Automation Tools)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 사람이 반복적으로 수행하던 테스트 작업을 스크립트나 도구를 사용하여 **기계가 대신 수행**하게 하는 것.
- **[2] 핵심 키워드:** **반복 작업 자동화(Repetitive)**, **일관성(Consistency)**, **객관성(Objectivity)**, **비용/교육(Cost/Training)**
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 테스트 자동화
- **[4] 시험 포인트:** 자동화 도구의 **장점**과 **단점**을 명확히 구분하는 문제가 출제됩니다.
    - **장점 (Pros):**
        - **효율성:** 데이터 재입력 같은 **반복적인 작업을 자동화**하여 인력과 시간을 획기적으로 줄임
        - **일관성 & 객관성:** 사람의 컨디션에 좌우되지 않고 **사용자 요구사항을 일관성 있게 검증**하며, 결과에 대한 **객관적인 평가 기준**을 제공함
        - **품질 향상:** 다양한 환경(다중 플랫폼)에서의 호환성을 보장하고, **UI가 없는 서비스**도 정밀하게 테스트 가능함
        - **시각화:** 결과를 그래프 등 다양한 형태로 보여줌
    - **단점 (Cons):**
        - **진입 장벽:** 도구 사용법에 대한 별도의 **교육 및 학습**이 필요함 (배우는 데 시간 걸림)
        - **초기 비용:** 프로세스 단계별로 적용하기 위한 **시간, 비용, 노력**이 많이 듦 (초기 세팅이 힘듦)
        - **가격:** 좋은 비공개 상용 도구(Commercial Tool)는 **가격이 비쌈**
- **[5] 한 문장 설명:** 테스트 자동화는 반복 작업을 줄이고 결과의 일관성/객관성을 보장하지만, 도구 사용법을 배워야 하고 초기 구축 비용이 많이 든다는 단점이 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **비유 (손설거지 vs 식기세척기):**
    - **손설거지 (Manual):** 그릇이 적을 땐 빠름. 하지만 매일 100명분을 해야 한다면? 사람이 지쳐서 그릇을 깸 (Human Error).
    - **식기세척기 (Automation):**
        - **장점:** 100명분이든 1000명분이든 똑같은 품질로 닦아줌. 사람은 딴 거 하면 됨.
        - **단점:** 기계가 비쌈. 그릇 넣는 법(Scripting)을 배워야 함. 그릇이 1개뿐이면 오히려 기계 돌리는 게 낭비임.
- **결론:** "반복되는 테스트(Regression Test)"에는 자동화가 필수적임.

**141-2. 테스트 자동화 수행 시 고려사항 (Considerations for Test Automation)**
**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**
• **[1] 개념:** 테스트 자동화를 성공적으로 도입하고 운영하기 위해 계획 단계에서 검토해야 할 핵심 원칙들
• **[2] 핵심 키워드:** **재사용성(Reusability)**, **적절한 도구(Appropriate Tool)**, **일정 계획(Scheduling)**, **초기 투입(Early Involvement)**
• **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 테스트 자동화 관리
• **[4] 시험 포인트:** 자동화 수행 시 **지켜야 할 사항**과 **피해야 할 사항**이 출제됩니다.
    ◦ **대상 선정:** 테스트 절차를 고려할 때, **재사용 및 측정이 불가능한** 테스트 프로그램은 자동화 대상에서 **제외**해야 함 (1회성 테스트는 자동화하면 손해임)
    ◦ **도구 선택:** 모든 테스트 과정을 완벽하게 자동화할 수 있는 '만능 도구'는 없으므로, **용도에 맞는 적절한 도구**를 선택해서 사용해야 함
    ◦ **일정 관리:** 자동화 도구를 도입하려면 **환경 설정** 및 사용법을 익히는 **습득 기간**이 필요하므로, 이를 프로젝트 일정에 포함시켜야 함
    ◦ **인력 투입:** 테스트 엔지니어가 늦게 투입되면 프로젝트 이해도가 떨어져 불완전한 테스트가 될 수 있으므로, 반드시 **프로젝트 초기**에 투입 시기를 계획해야 함
• **[5] 한 문장 설명:** 테스트 자동화 시에는 재사용 불가능한 테스트는 제외하고, 용도에 맞는 도구를 선택하며, 도구 습득 시간과 엔지니어의 조기 투입을 일정에 반영해야 한다.
**TẦNG B – NOTE 보충 (HIỂU SÂU)**
• **왜 '재사용성'이 중요한가?:**
    ◦ 자동화 스크립트를 짜는 데 3일이 걸렸는데, 테스트를 딱 한 번만 돌리고 끝난다면? $\rightarrow$ 그냥 사람이 1시간 동안 손으로 하는 게 훨씬 이득임.
    ◦ 자동화는 **"만들어서 여러 번 우려먹어야"** 본전이 뽑히는 투자임.
• **엔지니어 조기 투입의 이유:**
    ◦ 개발 다 끝난 뒤에 "자, 이제 자동화해주세요"라고 하면, 엔지니어는 "이 버튼의 ID가 뭐죠?", "이 기능은 왜 이렇게 동작하죠?"라고 묻느라 시간 다 보냄.
    ◦ 기획/설계 단계부터 같이 참여해야 **"자동화하기 좋은 구조"**로 개발할 수 있음.

## 148. 결함 (Fault)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 소프트웨어가 개발자의 설계와 다르게 동작하거나 잘못된 결과를 발생시키는 현상
- * 핵심 키워드**: 오류 발생, 작동 실패, 불일치, 결함 추적
- * 구조 / 관점 / 분류**: 개발자 설계 대비 실제 동작 결과의 차이
- * 시험 포인트**: 사용자의 예상 결과와 실행 결과가 일치하지 않는 모든 경우가 결함임
- * 한 문장 설명**: 결함은 소프트웨어의 완성도를 저해하는 오류나 명세와의 불일치를 의미한다.

## 150. 빅오 표기법 (Big-O Notation)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- * 개념**: 알고리즘의 실행 시간이 최악일 때(Worst Case)를 기준으로 복잡도를 표기하는 방법
- * 핵심 키워드**: 최악의 시간 복잡도, 성능 예측, 실행 단계 측정
- * 구조 / 관점 / 분류**: 데이터 양(n)에 따른 시간 변화량의 척도
- * 시험 포인트**: $O(1) < O(log_2n) < O(n) < O(n log_2n) < O(n^2)$ 순으로 성능이 저하됨
- * 한 문장 설명**: 빅오 표기법은 알고리즘의 효율성을 상한선 기준으로 나타내어 성능 예측을 용이하게 한다.
- * 연관 설명**: 151

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- **O(1)**: 입력값에 관계없이 일정 (스택의 Push/Pop)
- **O(log n)**: 해결 단계가 입력값에 따라 감소 (이진 트리 검색)
- **O(n log n)**: 힙 정렬, 2-Way 합병 정렬의 복잡도
- **O(n^2)**: 삽입, 선택, 버블 정렬의 최악/평균 복잡도

- **Hybrid**: Hub & Spoke와 Message Bus 방식을 혼합하여 그룹 내외부 통합에 최적화함
- 기업 내부의 데이터 무결성을 보장하고 시스템 간 연결성을 확보함

## 115. 분산 저장소 방식

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- * 개념**: 버전 관리 자료가 하나의 원격 저장소와 분산된 개발자 PC의 로컬 저장소에 함께 저장되어 관리되는 방식이다.

- * 구조 / 관점 / 분류**: 로컬과 원격의 이중 저장 구조.
- * 시험 포인트**: 원격 저장소에 문제가 생겨도 로컬 저장소의 자료를 이용하여 작업이 가능하다는 점이 핵심이다.
- * 한 문장 설명**: 로컬 저장소에서 버전 관리가 가능하므로 원격 저장소 사고 시에도 복구가 용이하다.

### TẦNG B – NOTE 보충 (HIỂU SÂU)**

- 변경된 내용은 먼저 로컬 저장소에 반영(버전 관리)한 후, 최종적으로 원격 저장소에 반영한다.
- 네트워크가 연결되지 않은 상태에서도 로컬에서 대부분의 버전 관리 기능을 수행할 수 있다.
- 대표적인 도구로는 Git, GNU arch, Mercurial, Bitkeeper 등이 있다.
