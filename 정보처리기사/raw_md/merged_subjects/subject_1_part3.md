
**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 시스템의 변경이나 확장에 유연하게 대응하기 위해 지켜야 할 5가지 원칙으로, 앞글자를 따서 **SOLID**라고 부름
- **[2] 핵심 키워드:** SOLID, SRP(단일 책임), OCP(개방-폐쇄), 응집도/결합도, 인터페이스 캡슐화,  LSP(자식=부모 행위), ISP(인터페이스 분리), DIP(의존 역전/추상화 의존)
- **[3] 구조 / 관점 / 분류:** 객체지향 설계(OOD) - 5대 원칙
- **[4] 시험 포인트:**
    - **SRP (Single Responsibility Principle):** 객체는 **'단 하나의 책임'**만 가져야 함 (응집도 높이고, 결합도 낮춤)
    - **OCP (Open-Closed Principle):** 기능 추가에는 **열려(Open)** 있어야 하고, 기존 코드 변경에는 **닫혀(Closed)** 있어야 함
    - **LSP:** **'자식 클래스는 최소한 부모 클래스의 행위를 수행할 수 있어야 한다'** (상속의 올바른 사용)
    - **ISP:** SRP가 '객체'의 단일 책임이라면, ISP는 **'인터페이스'의 단일 책임**을 의미함 (사용하지 않는 인터페이스 의존 X)
    - **DIP:** 구체적인 클래스보다 **'추상화된 클래스(인터페이스)'**와 의존 관계를 맺어야 함
- **[5] 한 문장 설명:** 변경과 확장에 유연한 시스템을 위한 5가지 원칙(SOLID) 중, SRP는 단일 책임을 강조하고 OCP는 변경 없이 확장이 가능하도록 설계하는 원칙이다. *
    - LSP는 상속의 호환성을, ISP는 인터페이스의 분리를, DIP는 추상화에 대한 의존을 강조하여 시스템의 유연성을 높인다.
- **[6] 연관 설명:** 응집도(Cohesion), 결합도(Coupling)

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **단일 책임 원칙 (SRP, Single Responsibility Principle):** '책임'이라는 모호한 개념을 '변경의 이유'로 해석하기도 함. 즉, 클래스를 수정해야 할 이유는 단 하나여야 함.
- **개방-폐쇄 원칙 (OCP, Open-Closed Principle):** 공통 인터페이스를 하나의 인터페이스로 묶어 **캡슐화**하는 방법이 대표적임. 이렇게 하면 기존 코드를 건드리지 않고 새로운 구현체를 추가할 수 있음.
- **리스코프 치환 원칙 (LSP, Liskov Substitution Principle):** 자식 클래스가 부모 클래스의 책임을 무시하거나 재정의(Overriding)하여 부모의 의도를 훼손하지 않고, **확장만 수행**하도록 해야 함.
- **인터페이스 분리 원칙 (ISP, Interface Segragation Principle ):** 자신이 사용하지 않는 메서드에 의존하지 않도록, 거대한 인터페이스를 구체적인 여러 개의 인터페이스로 분리하는 것.
- **의존 역전 원칙 (DIP, Dependency Inversion Principle ):** 하위 수준 모듈(구체적)이 상위 수준 모듈(추상적)에 의존하는 것이 자연스러워 보이지만, 실제로는 **둘 다 추상화(인터페이스)에 의존**해야 한다는 원칙.

### 054-1.모듈의 개요 (Module Overview)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 모듈화를 통해 분리된 시스템의 각 기능들로, 서브루틴(subroutine), 서브시스템(subsystem)(단일시스템), 작업 단위 등과 같은 의미로 사용됨
- **[2] 핵심 키워드:** 단독 컴파일/재사용, 기능적 독립성, 결합도(약하게), 응집도(강하게)
- **[3] 구조 / 관점 / 분류:** 소프트웨어 설계 - 구조적 설계 기초
- **[4] 시험 포인트:** 모듈의 **'기능적 독립성'**을 높이기 위한 조건이 가장 중요함.
    - **결합도(Coupling)**(Độ phụ thuộc)**:** **약하게(Weak)** 해야 함
    - **응집도(Cohesion)**(Độ gắn kết)**:** **강하게(Strong)** 해야 함
    - **모듈 크기:** 작게 만들어야 함
- **[5] 한 문장 설명:** 시스템의 기능을 분리한 단위로, 단독 컴파일과 재사용이 가능하며 결합도는 낮추고 응집도는 높여 기능적 독립성을 확보해야 한다.
- **[6] 연관 설명:** 결합도, 응집도

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **기능적 독립성 (Functional Independence):**
    - 각 모듈이 **하나의 기능**만을 수행하고, 다른 모듈과의 과도한 상호작용을 배제하는 것
    - 독립성이 높으면 모듈을 수정하더라도 **다른 모듈에 미치는 영향이 거의 없어** 오류 수정과 유지보수가 쉬움
- **측정 지표:** 모듈의 독립성은 **결합도(Coupling)**와 **응집도(Cohesion)**에 의해 측정됨
- **모듈 독립성 ↑** = 결합도 ↓ + 응집도 ↑ + 모듈 크기 ↓

## 055.결합도 (Coupling)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 모듈 간의 의존성 정도에 따라 자료, 스탬프, 제어, 외부, 공통, 내용 결합도로 분류됨
- **[2] 핵심 키워드:**
    - **자료:** 매개변수, 파라미터, 가장 바람직
    - **스탬프:** 자료 구조(배열/레코드), 포맷 변화 영향
    - **제어:** 제어 신호(Flag, Tag, Switch), 권리 전도
    - **외부:** 외부 변수 참조
    - **공통:** 공통 데이터 영역(전역 변수), 독립성 저하
    - **내용:** 내부 기능/자료 직접 참조, 스파게티 코드
- **[3] 구조 / 관점 / 분류:** 소프트웨어 설계 - 결합도 상세
- **[4] 시험 포인트:** 각 결합도의 **'정의'**와 **'핵심 상황'**을 연결하는 문제가 출제됨.
    - **파라미터(데이터)만 전달:** **자료 결합도** (가장 좋음)
    - **배열/레코드(자료 구조) 전달:** **스탬프 결합도**
    - **제어 신호(Flag) 전달:** **제어 결합도**
    - **전역 변수(공통 영역) 공유:** **공통 결합도**
- **[5] 한 문장 설명:** 결합도는 자료(파라미터) < 스탬프(구조) < 제어(신호) < 외부(참조) < 공통(전역) < 내용(직접) 순으로 강해지며, 자료 결합도가 품질이 가장 높다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **자료 결합도 (Data):** 모듈 간 인터페이스가 **자료 요소(파라미터, 인수, 매개변수)**로만 구성됨. 내용을 알 필요가 없어 가장 이상적임
- **스탬프 결합도 (Stamp):** 인터페이스로 **자료 구조(배열, 레코드 등)**가 전달됨. 구조가 변하면 조회하는 모든 모듈에 영향을 미침
- **제어 결합도 (Control):** **제어 **신호**(Function Code, Switch, Tag, Flag)**를 전달하여 다른 모듈의 흐름을 제어함. 하위 모듈이 상위 모듈에 명령을 내리는 **권리 전도 현상**이 발생할 수 있음
- **외부 결합도 (External):** 외부의 다른 모듈에서 선언한 **데이터(변수)를 참조**할 때 발생함
- **공통 결합도 (Common):** **공통 데이터 영역(전역 변수)**을 여러 모듈이 함께 사용할 때 발생. 내용이 조금만 변경되어도 모든 모듈에 영향을 미쳐 독립성이 약해짐
- **내용 결합도 (Content):** 한 모듈이 다른 모듈의 **내부 기능이나 자료를 직접 참조/수정**하거나, 내부로 제어가 이동(Branch)하는 경우. 가장 나쁜 형태
- Example
    
    ## 1️⃣ 자료 결합도 (Data Coupling) – **TỐT NHẤT**
    
    👉 Các module **chỉ truyền dữ liệu cần thiết (parameter)**.
    
    **Ví dụ**
    
    ```java
    // Module A
    intresult= sum(3,5);
    
    // Module B
    intsum(int a,int b) {
    return a + b;
    }
    
    ```
    
    **Giải thích**
    
    - Chỉ truyền `a`, `b`
    - Không biết logic bên trong của nhau
        
        ✅ Ít ảnh hưởng khi thay đổi
        
    
    ---
    
    ## 2️⃣ 스탬프 결합도 (Stamp Coupling)
    
    👉 Truyền **cả cấu trúc dữ liệu**, nhưng chỉ dùng **một phần**
    
    **Ví dụ**
    
    ```java
    classUser {
        String name;
    int age;
        String address;
    }
    
    // Module A
    printName(user);
    
    // Module B
    voidprintName(User user) {
        System.out.println(user.name);
    }
    
    ```
    
    **Giải thích**
    
    - Truyền cả `User`
    - Nhưng chỉ dùng `name`
        
        ⚠ Nếu cấu trúc `User` đổi → nhiều module bị ảnh hưởng
        
    
    ---
    
    ## 3️⃣ 제어 결합도 (Control Coupling)
    
    👉 Truyền **cờ điều khiển (flag, switch, mode)** để quyết định logic
    
    **Ví dụ**
    
    ```java
    // Module A
    processOrder(order,true);
    
    // Module B
    voidprocessOrder(Order order, boolean isExpress) {
    if (isExpress) {
    // xử lý nhanh
        }else {
    // xử lý thường
        }
    }
    
    ```
    
    **Giải thích**
    
    - Module A **can thiệp logic xử lý** của module B
        
        ⚠ Phụ thuộc logic → khó bảo trì
        
    
    ---
    
    ## 4️⃣ 외부 결합도 (External Coupling)
    
    👉 Các module cùng phụ thuộc vào **dữ liệu / format / thiết bị bên ngoài**
    
    **Ví dụ**
    
    ```java
    // Cả 2 module đều dùng chung file config.txt
    Filefile=newFile("config.txt");
    
    ```
    
    **Giải thích**
    
    - Phụ thuộc vào file, DB, protocol bên ngoài
        
        ⚠ Nếu format file đổi → nhiều module lỗi
        
    
    ---
    
    ## 5️⃣ 공통(공유) 결합도 (Common Coupling)
    
    👉 Nhiều module dùng **biến toàn cục / vùng nhớ chung**
    
    **Ví dụ**
    
    ```java
    // Global variable
    publicstaticint totalCount;
    
    // Module A
    totalCount++;
    
    // Module B
    System.out.println(totalCount);
    
    ```
    
    **Giải thích**
    
    - Thay đổi ở 1 module → module khác bị ảnh hưởng ngay
        
        ❌ Giảm tính độc lập
        
    
    ---
    
    ## 6️⃣ 내용 결합도 (Content Coupling) – **XẤU NHẤT**
    
    👉 Module **truy cập trực tiếp logic hoặc dữ liệu nội bộ** của module khác
    
    **Ví dụ**
    
    ```java
    // Module A
    moduleB.internalValue =10;
    
    // Module B
    classModuleB {
    int internalValue;
    }
    
    ```
    
    Hoặc:
    
    ```java
    // Gọi trực tiếp hàm private / nhảy vào giữa logic
    
    ```
    
    **Giải thích**
    
    - Phá vỡ hoàn toàn tính đóng gói
        
        ❌ Thay đổi nhỏ cũng gây lỗi dây chuyền

## 056.응집도 (Cohesion)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 모듈의 내부 요소들이 서로 얼마나 밀접하게 관련되어 있는지를 나타내는 정도
- **[2] 핵심 키워드:** 내부 요소 관련성, 독립적인 기능, 강할수록 좋음(High Quality), 기순교절시논우(순서 암기)
- **[3] 구조 / 관점 / 분류:** 소프트웨어 설계 - 모듈 독립성 측정 지표 2
- **[4] 시험 포인트:**
    - **품질과의 관계:** 응집도가 **강할수록 품질이 높고**, 약할수록 품질이 낮음 (결합도와 반대)
    - **순서 암기 (필수):** 응집도가 강한(좋은) 순서대로 나열하는 문제가 빈출됨. 암기 팁: **"기-순-교-절-시-논-우"**
        - **강함 (Good):** 기능(Functional) > 순차(Sequential) > 교환(Communication) > 절차(Procedural) > 시간(Temporal) > 논리(Logical) > **약함 (Bad):** 우연(Coincidental)
- **[5] 한 문장 설명:** 모듈 내부 요소들의 관련성을 나타내며, 응집도는 기능(단일 문제) < 순차(출력-입력) < 교환(동일 입출력) < ... < 우연(무관) 순으로 약해지며, 기능적 응집도가 품질이 가장 높다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **기능적 응집도 (Functional):** 모듈 내부의 모든 기능 요소들이 **단일 문제**와 연관되어 수행됨. 가장 이상적인 형태
- **순차적 응집도 (Sequential):** 한 활동의 **출력 데이터가 다음 활동의 입력 데이터**로 사용됨
- **교환(통신)적 응집도 (Communication):** **동일한 입력과 출력**을 사용하여 서로 다른 기능을 수행하는 요소들이 모여 있음
- **절차적 응집도 (Procedural):** 다수의 관련 기능을 가질 때, 그 기능들을 **순차적으로 수행**하는 경우
- **시간적 응집도 (Temporal):** **특정 시간**에 처리되는 기능들을 모아놓음 (예: 초기화 기능들)
- **논리적 응집도 (Logical):** **유사한 성격**을 갖거나 특정 형태로 분류되는 처리 요소들을 모아놓음
- **우연적 응집도 (Coincidental):** 모듈 내부 요소들이 **서로 아무런 관련 없이** 구성됨. 가장 나쁜 형태

## 057.팬인(Fan-In) / 팬아웃(Fan-Out)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 시스템의 복잡도를 측정하는 지표로, 모듈 간의 호출 관계(제어/피제어)를 숫자로 나타낸 것
- **[2] 핵심 키워드:**
    - **Fan-In (들어옴):** 나를 호출하는(제어하는) 모듈 수
    - **Fan-Out (나감):** 내가 호출하는(제어되는) 모듈 수
    - **최적화 규칙:** **Fan-In은 높게(High), Fan-Out은 낮게(Low)**
- **[3] 구조 / 관점 / 분류:** 소프트웨어 설계 - 모듈 복잡도 분석
- **[4] 시험 포인트:**
    - **Fan-In이 높다:** **재사용성** 측면에서 설계가 잘 된 것이지만, **단일 장애점(Single Point of Failure)**이 되어 전체에 영향을 줄 수 있으므로 중점 관리가 필요함
    - **Fan-Out이 높다:** 불필요하게 많은 모듈을 호출하고 있는지 검토하여 **단순화**시켜야 함
- **[5] 한 문장 설명:** Fan-In은 나를 호출하는 상위 모듈 수, Fan-Out은 내가 호출하는 하위 모듈 수를 의미하며, 시스템 복잡도를 최적화하려면 Fan-In은 높이고 Fan-Out은 낮추도록 설계해야 한다.
- **[6] 연관 설명:** 모듈화, 결합도, 구조적 설계

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **분석 목적:** 시스템의 **복잡도(Complexity)**를 알기 위해 팬인과 팬아웃을 분석함
- **설계 전략:**
    - **High Fan-In:** 여러 곳에서 해당 모듈을 쓴다는 뜻이므로 공통 모듈로서 **재사용성**이 뛰어남. 하지만 이 모듈이 고장 나면 시스템 전체가 마비될 수 있음 (관리 중요)
    - **Low Fan-Out:** 한 모듈이 너무 많은 일을 다른 모듈에 떠넘기거나 의존하지 않도록 하여, 로직을 단순하고 명확하게 유지해야 함
- Note thê
    
    ### FAN-IN / FAN-OUT (đọc lướt)
    
    ```
    A →B  (AgọiB)
    ```
    
    - **Fan-out** = số mũi tên **ĐI RA**
        
        → tôi gọi bao nhiêu module
        
    - **Fan-in** = số mũi tên **ĐI VÀO**
        
        → bao nhiêu module gọi tôi
        
    
    ❗ **Chỉ tính phụ thuộc TRỰC TIẾP** (không tính gián tiếp)
    
    Ví dụ:
    
    ```
    A →C →D
    B →D
    
    ```
    
    - Fan-out(A) = 1
    - Fan-in(D) = 2
    
    Nguyên tắc:
    
    - **Fan-out cao** → module ôm nhiều việc
    - **Fan-in cao** → module trung tâm, sửa phải rất cẩn thận
    
    👉 **RA = Fan-out | VÀO = Fan-in**
    
    | Tiêu chí | Fan-in | Fan-out | 응집도 (Cohesion) | 결합도 (Coupling) |
    | --- | --- | --- | --- | --- |
    | Bản chất | Số module **gọi vào** một module | Số module **bị gọi ra** từ một module | Mức liên quan **bên trong 1 module** | Mức phụ thuộc **giữa các module** |
    | Phạm vi | Giữa module | Giữa module | Nội bộ module | Giữa module |
    | Giá trị tốt | **Cao** | **Thấp** | **Cao** | **Thấp** |
    | Ý nghĩa | Module trung tâm, dùng chung | Module phụ thuộc nhiều nơi | 1 module = 1 nhiệm vụ rõ | Ít ảnh hưởng khi thay đổi |
    | Liên quan trực tiếp | Tái sử dụng | Độ phức tạp | Chất lượng thiết kế module | Độ phụ thuộc hệ thống |
    |  |  |  |  |  |
    - 응집도: **module 안** → 높을수록 좋음
    - 결합도: **module 사이** → 낮을수록 좋음
    - Fan-out: **내가 몇 개 부르나** → 낮을수록 좋음
    - Fan-in: **나를 몇 개가 부르나** → 높아도 괜찮음

## 058.N-S 차트 (Nassi–Schneiderman Chart)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 논리의 기술에 중점을 둔 도형을 이용한 표현 방법으로, **박스 다이어그램(Box Diagram)** 또는 **Chapin Chart**라고도 함
- **[2] 핵심 키워드:** 논리 기술 중점, 박스 다이어그램, Chapin Chart, **GOTO/화살표 사용 안 함**, 단일 입구/단일 출구
- **[3] 구조 / 관점 / 분류:** 소프트웨어 설계 - 상세 설계 도구 (논리 표현)
- **[4] 시험 포인트:**
    - **특징적 제약:** 흐름도와 달리 **'GOTO'나 '화살표'를 절대 사용하지 않는다**는 점이 가장 큰 특징이자 빈출 포인트임
    - **별칭:** **Box Diagram**, **Chapin Chart**라는 다른 이름도 기억해야 함
    - **구조:** **순차(Sequence), 선택(Selection), 반복(Repetition)**의 3가지 제어 논리 구조를 시각적으로 표현함
- **[5] 한 문장 설명:** 논리 표현에 중점을 둔 박스 형태의 다이어그램으로, GOTO나 화살표를 쓰지 않고 단일 입구/출구를 가지며 코드로 변환하기 용이하다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **장점:**
    - 이해하기 쉽고, 프로그래밍 코드(Code)로 변환이 용이함
    - 조건이 복잡한 곳의 처리를 시각적으로 명확히 식별하는 데 적합함
- **단점:**
    - 읽기는 쉽지만 **작성하기(그리기)가 어려움**
    - 임의로 제어를 전이하는 것이 불가능함 (GOTO가 없으므로)
    - 시스템의 총체적인 구조나 인터페이스를 나타내기는 어려움
- **3가지 기본 구조 (이미지 우측 도해):**
    1. **순차:** 위에서 아래로 박스가 쌓인 형태
    2. **선택:** 삼각형으로 분기되는 형태 (If-else)
    3. **반복:** 'ㄱ'자(L자) 형태로 감싸는 형태 (Loop)

## 059.공통 모듈의 개요

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 여러 프로그램에서 공통적으로 사용할 수 있는 모듈 (예: 계산식, 사용자 인증 등)
- **[2] 핵심 키워드:** 재사용성 확보, 중복 개발 회피, 명세 기법 5가지(정확성, 명확성, 완전성, 일관성, 추적성)
- **[3] 구조 / 관점 / 분류:** 소프트웨어 설계 - 모듈 설계 지침
- **[4] 시험 포인트:**
    - **목적:** **재사용성(Reusability)**을 높이고 **중복 개발을 피하기 위해** 설계함
    - **명세 기법 5가지 (암기 필수):** 공통 모듈 명세서 작성 시 준수해야 할 5가지 원칙을 묻는 문제가 출제됨.
        - **정확성 (Correctness)**
        - **명확성 (Clarity)**
        - **완전성 (Completeness)**
        - **일관성 (Consistency)**
        - **추적성 (Traceability)**
- **[5] 한 문장 설명:** 자주 사용하는 기능을 공통 모듈로 만들어 재사용성을 높여야 하며, 이를 위해 정확성, 명확성, 완전성, 일관성, 추적성을 갖춘 명세서를 작성해야 한다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **공통 모듈의 필요성:**
    - 자주 사용되는 계산식이나 매번 필요한 사용자 인증(Login) 등을 매번 새로 짜는 것은 비효율적이므로, 이를 식별하여 공통 부분으로 만듦
    - 다른 개발자들이 해당 기능을 명확히 이해하고 쓸 수 있어야 하므로 **명세 기법** 준수가 매우 중요함
- **명세 기법 상세 정의:**
    1. **정확성(Correctness):** 해당 기능이 필요하다는 것을 알 수 있도록 정확히 작성
    2. **명확성(Clarity):** 중의적으로(두 가지 뜻으로) 해석되지 않도록 명확하게 작성
    3. **완전성(Completeness):** 구현에 필요한 **모든 것**을 빠짐없이 기술
    4. **일관성(Consistency):** 공통 기능들 간에 **상호 충돌**이 발생하지 않도록 작성
    5. **추적성(Traceability):** 요구사항의 **출처**나 관련 시스템과의 관계를 파악(추적)할 수 있도록 작성

## 60. 재사용 (Reuse)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 이미 개발된 기능들을 파악하고 재구성하여, 새로운 시스템 개발에 적합하도록 최적화시키는 작업
- **[2] 핵심 키워드:** 비용/시간 절약, 사용법 공개, **결합도는 낮고(Low) 응집도는 높아야(High)** 함, 규모별 분류(함수/컴포넌트/애플리케이션)
- **[3] 구조 / 관점 / 분류:** 소프트웨어 설계 - 생산성 향상 기법
- **[4] 시험 포인트:**
    - **전제 조건:** 재사용되는 대상은 외부 모듈과의 **결합도는 낮고(Low)**, **응집도는 높아야(High)** 한다는 점이 빈출 포인트임
    - **규모에 따른 분류 (3가지 구분):**
        - **함수와 객체:** **소스 코드** 단위의 재사용
        - **컴포넌트:** 수정 없이 **인터페이스**를 통해 통신
        - **애플리케이션:** 공통 기능을 제공하는 **프로그램 자체**를 공유
- **[5] 한 문장 설명:** 비용과 시간을 절약하기 위해 기존 기능을 최적화하여 다시 쓰는 것으로, 결합도는 낮고 응집도는 높아야 하며 규모에 따라 함수, 컴포넌트, 애플리케이션 단위로 나뉜다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **목적:** 처음부터 새로 만드는 것보다 비용과 개발 시간을 획기적으로 절약하기 위함
- **공유 원칙:** 나만 아는 코드는 재사용할 수 없으므로, 누구나 이해하고 사용할 수 있도록 **사용법을 공개**해야 함
- **재사용 유형 상세:**
    1. **함수와 객체 (Function & Object):** 클래스나 메소드 단위의 **소스 코드(Source Code)**를 가져와서 쓰는 방식
    2. **컴포넌트 (Component):** 컴포넌트 자체(내부 소스)는 건드리지 않고, 제공된 **인터페이스(Interface)**를 통해서만 기능을 호출하여 사용
    3. **애플리케이션 (Application):** 공통된 기능을 제공하는 **완성된 애플리케이션**을 공유하여 사용

### 061. 효과적인 모듈 설계 방안 (Effective Module Design Strategies)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 모듈의 독립성과 재사용성을 높이기 위해 지켜야 할 설계 원칙들
- **[2] 핵심 키워드:** 결합도↓/응집도↑, 제어 영역 내 영향 영역, 복잡도/중복성 감소, 일관성 유지, 단일 입구/단일 출구
- **[3] 구조 / 관점 / 분류:** 소프트웨어 설계 - 설계 최적화 지침
- **[4] 시험 포인트:**
    - **독립성 향상:** **결합도는 줄이고(Low), 응집도는 높여서(High)** 설계해야 함 (가장 기본이자 빈출)
    - **영역 관계:** 모듈의 **영향 영역(Scope of Effect)**이 그 모듈의 **제어 영역(Scope of Control)** 안(내부)에 있어야 함
    - **구조적 특징:** **하나의 입구와 하나의 출구(Single Entry, Single Exit)**를 갖도록 해야 함
- **[5] 한 문장 설명:** 결합도는 낮추고 응집도는 높이며, 영향 영역을 제어 영역 안에 두고, 복잡도와 중복성을 줄여 유지보수가 용이하게 설계해야 한다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **제어와 영향의 관계:** 내가 제어할 수 있는 범위 안에서만 영향을 미쳐야 시스템이 예측 가능해짐. 제어할 수 없는 곳에 영향을 주면 오류 발생 시 추적이 어려움
- **예측 가능성(Predictability):** 모듈의 기능은 예측 가능해야 하며, 지나치게 제한적이어서는 안 됨
- **유지보수성(Maintainability):** 복잡도(Complexity)와 중복성(Redundancy)을 줄이고 일관성(Consistency)을 유지하여, 나중에 수정하거나 고치기 쉽게 만들어야 함
- **모듈 크기:** 시스템의 전반적인 기능과 구조를 이해하기 쉬운 적절한 크기로 분해해야 함
- **인터페이스:** 인덱스 번호나 기능 코드 등이 전반적인 처리 논리 구조에 예기치 못한 영향을 끼치지 않도록 설계해야 함

## 064. 디자인 패턴 (Design Pattern)의 개요

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 각 모듈의 세분화된 역할이나 인터페이스 구현 방안을 설계할 때 참조할 수 있는 **전형적인 해결 방식 또는 예제**
- **[2] 핵심 키워드:** 바퀴를 다시 발명하지 마라, GoF(Gang of Four), **총 23개**, 생성(5)/구조(7)/행위(11)
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 설계 재사용 기술
- **[4] 시험 포인트:**
    - **GoF (Gang of Four):** 1995년 에릭 감마 등 4명이 처음으로 패턴을 구체화 및 체계화함
    - **패턴 수 (암기 필수):** GoF 디자인 패턴은 총 **23개**이며, **생성(5개), 구조(7개), 행위(11개)**로 분류됨
    - **격언:** **"바퀴를 다시 발명하지 마라(Don't reinvent the wheel)"** - 이미 해결된 문제를 처음부터 다시 고민하지 말고 검증된 패턴을 쓰라는 의미
- **[5] 한 문장 설명:** 디자인 패턴은 "바퀴를 다시 발명하지 마라"는 원칙하에 GoF가 체계화한 23개의 전형적인 해결 방식(생성 5, 구조 7, 행위 11)이다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **효율성:** 개발 과정 중 문제가 발생했을 때 새로운 해결책을 구상하는 것보다, 해당 문제에 맞는 **디자인 패턴을 참고하여 적용하는 것이 훨씬 효율적**임
- **유연성:** 패턴은 고정된 것이 아니라, 특정 요구사항을 반영하여 변형하거나 유사한 형태의 다른 패턴으로 변화될 수 있음
- **구성 요소:** 디자인 패턴은 문제 및 배경, 실제 적용 사례, 재사용 가능한 샘플 코드 등으로 구성됨
- **GoF의 위상:** 수많은 패턴 중 **가장 일반적인 사례**에 적용될 수 있는 것들을 분류한 것으로, 현재까지도 현업에서 가장 많이 사용됨

## 065. 디자인 패턴 사용의 장·단점

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 소프트웨어 설계 시 디자인 패턴을 도입했을 때 얻을 수 있는 이익과 감수해야 할 단점
- **[2] 핵심 키워드:** 구조 파악 용이, 생산성 향상, 의사소통 원활, **초기 투자 비용 부담**, **객체지향 전용**
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 디자인 패턴 기초
- **[4] 시험 포인트:**
    - **장점:** 범용적인 코딩 스타일로 **구조 파악이 쉽고**, 개발자 간의 **의사소통이 원활**해지며, 검증된 구조의 **재사용**으로 시간과 비용이 절약됨
    - **단점(빈출):** 패턴을 익히고 적용하는 데 드는 **'초기 투자 비용'이 부담될 수 있음**
    - **제약:** **객체지향(Object-Oriented)** 기반의 개발에는 적합하지만, 다른 기반의 애플리케이션 개발에는 적합하지 않음
- **[5] 한 문장 설명:** 디자인 패턴은 의사소통, 구조 파악, 재사용성 면에서 유리하여 생산성을 높여주지만, 초기 투자 비용이 들고 객체지향 외의 개발에는 부적합할 수 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **범용성(Universality):** 나만 아는 코드가 아니라 '범용적인 코딩 스타일'을 따르기 때문에, 다른 개발자가 내 코드를 보더라도 **구조를 빨리 파악**할 수 있음
- **유연성(Flexibility):** 설계 변경 요청이 들어왔을 때 유연하게 대처할 수 있는 구조를 제공함
- **비용의 양면성:**
    - **절약:** 이미 검증된 구조를 가져다 쓰므로 시행착오를 줄여 **전체 개발 비용은 절약**됨
    - **부담:** 하지만 패턴 자체를 학습하고 설계에 적용하기 위한 **초기 진입 장벽(비용)**은 존재함

## 066. 생성 패턴 (Creational Pattern)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 객체의 **생성**과 관련된 패턴으로, 객체의 생성과 참조 과정을 **캡슐화**하여 프로그램의 구조가 변경되어도 영향을 크게 받지 않도록 유연성을 더해주는 기법
- **[2] 핵심 키워드:** 생성 캡슐화, 유연성, 5가지 패턴(추상 팩토리, 빌더, 팩토리 메소드, 프로토타입, 싱글톤)
- **[3] 구조 / 관점 / 분류:** 디자인 패턴 - 생성 패턴 (총 5개)
- **[4] 시험 포인트:** 5가지 패턴의 **'핵심 정의'**와 **'별칭'**을 연결하는 문제가 출제됨.
    - **추상 팩토리:** **'서로 연관·의존하는 객체들의 그룹'**을 생성함
    - **빌더:** **'생성 과정과 표현 방법을 분리'**하여 동일한 생성 절차로 서로 다른 결과를 만듦
    - **팩토리 메소드:** 객체 생성을 **'서브 클래스'**가 담당하도록 함 (**가상 생성자**라고도 불림)
    - **프로토타입:** **'원본 객체를 복제(Clone)'**하는 방법
    - **싱글톤:** 인스턴스가 **'하나뿐임'**을 보장함
- **[5] 한 문장 설명:** 객체 생성 과정을 캡슐화하여 유연성을 높이는 패턴으로, 추상 팩토리(그룹), 빌더(과정 분리), 팩토리 메소드(서브 클래스), 프로토타입(복제), 싱글톤(단일)이 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **추상 팩토리 (Abstract Factory):** 구체적인 클래스에 의존하지 않고, 인터페이스를 통해 연관된 서브 클래스들을 묶어 한 번에 교체할 수 있음
- **빌더 (Builder):** 작게 분리된 인스턴스를 건축하듯 조합하여 객체를 생성함. 생성 과정이 분리되어 있어 같은 절차라도 구성요소에 따라 다른 객체가 만들어질 수 있음
- **팩토리 메소드 (Factory Method):** 상위 클래스에서는 인터페이스만 정의하고, 실제 생성은 서브 클래스가 처리하도록 분리하여 캡슐화한 패턴 (**Virtual Constructor**라고도 함)
- **프로토타입 (Prototype):** 비용이 큰 경우 주로 이용하며, 일반적인 생성 방식 대신 원본 객체를 복제하여 생성함
- **싱글톤 (Singleton):** 클래스 내에서 인스턴스가 오직 하나만 생성되도록 하며, 어디서든 참조할 수 있지만 불필요한 메모리 낭비를 최소화할 수 있음

## 067. 구조 패턴 (Structural Pattern)

### 구조 패턴 (Structural Patterns)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 클래스나 객체들을 조합하여 **더 큰 구조**로 만들 수 있게 해주는 패턴으로, 복잡한 시스템 개발을 쉽게 도와줌
- **[2] 핵심 키워드:** 구조 조합, 인터페이스 변환, 기능 확장, 메모리 절약, 7가지 패턴(어댑터, 브리지, 컴포지트, 데코레이터, 퍼싸드, 플라이웨이트, 프록시)
- **[3] 구조 / 관점 / 분류:** 디자인 패턴 - 구조 패턴 (총 7개)
- **[4] 시험 포인트:** 각 패턴의 **핵심 기능**과 **사용 목적**을 연결하는 문제가 출제됨.
    - **어댑터:** **인터페이스가 일치하지 않을 때** 변환하여 사용
    - **브리지:** **구현부에서 추상층을 분리**하여 독립적으로 확장
    - **컴포지트:** **트리 구조**, 복합 객체와 단일 객체를 구분 없이 다룸
    - **데코레이터:** 객체 간의 결합을 통해 **능동적으로(동적으로) 기능을 확장**
    - **퍼싸드:** 복잡한 서브 클래스들을 피해 **상위에 통합 인터페이스** 구성 (Wrapper 객체 필요)
    - **플라이웨이트:** 인스턴스를 매번 생성하지 않고 **공유(Sharing)하여 메모리 절약**
    - **프록시:** 접근이 어려운 객체와 연결하려는 객체 사이에서 **인터페이스(대리) 역할** 수행
- **[5] 한 문장 설명:** 클래스나 객체를 조합해 더 큰 구조를 만드는 패턴으로, 인터페이스 변환(어댑터), 기능 확장(데코레이터), 메모리 절약(플라이웨이트) 등의 목적에 따라 사용된다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **어댑터 (Adapter):** 호환성이 없는 클래스의 인터페이스를 다른 클래스가 이용할 수 있도록 **변환**해줌. 기존 클래스를 재사용하고 싶지만 인터페이스가 다를 때 유용함
- **브리지 (Bridge):** 기능과 구현을 두 개의 별도 클래스로 구현하여, 서로가 **독립적으로 확장**할 수 있도록 구성함
- **컴포지트 (Composite):** 객체들을 **트리 구조**로 구성하여, 디렉터리 안에 파일과 또 다른 디렉터리가 있듯이 복합 객체 안에 복합 객체가 포함되는 구조를 구현함
- **데코레이터 (Decorator):** 임의의 객체에 부가적인 기능을 추가하기 위해 다른 객체들을 **덧붙이는 방식**으로 구현함
- **퍼싸드 (Facade):** 서브 클래스들의 기능을 간편하게 사용할 수 있도록 **통합 인터페이스**를 제공하는 Wrapper 객체를 활용함
- **플라이웨이트 (Flyweight):** 다수의 유사 객체를 생성하거나 조작할 때 유용하며, 가능한 한 **객체를 공유**하여 메모리 낭비를 막음
- **프록시 (Proxy):** 네트워크 연결이나 메모리 대용량 객체 등 접근이 복잡한 객체에 대해 **대신 접근**해주는 역할을 수행함

## 068. 행위 패턴 (Behavioral Pattern)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 클래스나 객체들이 서로 **상호작용**하는 방법이나 **책임 분배** 방법을 정의하는 패턴으로, 총 11개의 패턴이 있음
- **[2] 핵심 키워드:** 상호작용, 책임 분배, 결합도 최소화, 11가지 패턴(책임 연쇄, 커맨드, 인터프리터, 반복자, 중재자, 메멘토, 옵서버, 상태, 전략, 템플릿 메소드, 방문자)
- **[3] 구조 / 관점 / 분류:** 디자인 패턴 - 행위 패턴 (총 11개)
- **[4] 시험 포인트:** 각 패턴의 **핵심 기능**과 **대표 예시**를 연결하는 문제가 빈출됨.
    - **책임 연쇄:** 요청을 처리할 수 있는 객체가 둘 이상일 때, **고리(Chain)**를 따라 책임을 넘김
    - **커맨드:** 요청을 **객체로 캡슐화**하여 로그 남기기, 취소(Undo) 등에 사용
    - **인터프리터:** **언어 문법** 정의 (SQL, 프로토콜 개발)
    - **반복자:** 접근이 잦은 객체에 대해 **순차적 접근** 지원
    - **중재자:** 복잡한 상호작용을 캡슐화하여 **통제 및 지시** 역할 수행 (M:N 관계를 단순화)
    - **메멘토:** 특정 시점의 상태를 저장하여 **되돌리기(Undo/Ctrl+Z)** 기능 구현
    - **옵서버:** 한 객체의 상태 변화를 상속된 다른 객체들에게 **전파(알림)**. **발행/수신(Publish/Subscribe)** 모델
    - **상태:** 객체 상태에 따라 **동일한 동작을 다르게 처리**
    - **전략:** 알고리즘을 캡슐화하여 **상호 교환** 가능하게 함
    - **템플릿 메소드:** 상위 클래스는 **골격(구조)** 정의, 하위 클래스는 세부 처리 구체화
    - **방문자:** 처리 기능을 분리하여 각 클래스를 **방문(Visit)**하며 수행
- **[5] 한 문장 설명:** 객체 간의 상호작용과 책임 분배를 정의하는 11가지 패턴으로, 책임 연쇄, 옵서버(알림), 전략(알고리즘 교체), 템플릿 메소드(골격 정의) 등이 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **책임 연쇄 (Chain of Responsibility):** 내가 처리 못하면 다음 사람에게 넘기는 방식. 요청이 해결될 때까지 연결된 고리를 따라 이동함
- **커맨드 (Command):** 요청 내역을 객체로 저장해두므로 나중에 '실행 취소'하거나 '로그'를 확인하기 좋음. 명령어들을 추상/구체 클래스로 분리함
- **인터프리터 (Interpreter):** 구문 해석이 필요한 경우 사용됨
- **반복자 (Iterator):** 내부 구조를 노출하지 않고도 집합 객체 안의 원소들에 순서대로 접근할 수 있게 해줌
- **중재자 (Mediator):** 객체들끼리 직접 대화하게 하면 너무 복잡해지니, 중간에 '중재자'를 두어 의존성을 줄이고 결합도를 낮춤
- **메멘토 (Memento):** 객체의 내부 상태를 스냅샷 찍듯이 저장해 두었다가, 필요할 때 그 시점으로 복원함
- **옵서버 (Observer):** 분산 시스템에서 이벤트 발생 시 이를 구독하고 있는 다른 객체들에게 자동으로 알려줌
- **상태 (State):** 객체의 상태(State)를 캡슐화하고 이를 참조하게 하여, 상태가 바뀌면 행동도 바뀌도록 함
- **전략 (Strategy):** 클라이언트는 어떤 전략(알고리즘)을 쓰는지 상관없이 독립적으로 알고리즘을 바꿔 낄 수 있음
- **템플릿 메소드 (Template Method):** 전체적인 흐름은 부모가 잡고, 구체적인 내용은 자식이 채워넣게 하여 코드 중복을 줄임
- **방문자 (Visitor):** 데이터 구조와 처리 기능을 분리하고 싶을 때 사용하며, 처리 기능이 각 클래스를 돌아다니며 작업을 수행함

### 069-2.시스템 인터페이스 요구사항 분석 (System Interface Requirements Analysis)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 요구사항 명세서에서 요구사항을 **기능적 요구사항**과 **비기능적 요구사항**으로 **분류하고 조직화**하여 명세를 구체화하고, 이를 **이해관계자에게 전달**하는 일련의 과정
- **[2] 핵심 키워드:** 분류/조직화, 기능적/비기능적, 구체화, 이해관계자 전달, 우선순위 부여
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 요구사항 분석 프로세스
- **[4] 시험 포인트:**
    - **분류 기준:** 요구사항을 크게 **'기능적(Functional)'**과 **'비기능적(Non-functional)'**으로 나누어 조직화한다는 점이 핵심임
    - **최종 목표:** 단순히 분석하는 것에 그치지 않고, 구체화된 내용을 **'이해관계자에게 전달'**하는 것까지가 분석의 과정임
- **[5] 한 문장 설명:** 요구사항을 기능/비기능으로 분류하고 조직화하여 명세를 구체화한 뒤, 이해관계자에게 전달하는 과정이다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **분석 기법 적용:** 소프트웨어 요구사항 분석 기법을 적절히 이용하여 수행함
- **세분화 (Decomposition):** 요구사항의 분해가 필요한 경우, 너무 복잡하지 않게 **적절한 수준으로 세분화**해야 함
- **누락 보완:** 분석 시 명세서에 빠져 있는(누락된) 요구사항이나 제한조건이 있다면 이를 **추가**해야 함
- **우선순위 (Priority):** 모든 요구사항이 똑같이 중요한 것은 아니므로, **상대적 중요도**를 평가하여 우선순위를 부여해야 함

### 069-3.시스템 인터페이스 요구사항 분석 절차 (System Interface Requirements Analysis Procedure)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 소프트웨어 요구사항에서 인터페이스 관련 사항을 선별하여, 분류/분석/수정한 뒤 이해관계자에게 전달하는 5단계 절차
- **[2] 핵심 키워드:** 목록 별도 생성, 자료 준비, 기능/비기능 분류, 분석 및 수정, 이해관계자 전달
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 분석 절차 (순서 중요)
- **[4] 시험 포인트:**
    - **절차 순서 (암기):** **선별(목록 작성) → 자료 준비 → 분류(기능/비기능) → 분석 및 수정 → 전달**
    - **분류 기준:** 요구사항 명세서를 확인하여 **'기능적 요구사항'**과 **'비기능적 요구사항'**으로 나눈다는 점이 핵심
- **[5] 한 문장 설명:** 전체 요구사항에서 인터페이스 관련만 뽑아 목록을 만들고, 관련 자료를 준비해 기능/비기능으로 분류한 뒤, 내용을 분석/수정하여 이해관계자에게 전달한다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **단계별 상세 내용:**
    1. **목록 작성:** 소프트웨어 요구사항 목록에서 시스템 인터페이스 관련 요구사항만 선별하여 **별도로 목록**을 만듦
    2. **자료 준비:** 아키텍처 정의서, 현행 시스템의 대·내외 연계 시스템 현황 자료 등 **관련 자료**를 준비함
    3. **분류:** 시스템 인터페이스 요구사항 명세서를 확인하여 **기능적(Functional)** 요구사항과 **비기능적(Non-functional)** 요구사항으로 분류함
    4. **분석 및 수정:** 명세서와 목록, 기타 관련 자료들을 **비교**하여 요구사항을 분석하고, 내용을 **추가하거나 수정**함
    5. **전달:** 추가·수정된 명세서와 목록을 관련 **이해관계자에게 전달**하여 공유함

**69-3. 요구사항 검증 (Requirements Verification)**

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 인터페이스의 설계 및 구현 **전에** 사용자의 요구사항이 명세서에 **정확하고 완전하게** 기술되었는지 검토하고, 개발 범위의 기준인 **베이스라인(Baseline)**을 설정하는 것
- **[2] 핵심 키워드:** 설계/구현 전, 정확성/완전성 검토, 베이스라인 설정, 비용 절감
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 요구사항 관리 및 검증
- **[4] 시험 포인트:**
    - **시점(Timing):** 반드시 **'설계 및 구현 전(Before)'**에 수행해야 함. 나중에 하면 늦음.
    - **목적:** 개발의 기준선이 되는 **'베이스라인(Baseline)'**을 확정하는 것
    - **순서:** **계획 수립 → 검토 및 오류 수정 → 베이스라인 설정**
- **[5] 한 문장 설명:** 설계/구현 전에 요구사항 명세서의 정확성을 검토하여 오류 수정 비용을 줄이고, 개발 기준인 베이스라인을 설정하는 과정이다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **필요성 (비용):**
    - 설계나 구현 중에 명세서 오류가 발견되면 수정 비용이 많이 듦.
    - 따라서 프로젝트 **초기 단계**에서 철저한 검증이 필수적임
- **수행 절차 상세:**
    1. **계획 수립:** 검토 방법과 일정을 짬
    2. **검토 및 수정:** 명세서를 확인하고 오류를 고침
    3. **베이스라인 설정:** 수정된 명세서를 최종 승인하고 기준선으로 삼음

### 069-4. 인터페이스 요구사항 검토 계획 수립 (Establishment of Interface Requirements Review Plan)

    - **체크리스트 항목:** **완전성, 일관성, 명확성** 등을 점검할 수 있는 리스트를 작성함
- **[5] 한 문장 설명:** 품질 관리 계획을 바탕으로 검토 기준, 참여자, 체크리스트(완전성/일관성 등), 일정 등을 정의하여 검토 계획을 수립하는 단계다.

    - **검토 기준 및 방법:** 프로젝트의 **규모, 참여 인력, 검토 기간** 등을 고려하여 어떻게 검토할지 정함
    - **참여자:** 프로젝트 규모에 따라 PM, 품질 관리자(QA), 인터페이스 분석가, 아키텍트, 사용자, 테스트 관리자 등을 선정함
    - **체크리스트 (Checklist):** 요구사항의 **완전성(Completeness), 일관성(Consistency), 명확성(Clarity)** 등을 객관적으로 점검하기 위해 작성함
    - **관련 자료:** 인터페이스 요구사항 목록 및 명세서, 현행 및 표준 시스템 구성도 등 검토에 필요한 자료를 미리 준비함
    - **일정:** 언제 검토할지 일정을 정함

### 069-5. 인터페이스 요구사항 검토 및 오류 수정 (Review and Error Correction of Interface Requirements)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 검토 체크리스트의 항목에 따라 인터페이스 요구사항 명세서를 **검토**하고, 오류 발생 시 수정하는 과정
- **[2] 핵심 키워드:** 체크리스트 기반 검토, **오류 목록**, **시정 조치서**, 시정 조치 완료 확인
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 요구사항 검증 절차 (2단계: 실행 및 조치)
- **[4] 시험 포인트:**
    - **오류 발견 시 조치:** 오류가 발견되면 **'오류 목록'**과 **'시정 조치서'**를 작성해야 한다는 점이 핵심
    - **완료 시점:** 시정 조치서를 작성한 경우, 단순히 작성에서 끝나는 것이 아니라 **'시정 조치가 완료되었는지 확인'**한 후에야 비로소 검토 작업이 완료됨
- **[5] 한 문장 설명:** 체크리스트를 기반으로 명세서를 검토하고, 오류 발견 시 오류 목록과 시정 조치서를 작성하여 수정하며, 조치가 완료되었는지 확인하여 작업을 마무리한다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **프로세스 상세:**
    1. **검토 수행:** 준비된 체크리스트를 보며 명세서를 하나하나 뜯어봄
    2. **문서화:** 문제가 보이면 말로만 하는 게 아니라 **오류 목록**과 **시정 조치서**라는 공식 문서를 만듦
    3. **전달 및 수정:** 검토 결과를 관련자들에게 전달하여 수정을 요청하고 승인 절차를 진행함
    4. **최종 확인:** 수정했다고 보고가 오면 진짜로 고쳐졌는지(시정 조치 완료 여부) 확인하고 끝냄

### 069-6. 인터페이스 요구사항 베이스라인 설정 (Interface Requirements Baseline Establishment)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 검토를 통해 검증된 인터페이스 요구사항을 **프로젝트 관리자(PM)**와 **주요 의사 결정자**에게 **공식적으로 승인** 받는 단계
- **[2] 핵심 키워드:** 공식적 승인, 프로젝트 관리자/의사 결정자, 설계 및 구현의 기준, 베이스라인
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 요구사항 검증 절차 (3단계: 최종 단계)
- **[4] 시험 포인트:**
    - **승인 주체:** 누구에게 승인받는가? → **'프로젝트 관리자(PM)'**와 **'주요 의사 결정자'**
    - **목적:** 소프트웨어 **설계 및 구현**을 시작하기 위한 기준선(**베이스라인**)을 설정하기 위함
    - **절차 순서 (마지막):** 요구사항 검토 계획 수립 → 검토 및 오류 수정 → **베이스라인 설정** (이 순서의 마지막 단계임)
- **[5] 한 문장 설명:** 검증된 요구사항을 프로젝트 관리자와 의사 결정자에게 공식 승인받아, 설계와 구현의 기준이 되는 베이스라인을 설정하는 최종 단계이다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **베이스라인(Baseline)의 의미:**
    - 이제 요구사항 분석이 끝났으니, 이 내용을 **'기준'**으로 삼아 다음 단계(설계/개발)로 넘어가자는 약속임
    - 베이스라인이 설정되면 이후에는 요구사항을 함부로 바꿀 수 없으며, 변경 시에는 공식적인 변경 관리 절차를 따라야 함.
- **흐름 정리:**
    1. 계획을 세우고 (Plan)
    2. 검토해서 오류를 고치고 (Do/Check)
    3. **최종적으로 도장(승인)을 찍는 단계 (Act/Baseline)**

## 069-8. 요구사항 검증 방법 (Requirement Validation)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 인터페이스 요구사항의 결함을 찾기 위해 수작업 검토뿐만 아니라 **견본품 제작, 테스트 설계, 자동화 도구** 등을 활용하는 방법
- **[2] 핵심 키워드:** 동료검토/워크스루/인스펙션(수작업), **프로토타이핑(견본)**, **테스트 설계(테스트 케이스)**, **CASE 도구(일관성 분석)**
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 검증 기법의 다양화
- **[4] 시험 포인트:**
    - **검토 기법 3대장 (재확인):**
        - **동료검토:** 작성자가 직접 설명
        - **워크스루:** 미리 배포 + 짧은 회의
        - **인스펙션:** 작성자 제외한 전문가
    - **프로토타이핑 (Prototyping):** 실제 개발될 소프트웨어의 **'견본(Prototype)'**을 만들어 최종 결과물을 예측하고 요구사항을 정확히 파악함
    - **테스트 설계 (Test Design):** **'테스트 케이스(Test Case)'**를 생성하여 요구사항이 현실적으로 **테스트 가능한지(Testable)** 검토함
    - **CASE 도구 활용:** 컴퓨터 보조 도구를 사용하여 **일관성 분석(Consistency Analysis)** 등을 수행하고 변경사항을 추적/관리함
- **[5] 한 문장 설명:** 요구사항 검증은 수작업 검토(동료검토, 워크스루, 인스펙션) 외에도 견본을 만드는 프로토타이핑, 테스트 가능성을 보는 테스트 설계, 자동화 도구인 CASE를 활용한다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **프로토타이핑의 목적:** 사용자들은 완성된 것을 보기 전까지는 본인이 뭘 원하는지 모르는 경우가 많음. 따라서 "이런 식으로 만들어질 겁니다"라고 **미리 보여줘서** 피드백을 받기 위함
- **테스트 설계의 의의:** "이 요구사항을 어떻게 테스트할 것인가?"를 고민하다 보면, 요구사항 자체가 모호하거나 비현실적인 경우를 발견할 수 있음 (역검증 효과)
- **CASE (Computer Aided Software Engineering) 도구:** 사람이 일일이 찾기 힘든 논리적 오류나 **일관성(모순 여부)**을 소프트웨어가 자동으로 분석해줌

### 069-8.인터페이스 요구사항 검증의 주요 항목 (Key Items for Interface Requirements Verification)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 인터페이스 요구사항 검증 시 점검해야 할 7가지 주요 품질 기준(항목)
- **[2] 핵심 키워드:** 완전성, 일관성, 명확성, 기능성(What>How), 검증 가능성, 추적 가능성, 변경 용이성
- **[3] 구조 / 관점 / 분류:** 소프트웨어 공학 - 요구사항 품질 속성
- **[4] 시험 포인트:** 각 항목의 **정의**를 묻는 문제가 출제됨. 특히 '기능성'과 '추적 가능성'이 중요함.
    - **완전성 (Completeness):** 누락되지 않고 **완전하게 반영**되었는가?
    - **일관성 (Consistency):** **모순되거나 충돌**되는 점이 없는가?
    - **기능성 (Functionality):** '어떻게(How to)'보다 **'무엇을(What)'**에 중점을 두고 있는가? (이게 빈출 함정)
    - **추적 가능성 (Traceability):** 명세서와 설계서를 **연결(추적)**할 수 있는가?
- **[5] 한 문장 설명:** 요구사항 검증은 완전성, 일관성, 명확성, 기능성(What 중점), 검증 가능성, 추적 가능성, 변경 용이성 등 7가지 항목을 기준으로 수행된다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **명확성 (Unambiguity):** 모든 참여자가 요구사항을 **명확히(똑같이) 이해**할 수 있어야 함. (중의적 표현 금지)
- **검증 가능성 (Verifiability):** 요구사항이 충족되었는지 **테스트(검증)가 가능**해야 함. (예: "빠르게 처리한다"는 검증 불가, "1초 내 처리한다"는 검증 가능)
- **변경 용이성 (Easily Changeable):** 나중에 요구사항이 바뀌더라도 명세서의 **변경이 쉽도록** 작성되어야 함

### 070-1.인터페이스 통신 유형 (Interface Communication Types)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 개발할 시스템과 내·외부 시스템 간에 데이터를 **송·수신하는 형태**를 의미함
- **[2] 핵심 키워드:** 단방향(응답X), 동기(대기), 비동기(다른 작업 수행), Request-Reply, Publish-Subscribe
- **[3] 구조 / 관점 / 분류:** 시스템 통합 - 데이터 통신 방식
- **[4] 시험 포인트:** 각 유형의 **'응답 대기 여부'**와 **'동작 방식'**을 구분하는 문제가 출제됨.
    - **단방향 (Unidirectional):** 시스템에서 거래를 요청만 하고 **응답이 없는** 방식
    - **동기 (Synchronous):** 시스템에서 거래를 요청하고 응답이 올 때까지 **대기(Waiting)**하는 방식 (**Request-Reply**)
    - **비동기 (Asynchronous):** 거래를 요청하고 **다른 작업을 수행**하다가 응답이 오면 처리하는 방식 (**Send-Receive, Publish-Subscribe** 등)
- **[5] 한 문장 설명:** 통신 유형에는 요청 후 응답이 없는 단방향, 응답 올 때까지 기다리는 동기, 기다리지 않고 다른 일을 하는 비동기 방식이 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **동기 (Synchronous):**
    - 전화 통화와 비슷함. 내가 말하고 상대방이 대답할 때까지 기다려야 다음 말을 할 수 있음.
    - 데이터의 정합성을 맞추기 좋지만, 응답이 늦어지면 시스템 전체가 느려질 수 있음
- **비동기 (Asynchronous):**
    - 이메일이나 메신저와 비슷함. 보낸 뒤에 다른 일을 하다가 답장이 오면 그때 확인하면 됨.
    - 시스템 자원을 효율적으로 쓸 수 있음.
    - **세부 방식:** Send-Receive, Send-Receive-Acknowledge, **Publish-Subscribe(구독형)** 등이 포함됨

### 070-2. 인터페이스 처리 유형 (Interface Processing Types)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 송·수신 데이터를 어떤 형태로 처리할 것인지에 대한 **방식**을 의미함
- **[2] 핵심 키워드:** 업무 성격, 전송량, 실시간, 지연 처리(비용 절감), 배치(대량)
- **[3] 구조 / 관점 / 분류:** 시스템 통합 - 데이터 처리 방식
- **[4] 시험 포인트:** 업무 성격과 데이터 양에 따라 3가지를 구분하는 문제가 출제됨.
    - **실시간 방식 (Real-time):** 사용자가 요청한 내용을 **'바로(즉시)'** 처리해야 할 때 사용
    - **지연 처리 방식 (Deferred):** 데이터를 매 건 단위로 즉시 처리할 경우 **'비용이 많이 발생'**할 때, 이를 모아서 나중에 처리하는 방식
    - **배치 방식 (Batch):** **'대량의 데이터'**를 한 번에(일괄적으로) 처리할 때 사용
- **[5] 한 문장 설명:** 인터페이스 처리는 업무 성격과 데이터 양에 따라 즉시 처리하는 실시간, 비용 절감을 위한 지연 처리, 대용량 처리를 위한 배치 방식으로 나뉜다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **구분 기준:** 단순히 빠르냐 느리냐가 아니라, **'업무의 성격'**과 **'데이터 전송량'**을 고려하여 결정함
- **상세 비교:**
    - **실시간:** 조회, 예매 등 즉각적인 반응이 필요한 경우 (응답 속도 중요).
    - **지연 처리:** 통신 비용이나 시스템 부하 비용이 비쌀 때, 급하지 않은 건을 잠시 미뤘다가 처리함 (효율성 중요).
    - **배치:** 정산, 마감 등 쌓여있는 데이터를 한꺼번에 돌릴 때 사용 (대용량 처리 최적화).

### 070-2. 인터페이스 발생 주기 (Interface Frequency)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 개발할 시스템과 내·외부 시스템 간에 송·수신 데이터가 전송되어 **인터페이스가 사용되는 주기**를 의미함
- **[2] 핵심 키워드:** 송·수신 데이터 전송, 사용 주기, 업무 성격/전송량 고려, 매일/수시/주 1회

- **[4] 시험 포인트:**
    - **고려 요소:** 주기를 결정할 때는 **'업무의 성격'**과 **'송·수신 데이터 전송량'**을 고려해야 함
    - **구분 예시:** **매일(Daily)**, **수시(Frequent/Ad-hoc)**, **주 1회(Weekly)** 등으로 구분됨
- **[5] 한 문장 설명:** 인터페이스가 사용되는 주기를 말하며, 업무 성격과 데이터 양에 따라 매일, 수시, 주 1회 등으로 설정한다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **실무적 의미:**
    - **수시(Ad-hoc):** 실시간 처리가 필요하거나 이벤트가 발생할 때마다 즉시 전송하는 경우.
    - **매일/주 1회:** 배치(Batch) 작업처럼 데이터를 모아서 정기적으로 전송하는 경우.

- **[5] 한 문장 설명:** 아키텍처 정의서를 기반으로 각 인터페이스의 연계 방식, 통신 및 처리 유형, 주기 등을 구체적으로 정의하여 문서화하는 과정이다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

### 070-4. 송·수신 데이터 명세화 (Specification of Transmission/Reception Data)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 내·외부 인터페이스 목록에 있는 각각의 인터페이스에 대해, 인터페이스 시 필요한 **송·수신 데이터**에 대한 명세를 작성하는 것
- **[2] 핵심 키워드:** 테이블/파일 단위, 데이터 명세, 필드(Field)/타입(Type)/사이즈(Size), **암호화(Condition)**
- **[3] 구조 / 관점 / 분류:** 시스템 통합 - 상세 데이터 설계
- **[4] 시험 포인트:**
    - **작성 단위:** 인터페이스별로 **'테이블 정의서'**와 **'파일 레이아웃'**에서 연계하고자 하는 **테이블 또는 파일 단위**로 작성함
    - **구성 항목 (예시 표):** 인터페이스 ID, 송수신 구분, 시스템명, 데이터 항목(**필드명, 타입, 사이즈, Null 허용 여부, 설명, 조건**) 등을 상세히 기술해야 함
    - **보안 사항:** 주민번호(SSN), 이름(NAME) 등 민감한 개인정보는 조건(Condition) 항목에 **'암호화'** 처리를 명시해야 함
- **[5] 한 문장 설명:** 인터페이스별로 전송되는 데이터를 테이블이나 파일 단위로 상세히 정의하는 과정으로, 필드명, 타입, 사이즈 및 암호화 여부 등을 명세화한다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **명세화의 목적:** 단순히 "데이터를 보낸다"가 아니라, "어떤 컬럼을, 몇 글자 크기로, 어떤 보안 처리를 해서 보낼지"를 개발자가 코드로 짤 수 있게 확정하는 단계임.
- **작성 예시 분석 (이미지 표 - IFID-006):**
    - **업무:** 고객 정보 관리 / **서비스명:** 고객 정보 저장
    - **데이터 항목 상세:**
        - **CON_NO (고객번호):** Key값(Y), Varchar(13), Null 불가(N)
        - **SSN (주민번호):** Char(13), **암호화** 필수
        - **NAME (이름):** Char(10), **암호화** 필수
    - 이처럼 개인정보 보호법 등에 따라 **암호화**가 필요한 필드는 명세서 단계에서부터 확실히 정의해두어야 함.

### 070-4. 오류 식별 및 처리 방안 명세화 (Error Identification & Processing Specification)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 내·외부 인터페이스 목록에 있는 각각의 인터페이스에 대해, 인터페이스 시 발생할 수 있는 **오류를 식별**하고 이에 대한 **처리 방안**을 문서화(명세)하는 것
- **[2] 핵심 키워드:** 오류 식별, 처리 방안, 송신/수신/연계서버 오류, **오류 코드/메시지/해결방법**
- **[3] 구조 / 관점 / 분류:** 시스템 통합 - 예외 처리 설계
- **[4] 시험 포인트:**
    - **오류 발생 지점:** 오류는 **송신 시스템**, **연계 서버**, **수신 시스템** 어디서든 발생할 수 있음을 인지해야 함 (이미지 도해 참조)
    - **명세 항목:** 오류 상황에 대해 **오류 코드, 오류 메시지, 설명, 해결 방법** 등을 구체적으로 명세화해야 함
- **[5] 한 문장 설명:** 인터페이스 도중 송신/수신/연계 서버에서 발생할 수 있는 오류를 식별하고, 이에 대한 코드, 메시지, 해결 방법 등을 구체적으로 정의하는 과정이다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **발생 가능한 오류 유형:** 시스템 및 전송 오류, 연계 프로그램 내의 예외(Exception) 상황 등 다양함
- **실제 명세 예시 (테이블 분석):**
    - **네트워크 오류 (ES10001):** "연계 서버에 접속할 수 없음" → 원인: 네트워크 회선 오류 → 해결: 회선 확인 후 조치
    - **데이터 변환 오류 (ES50001):** "연계 서버에서 데이터 변환 에러" → 원인: 유효하지 않은 코드값으로 인한 매핑 실패 → 해결: 미등록 코드를 매핑 정의서에 등록 후 재실행
    - **DB 조회 오류 (SD40001):** "송신 시스템에서 데이터 조회 실패" → 원인: DB 권한 문제나 테이블 삭제 등 → 해결: 권한 및 작동 여부 확인 후 재실행
- **시사점:** 단순히 "에러 났다"고 끝내는 게 아니라, **'어디서(Where)', '왜(Why)', '어떻게(How)'** 해결할지를 미리 코드로 정의해두어야 운영 시 빠른 대응이 가능함.

## 072. 미들웨어 (Middleware)

### TẦNG A – NOTE NÉN (ÔN / ĐI THI)

- 개념: 운영체제와 응용 프로그램 사이에서 서비스를 제공하는 소프트웨어
- 핵심 키워드: RPC, MOM, TP-Monitor, ORB, WAS
- 구조 / 관점 / 분류: 데이터베이스, 메시지 지향, 트랜잭션 처리, 웹 애플리케이션 등 용도별 분류
- 시험 포인트: MOM(비동기 메시지 전달)과 TP-Monitor(항공/철도 예약 등 트랜잭션 감시) 구분
- 한 문장 설명: 미들웨어는 분산 컴퓨팅 환경에서 서로 다른 기종 간의 원활한 통신을 지원한다.
- 연관 설명: 014

### TẦNG B – NOTE 보충 (HIỂU SÂU)

- RPC(Remote Procedure Call): 원격 프로시저를 마치 로컬 프로시저처럼 호출하는 방식
- MOM(Message Oriented Middleware): 메시지 기반 비동기 전달 방식, 이기종 간 데이터 동기화에 적합
- TP-Monitor: 온라인 트랜잭션 업무에서 빠른 응답 속도를 유지하고 처리를 감시하는 소프트웨어
- ORB(Object Request Broker): 코바(CORBA) 표준 스펙을 구현한 객체 지향 미들웨어
- WAS(Web Application Server): 웹 환경에서 동적인 콘텐츠를 처리하기 위해 주로 사용됨

### 072-1.DB (DataBase) - Middleware

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 데이터베이스 벤더(Vendor)에서 제공하는 클라이언트(Client)를 통해 원격의 데이터베이스와 연결하기 위한 **미들웨어**
- **[2] 핵심 키워드:** 벤더 제공 클라이언트, 원격 연결, **2-Tier 아키텍처**, **ODBC/IDAPI/Glue**
- **[3] 구조 / 관점 / 분류:** 미들웨어 - 데이터베이스 연계
- **[4] 시험 포인트:**
    - **아키텍처 특징:** DB 미들웨어를 사용하여 시스템을 구축하는 경우, 보통 **'2-Tier 아키텍처'**라고 부름
    - **대표 종류 (암기):**
        - 마이크로소프트의 **ODBC**
        - 볼랜드의 **IDAPI**
        - 오라클의 **Glue**
- **[5] 한 문장 설명:** 벤더가 제공하는 클라이언트를 통해 원격 DB에 연결하는 미들웨어로, 주로 2-Tier 아키텍처를 형성하며 ODBC, IDAPI, Glue 등이 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **2-Tier의 의미:**
    - 클라이언트(사용자 PC)가 미들웨어(ODBC 등)를 통해 데이터베이스 서버(DB Server)에 **직접** 붙는 구조.
    - 중간에 별도의 웹 서버나 애플리케이션 서버가 없는 단순한 구조를 의미함.
- **실무적 관점:** 과거 클라이언트-서버(C/S) 환경에서 많이 쓰였으며, 요즘은 웹 기반(3-Tier 이상)이 많지만 여전히 레거시 시스템이나 특정 솔루션 연동에는 ODBC 등이 필수적으로 사용됨.

### 072-2. RPC (Remote Procedure Call)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 응용 프로그램의 프로시저를 사용하여 **원격(Remote)** 프로시저를 마치 **로컬(Local)** 프로시저처럼 호출하는 방식의 미들웨어
- **[2] 핵심 키워드:** 원격 프로시저, 로컬 프로시저, Entera, ONC/RPC
- **[3] 구조 / 관점 / 분류:** 미들웨어 - 통신 방식
- **[4] 시험 포인트:**
    - **정의:** 원격지의 코드를 내 컴퓨터에 있는 것처럼 실행한다는 개념(**Local**처럼 호출)이 핵심임
    - **대표 종류 (암기):**
        - 이큐브시스템스의 **Entera**
        - OSF의 **ONC/RPC**
- **[5] 한 문장 설명:** RPC는 원격 프로시저를 로컬 프로시저처럼 호출할 수 있게 해주는 미들웨어로, Entera와 ONC/RPC 등이 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **투명성 (Transparency):** 프로그래머 입장에서는 네트워크 통신의 복잡한 과정을 몰라도, 그냥 함수(프로시저)를 호출하듯이 코드를 짜면 되므로 개발이 편리함. "원격에 있지만 마치 내 곁(로컬)에 있는 것처럼 느껴짐".
- **역사:** 분산 컴퓨팅 환경에서 가장 기본이 되는 기술 중 하나임.

### 072-3.MOM (Message Oriented Middleware)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 메시지 기반의 **비동기형 메시지**를 전달하는 방식의 미들웨어
- **[2] 핵심 키워드:** 메시지 기반, **비동기형(Asynchronous)**, 이기종 분산 데이터 시스템, **데이터 동기**, IBM MQ, JMS
- **[3] 구조 / 관점 / 분류:** 미들웨어 - 메시지 전송 방식
- **[4] 시험 포인트:**
    - **동작 방식:** **'비동기형(Asynchronous)'** 메시지 전달 방식이라는 점이 가장 중요함 (즉각적인 응답을 기다리지 않음)
    - **주요 용도:** 즉시 처리가 필요한 온라인 업무보다는, 서로 다른 기종(**이기종**)의 분산 데이터 시스템 간의 **'데이터 동기(Data Synchronization)'**를 위해 많이 사용됨
    - **대표 종류 (암기):**
        - IBM의 **MQ**
        - 오라클의 **Message Q**
        - JCP의 **JMS** (Java Message Service)
- **[5] 한 문장 설명:** MOM은 메시지 기반의 비동기형 미들웨어로, 주로 이기종 분산 시스템 간의 데이터 동기에 사용되며 IBM MQ, JMS 등이 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **비동기(Asynchronous)의 장점:**
    - 메시지를 보내는 쪽(Sender)은 받는 쪽(Receiver)이 지금 당장 받을 준비가 되어 있는지 신경 쓰지 않고 메시지를 큐(Queue)에 던져놓고 자기 할 일을 하면 됨.
    - 시스템 간의 **결합도(Coupling)**를 낮춰주며, 한쪽 시스템이 잠시 멈춰 있어도 데이터가 유실되지 않고 나중에 처리될 수 있음.
- **이기종 시스템 연동:** 리눅스 서버와 윈도우 서버, 혹은 메인프레임 등 서로 다른 환경의 시스템끼리 데이터를 주고받을 때 표준적인 메시지 포맷을 사용하여 원활하게 연결해줌.

### 073-4.TP-Monitor (Transaction Processing Monitor)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 항공기나 철도 예약 업무 등과 같이 트랜잭션이 빈번하게 발생하는 **온라인 트랜잭션 업무**에서 트랜잭션을 **처리 및 감시**하는 미들웨어
- **[2] 핵심 키워드:** 트랜잭션 처리/감시, 항공기/철도 예약, **빠른 응답 속도**, tuxedo, tmax
- **[3] 구조 / 관점 / 분류:** 미들웨어 - 트랜잭션 관리
- **[4] 시험 포인트:**
    - **사용 사례 (빈출):** **'항공기나 철도 예약'** 처럼 수많은 사용자가 몰리는 업무에 사용된다는 예시가 자주 나옴
    - **목적:** 사용자 수가 증가하더라도 **'빠른 응답 속도를 유지'**하기 위함
    - **대표 종류 (암기):**
        - 오라클(Oracle)의 **tuxedo**
        - 티맥스소프트(TmaxSoft)의 **tmax**
- **[5] 한 문장 설명:** TP-Monitor는 항공/철도 예약처럼 트랜잭션이 많은 시스템에서 빠른 응답 속도를 유지하며 트랜잭션을 감시/처리하는 미들웨어로, tuxedo와 tmax가 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **트랜잭션(Transaction)이란?:** 데이터베이스의 상태를 변화시키는 하나의 논리적인 작업 단위(예: '결제' 버튼을 눌러서 돈이 빠져나가고 티켓이 발권되는 일련의 과정).
- **왜 필요한가?:** 수만 명이 동시에 "예약" 버튼을 누르면 DB 혼자서는 감당이 안 되어 시스템이 느려지거나 뻗을 수 있음. TP-Monitor는 이 트래픽을 효율적으로 관리(교통정리)하여 시스템이 안정적으로 빠르게 돌아가게 해줌.

### 072-5.ORB (Object Request Broker)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** **객체 지향(Object Oriented)** 미들웨어로, **코바(CORBA)** 표준 스펙을 구현한 미들웨어
- **[2] 핵심 키워드:** 객체 요청 브로커, 객체 지향, **CORBA**, 트랜잭션 처리 추가, Orbix
- **[3] 구조 / 관점 / 분류:** 미들웨어 - 객체 지향 통신
- **[4] 시험 포인트:**
    - **정의 (빈출):** **'코바(CORBA)'**라는 단어가 나오면 무조건 ORB를 떠올려야 함
    - **최근 동향:** 최근 제품들은 TP-Monitor의 장점인 **'트랜잭션 처리'**와 **'모니터링'** 기능까지 추가로 구현하기도 함
    - **대표 종류 (암기):**
        - Micro Focus의 **Orbix**
        - OMG의 **CORBA**
- **[5] 한 문장 설명:** ORB는 CORBA 표준을 구현한 객체 지향 미들웨어로, 최근에는 트랜잭션 처리 기능도 포함하며 Orbix 등이 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **브로커(Broker)의 역할:** 주식 브로커가 매수자와 매도자를 연결해주듯, ORB는 네트워크상에 분산된 **객체(Object)**들이 서로의 위치를 몰라도 투명하게 메시지를 주고받을 수 있게 중개해줌.
- **CORBA (Common Object Request Broker Architecture):** 다양한 언어와 플랫폼에서 작성된 객체들이 서로 통신할 수 있도록 OMG(Object Management Group)에서 정한 표준 규격. ORB는 이 규격을 실제로 구현한 소프트웨어임.

### 072-6.WAS (Web Application Server)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 정적인 콘텐츠를 처리하는 웹 서버와 달리, 사용자의 요구에 따라 변하는 **동적인(Dynamic) 콘텐츠**를 처리하기 위해 사용되는 미들웨어
- **[2] 핵심 키워드:** 동적 콘텐츠, **웹 환경 구현**, HTTP 세션 처리, **미션-크리티컬(Mission-Critical)**, **JAVA/EJB**, WebLogic, WebSphere
- **[3] 구조 / 관점 / 분류:** 미들웨어 - 웹 애플리케이션 실행 환경
- **[4] 시험 포인트:**
    - **웹 서버 vs WAS:** 웹 서버(Apache 등)는 HTML 같은 **'정적'** 파일을 주지만, WAS는 DB 조회나 로직 처리를 통해 만들어진 **'동적'** 결과를 준다는 차이점이 핵심
    - **주요 기능:** 단순 웹 기능뿐만 아니라, **'미션-크리티컬(Mission-Critical)'**한 기업의 중요 업무까지 **JAVA, EJB 컴포넌트** 기반으로 구현 가능함
    - **대표 종류 (암기):**
        - 오라클(Oracle)의 **WebLogic**
        - IBM의 **WebSphere**
- **[5] 한 문장 설명:** WAS는 정적인 웹 서버와 달리 사용자의 요구에 따라 동적인 콘텐츠를 처리하고, 기업의 핵심 업무(미션-크리티컬)를 수행하는 미들웨어로 WebLogic, WebSphere 등이 있다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **정적 vs 동적:**
    - **정적 (Static):** 누가 언제 접속하든 항상 똑같은 화면(예: 회사 소개 페이지).
    - **동적 (Dynamic):** 접속한 사람이나 시간에 따라 다른 화면(예: "안녕하세요, 홍길동님" 마이페이지, 실시간 주식 차트).
- **웹 환경의 주역:** 과거 C/S(Client-Server) 환경에서 **Web 환경**으로 넘어오면서 가장 중요해진 미들웨어임.
- **통합 역할:** 보통 실무에서는 [Web Server(앞단) + WAS(뒷단) + DB] 구조로 구성하여, 정적인 건 앞단에서 빨리 처리하고 복잡한 건 뒷단(WAS)에서 처리하게 함

### 072-7. 미들웨어 솔루션 식별 (Identification of Middleware Solutions)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 개발 및 운영 환경에서 사용될 미들웨어 솔루션을 확인하고 **목록을 작성**하는 것
- **[2] 핵심 키워드:** 아키텍처 구성 정보, 구매 내역 확인, 솔루션 목록(명칭/버전/제조사), 이해관계자 전달/수정
- **[3] 구조 / 관점 / 분류:** 시스템 통합 - 미들웨어 관리
- **[4] 시험 포인트:**
    - **식별 근거:** 무엇을 보고 식별하는가?
        - 소프트웨어 아키텍처에서 정의한 **'아키텍처 구성 정보'**
        - 프로젝트에서 구매 진행 중이거나 예정인 **'소프트웨어 구매 내역'**
    - **목록 구성 항목:** 식별된 솔루션에 대해 **시스템, 구분, 솔루션명, 버전, 제조사** 등의 정보를 정리함
    - **검토:** 작성된 목록은 **'이해관계자'**에게 전달하여 누락이나 오류가 없는지 확인받아야 함
- **[5] 한 문장 설명:** 아키텍처 정의와 구매 내역을 바탕으로 사용될 미들웨어를 식별하여 목록(명칭, 버전 등)을 작성하고, 이해관계자의 검토를 거쳐 확정하는 과정이다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **실무 프로세스:**
    1. **확인:** "우리 시스템 구조(아키텍처)상 웹 서버랑 DB 연결이 필요하네? 그리고 구매팀에서 WebLogic 샀다고 했지?" → 확인.
    2. **작성:** 엑셀 등에 [시스템: 계정계 / 구분: WAS / 솔루션명: WebLogic / 버전: 12c / 제조사: Oracle] 처럼 정리.
    3. **검증:** 개발팀장님이나 인프라 담당자에게 보여주고 "이거 맞나요? 빠진 거 없나요?" 확인 받음.

### 90. 미들웨어 솔루션 명세서 작성 (Preparation of Middleware Solution Specification)

**TẦNG A – NOTE NÉN (ÔN / ĐI THI)**

- **[1] 개념:** 미들웨어 솔루션 목록에 있는 각 솔루션별로 관련 정보들을 **상세하게 기술**하는 문서화 과정
- **[2] 핵심 키워드:** 제품안내서/설명자료 검토, 사용 환경/특징, **제약사항 확인**, 기술 지원 담당자
- **[3] 구조 / 관점 / 분류:** 시스템 통합 - 상세 설계 문서화
- **[4] 시험 포인트:**
    - **검토 자료:** 명세서를 쓸 때 무엇을 보고 쓰는가? → **'제품안내서'** 및 **'설명 자료'**
    - **검토 대상:** 단순히 이름만 쓰는 게 아니라 **사용 환경, 특징, 제공 기능** 등을 파악해야 함
    - **제약사항 확인 (중요):** 시스템 범위와 정상적인 서비스를 위해 필요한 환경 구성 등에 대한 **'제약사항'**이 존재하는지, **'기술 지원 담당자'**를 통해 확인해야 함
- **[5] 한 문장 설명:** 식별된 미들웨어의 명칭, 버전, 목적 등을 제품 설명서와 담당자를 통해 검토하고, 기능 및 제약사항을 정리하여 상세 명세서를 작성하는 과정이다.

**TẦNG B – NOTE 보충 (HIỂU SÂU)**

- **왜 필요한가?:**
    - 목록에 "WebLogic 쓴다"라고만 적혀있으면, 개발자가 "자바 버전은 몇을 써야 하지?", "메모리는 얼마나 필요하지?"를 알 수 없음.
    - 따라서 "WebLogic 12c, JDK 1.8 이상 필요, 최소 메모리 4GB" 처럼 **구체적인 스펙(Spec)**을 적어두는 것임.
- **제약사항(Constraints)의 중요성:**
    - "이 미들웨어는 리눅스에서는 잘 도는데 윈도우에서는 안 됩니다" 같은 치명적인 제약사항을 미리 파악하지 못하면 프로젝트 후반부에 큰 문제가 터질 수 있음
