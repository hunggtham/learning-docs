## Cách sử dụng casebook

Không nên học bằng cách bản sao (copy / 복사) nguyên mã (code / 코드). Với mỗi chapter, hãy tự trả lời bốn câu trước khi nhìn hiện thực (implementation / 구현): trạng thái (state / 상태) nào phải sống qua recomposition; trạng thái (state / 상태) nào phải sống qua cấu hình (configuration / 구성) thay đổi (change / 변경); trạng thái (state / 상태) nào phải sống qua tiến trình (process / 프로세스) death; dữ liệu nào phải sống qua uninstall hoặc phải được khôi phục từ máy chủ (server / 서버). Chỉ bốn câu này đã giúp phân biệt `remember`, `rememberSaveable`, `ViewModel`, `SavedStateHandle`, Room/DataStore và remote backend.

Sau đó hỏi tiếp: ai là nguồn chuẩn (source of truth / 정본), ai được quyền mutate trạng thái (state / 상태), mã (code / 코드) đang chạy ở luồng thực thi (thread / 스레드)/tiến trình (process / 프로세스)/vòng đời (lifecycle / 생명주기) nào, hệ thống bên ngoài (external system / 외부 시스템) nào có thể thất bại (fail / 실패), permission/năng lực (capability / 역량) nào có thể bị mất, thao tác (operation / 연산) nào cần idempotency, sản phẩm tạo ra (artifact / 산출물) nào thật sự được ship, dữ liệu nào là secret, và nếu phiên bản (version / 버전) N+1 quay lui (rollback / 롤백) về N thì lược đồ (schema / 스키마)/dữ liệu (data / 데이터)/nhị phân (binary / 이진) đặc tả hợp đồng (contract / 계약) có còn đọc hoặc link được hay không. Đây là các câu hỏi cấp cao (senior / 시니어)/Master quan trọng hơn việc thuộc tên API.

Trường hợp (case / 사례) 08–09 nên được đọc như tầng “under the hood”. Không cần áp dụng bytecode/Binder lập luận (reasoning / 추론) vào mọi dòng mã (code / 코드); hãy dùng khi lớp trừu tượng (abstraction / 추상화) leak: bản dựng (build / 빌드)/plugin incompatibility, Java interop kỳ lạ, coroutine ngăn xếp (stack / 스택) khó hiểu, bộ nhớ (memory / 메모리)/hiệu năng (performance / 성능) hotspot, ANR, reflection/R8 issue, IPC hoặc nhị phân (binary / 이진) tính tương thích (compatibility / 호환성) bài toán (problem / 문제).

Trường hợp (case / 사례) 10–14 là tầng “Android nền tảng (platform / 플랫폼) đặc tả hợp đồng (contract / 계약)”. Chúng giúp trả lời những câu hỏi mà kiến trúc (architecture / 아키텍처) thuần Kotlin không giải thích được: vì sao permission cũ đổi hành vi (behavior / 동작) khi mục tiêu (target / 대상) SDK tăng, vì sao camera/BLE phải có máy trạng thái (state machine / 상태 머신) riêng, vì sao khả năng tiếp cận (accessibility / 접근성) nằm trong ngữ nghĩa (semantics / 의미론) cây (tree / 트리), vì sao notification tap phải hoạt động khi tiến trình (process / 프로세스) cold-start, và vì sao widget/dịch vụ (service / 서비스)/receiver không được xem như cách giữ app sống.

Trường hợp (case / 사례) 15–20 là tầng **bản dựng (build / 빌드), phân phối (distribution / 분포) và ecosystem kỹ thuật (engineering / 엔지니어링)**. Chúng nối mã nguồn (source code / 소스 코드) với sản phẩm tạo ra (artifact / 산출물) thực tế: Gradle/AGP quyết định mã (code / 코드)/tài nguyên (resource / 자원) nào được compile; AAB/Play quyết định bytes nào tới thiết bị (device / 장치); bản địa (native / 네이티브) libraries thêm ABI/page-size/memory-safety đặc tả hợp đồng (contract / 계약); Android nền tảng (platform / 플랫폼) di chuyển (migration / 마이그레이션) thay hành vi (behavior / 동작) đặc tả hợp đồng (contract / 계약); startup quyết định đường găng (critical path / 임계 경로) đầu tiên; còn thư viện (library / 라이브러리)/SDK authoring biến API công khai (public API / 공개 API) và bản dựng (build / 빌드) siêu dữ liệu (metadata / 메타데이터) thành tính tương thích (compatibility / 호환성) obligation với bên tiêu thụ (consumer / 소비자) khác.

> **Nối mạch:** Cách dùng casebook xác định cách đọc một scenario; nguyên tắc xuyên suốt tiếp theo buộc mỗi case nối invariant, ownership, failure và release evidence.

## Nguyên tắc xuyên suốt

Casebook sử dụng một số quy ước nhất quán. UI kết xuất (render / 렌더링) từ immutable `UiState` và gửi sự kiện (event / 이벤트) xuống; `ViewModel` điều phối screen trạng thái (state / 상태) nhưng không trở thành cơ sở dữ liệu (database / 데이터베이스)/mạng (network / 네트워크) god đối tượng (object / 객체); repository sở hữu dữ liệu (data / 데이터) đặc tả hợp đồng (contract / 계약) và giải quyết nhiều dữ liệu (data / 데이터) nguồn (source / 소스); cục bộ (local / 로컬) cơ sở dữ liệu (database / 데이터베이스) thường là nguồn chuẩn (source of truth / 정본) cho tính năng (feature / 기능) offline-first; mạng (network / 네트워크) DTO không đi thẳng lên UI; coroutine phải có quyền sở hữu (ownership / 소유권)/thời gian tồn tại (lifetime / 수명) rõ ràng; cancellation không được nuốt; lỗi (error / 오류) được phân loại theo vận chuyển (transport / 전송)/giao thức (protocol / 프로토콜)/lĩnh vực (domain / 도메인) thay vì một `Exception` chung; authentication và authorization không bị nhầm lẫn; máy khách (client / 클라이언트) không được coi là trusted môi trường (environment / 환경); permission không được nhầm với nghiệp vụ (business / 비즈니스) entitlement; hệ thống (system / 시스템) thành phần (component / 컴포넌트)/bên ngoài (external / 외부) Intent được coi là ranh giới (boundary / 경계) không tin cậy; hiện vật bản dựng (build artifact / 빌드 산출물) phải dấu vết (trace / 추적) được về nguồn (source / 소스)/toolchain; bản địa (native / 네이티브) bộ nhớ (memory / 메모리) phải có quyền sở hữu (ownership / 소유권); di chuyển (migration / 마이그레이션) phải được kiểm thử (test / 테스트) bằng dữ liệu của lược đồ (schema / 스키마) cũ; bản phát hành (release / 릴리스) phải có khả năng quan sát và quay lui (rollback / 롤백).

Những nguyên tắc này không có nghĩa mọi app phải nhiều mô-đun (module / 모듈), Clean kiến trúc (architecture / 아키텍처) đầy đủ, động (dynamic / 동적) tính năng (feature / 기능), NDK hoặc có use trường hợp (case / 사례) cho từng phương thức (method / 메서드). độ phức tạp (complexity / 복잡도) chỉ được thêm khi nó mua được một lợi ích rõ ràng: ranh giới (boundary / 경계) dễ kiểm thử (test / 테스트) hơn, quyền sở hữu (ownership / 소유권) rõ hơn, bản dựng (build / 빌드) nhanh hơn, download nhỏ hơn, tính năng (feature / 기능) độc lập hơn, nền tảng (platform / 플랫폼) thất bại (failure / 실패) dễ recover hơn, hoặc di chuyển (migration / 마이그레이션)/rủi ro (risk / 위험) dễ kiểm soát hơn.

> **Bàn giao:** Sau **Nguyên tắc xuyên suốt**, hãy giữ lại kết luận và ranh giới của mục này; quay về [README](./README.md) khi cần định vị owner hoặc chọn nhánh học tiếp theo.
